# Техническая оценка #518: сохранять позицию и состояние при возврате назад

Дата: 2026-11-06. Код не менялся. Реализацию начинать только после согласования Павлом.
Источник требований: Issue #518 и сообщение Павла в треде.

## 1. Как устроена навигация сейчас и почему теряется состояние

Роутера нет. Всё приложение (`web/src/App.tsx`, `ShellInner`) — один компонент:

- Текущий раздел хранится в `useState<Tab>` (`tabRaw`). Нижняя панель (`BottomNav`) просто вызывает `setTab`.
- Активный экран выбирается длинной цепочкой тернарных условий (`const screen = ...`). При смене вкладки старый экран **размонтируется**, и всё его локальное состояние (поиск, фильтры, вкладки, раскрытые блоки, загруженные данные) пропадает.
- Для администратора раздел из «Ещё» рендерится через `More` → `AdminSection`. Выбранный подраздел хранится в `useState` внутри `More` (`sub`). Повторное нажатие «Ещё» принудительно сбрасывает: `setMoreKey(k => k + 1)` меняет `key` у `<More>` и возвращает к каталогу. Это прямо противоречит требованию спецификации.
- Вложенные экраны (карточка игрока, редактирование, матч, лагерь, заказ экипировки и т. д.) — это локальные `useState` внутри каждого экрана (`card`, `edit`, `open`, `sel` и т. п.; ~36 таких мест, у 21 экрана есть `BackNav`). «Назад» — это `setCard(null)`: список после этого монтируется заново, заново грузит данные и начинает с начала страницы. Поэтому теряются и фильтры (`q`, `gid`, `status`, `onlyUnpaid` в `Players.tsx`), и прокрутка.
- Прокрутка: восстановления нет вообще. Есть только `scrollTop = 0` в `About.tsx` и блокировка прокрутки под модальным окном (`useBodyScrollLock` в `ConfirmSheet.tsx`, она корректно возвращает позицию и менять её не нужно).
- Кнопка «Назад»: `ui/nav.tsx` → `BackNav`. Каждый экран сам регистрирует нативную `Telegram.BackButton` (или рисует свою кнопку в браузере) и передаёт свой `onBack`. Единой точки нет; история браузера (`history`/`popstate`) не используется, поэтому системная кнопка «Назад» в браузере/PWA уходит из приложения, а не на предыдущий экран.
- Обновление страницы: состояние нигде не хранится, после перезагрузки всегда стартовый раздел по роли (`sessions` / `cash` / `home` / `about`). Единственное исключение — `Sessions.tsx` со своим `localStorage` (`STATE_KEY`: дата, группа, вкладка) — это локальная заплатка, её нужно перевести на общий механизм. Режим «Тренер/Родитель» хранится в `ks.parentMode` и остаётся как есть.
- Предупреждения о несохранённых изменениях: общего механизма нет. Есть локальные флаги `dirty` (`Sessions`, `IndMarks`, `Equipment`), которые только отключают кнопку «Сохранить». Уход с формы (кнопка «Назад», смена вкладки, закрытие) данные теряет молча.
- Выход из аккаунта: в `ShellInner` отдельного состояния «выход» нет, поэтому очистку надо привязать к событию Supabase `SIGNED_OUT` и к смене пользователя.

## 2. Предлагаемый единый механизм

Роутер-библиотека не нужна (приложение в Telegram Mini App, адресной строки нет, экраны завязаны на роли). Предлагается небольшой собственный слой `web/src/nav/` — «хранилище навигации» с тремя частями.

**а) Стек на каждый раздел.** Для каждого корневого раздела (вкладка нижней панели; «Ещё» — тоже раздел) хранится независимый стек записей:
`{ screen: 'players.list' | 'players.card' | ..., params: { playerId }, ui: { q, gid, status, ... }, scrollY }`.
Переключение между разделами не трогает чужие стеки. Повторное нажатие на активную вкладку ничего не сбрасывает. «Ещё» хранит и позицию в каталоге, и стек подразделов.

**б) Хуки вместо локального `useState`.**
- `useNavState(key, initial)` — как `useState`, но значение живёт в записи стека и восстанавливается (фильтры, поиск, вкладки, раскрытые элементы). Миграция экрана сводится к замене `useState` на `useNavState` для сохраняемых полей.
- `useScreen({ name, params })` / `nav.push(...)`, `nav.back()` — вложенный экран открывается через стек, а не через `setCard`. Список при этом остаётся в стеке и восстанавливается.
- `useRestoreScroll(ready)` — запоминает `scrollY` при уходе и возвращает его, когда экран сообщил «данные загружены» (`ready`); до этого экран не показывается на нулевой позиции (нет «прыжка» и мигания). Явное действие «в начало» и обычный переход на новый экран позицию не восстанавливают.

**в) Одна кнопка «Назад».** Единственный владелец `Telegram.BackButton` и записи `history.pushState` / `popstate` для браузера/PWA — слой навигации. `BackNav` остаётся совместимой оболочкой (экраны меняются постепенно), внутри — вызов `nav.back()`.

**г) Сохранение и восстановление.**
- Снимок стеков пишется в `localStorage` (с debounce) под ключом `ks.nav.v1:<userId>:<mode>`, где `mode` = реальная роль / режим «Родитель» / предпросмотр администратора. Состояние каждого устройства хранится на нём же, поэтому устройства независимы автоматически. Профиль и данные не хранятся: только идентификаторы, значения фильтров и позиции.
- Версия схемы. Срока жизни нет: снимок действует, пока активна авторизация, до выхода или смены пользователя. При несовместимой версии формата старый снимок сбрасывается.
- Очистка: при `SIGNED_OUT`, при смене `userId`, при выходе из предпросмотра.
- **Проверки при восстановлении:** снимок применяется только после того, как `ShellInner` определил роль, права и группы. Раздел, недоступный сейчас по роли, отбрасывается; запись, ссылающаяся на сущность (игрок, матч, лагерь), перепроверяется запросом к базе (права проверяет RLS, а не клиент). Если сущности нет или нет доступа — показываем родительский список с короткой пометкой «Эта запись больше недоступна». Данные всегда загружаются заново, из снимка — только положение и настройки экрана.
- **Предупреждение о несохранённом:** `useDirtyGuard(isDirty)` регистрирует форму в слое навигации. Он перехватывает «Назад» (нативная и браузерная), смену вкладки, раздел из «Ещё» и `beforeunload` в браузере, и показывает существующий `ConfirmSheet` («Уйти без сохранения?»). Сами несохранённые черновики на диск не пишем (иначе в хранилище окажутся введённые данные детей/платежей) — см. вопросы.

## 4. Риски и зависимости

- **Восстановление прокрутки до загрузки данных.** Страница короче, чем нужно, → позиция не восстановится или будет скачок. Решение: `ready`-флаг в каждом экране и пропуск показа до восстановления; для длинных списков — запасной таймаут.
- **Устаревшие данные.** После возврата список может измениться (оплатили, удалили). Решение: данные грузятся заново, позиция восстанавливается «по возможности»; запись по `id`, а не по индексу.
- **Права и роли.** Снимок нельзя применять до определения роли; ключ включает режим (предпросмотр, «Родитель»), чтобы не смешивать состояния. Клиентская проверка только подсказка, настоящую проверку по-прежнему делает база.
- **Смешивание пользователей/устройств.** Ключ с `userId`, очистка по `SIGNED_OUT`; на общем устройстве — проверка при старте, что `userId` совпадает.
- **Telegram WebView:** поведение `BackButton`, системного жеста «назад» и перезагрузки WebView различается на iOS/Android/Desktop; нужна проверка на реальных устройствах, эмулятор не заменит. `localStorage` в Telegram может быть очищен — снимок считаем необязательным.
- **Большой объём миграции экранов (~60 файлов) и регрессии.** Поэтому поэтапно, с совместимой оболочкой `BackNav`, чтобы непереведённые экраны продолжали работать по-старому.
- **Конфликт с активной работой.** Открытых PR сейчас нет, `App.tsx` ни с кем не конфликтует. Но задачи #503 и #504 (баллы) и любые правки экранов во время миграции затрагивают те же файлы: желательно не вести их параллельно на одном экране.
- **Предупреждение о несохранённом + нативная «Назад» в Telegram:** иногда её нельзя перехватить для закрытия приложения; закрытие крестиком Telegram предупредить не даст (ограничение платформы, возможна только `enableClosingConfirmation`). Это стоит проверить и честно зафиксировать.
- **Зависимости:** новых библиотек нет; без миграций БД; production-изменений нет.

## Редакция 2 (2026-11-06, по уточнениям Павла)

Решения Павла: (1) срока хранения нет, состояние живёт до выхода из аккаунта или смены пользователя, при несовместимой версии формата сбрасывается; (2) повторное нажатие на активную вкладку ничего не меняет и не прокручивает; (3) системная «Назад» в браузере/PWA идёт по внутренней истории; (4) черновики форм не сохраняем; (5) предупреждение при уходе и обновлении там, где платформа позволяет. Вопросы из первой редакции закрыты.

### 7. Что попадает в localStorage (хранение по белому списку)

Ключ: `ks.nav.v1:<userId>:<mode>`, где `mode` = `real` / `parent` / `preview-<роль>`. Формат: JSON `{ v: 1, stacks: { <раздел>: [ { screen, params, ui, scrollY } ] } }`.

Разрешено хранить (только небелый «всё что есть в state», а явно объявленные поля):
- идентификаторы сущностей в `params` (`playerId`, `eventId`, `groupId` — UUID, без имён);
- выбор вкладки, режимы переключателей, раскрыт/свёрнут, выбранный месяц и дата, выбранная группа (id), статус-фильтр;
- `scrollY` (число).

Запрещено хранить (проверяется кодом, не договорённостью):
- содержимое любых форм и черновики (ввод, суммы платежей, комментарии, телефоны, размеры, тексты статей);
- платёжные и персональные данные, ответы базы, токены;
- имена и фамилии.

**Поисковые запросы.** Строка поиска может содержать имя ребёнка, поэтому по умолчанию она **не сохраняется** между перезагрузками (`useNavState(..., { persist: false })` для поля `q`). Внутри сеанса (возврат «Назад», переключение вкладок) запрос живёт только в памяти приложения и восстанавливается. После обновления страницы поиск пустой, а фильтры и вкладки восстанавливаются. Если Павел захочет, чтобы поиск переживал перезагрузку, это отдельное решение; сейчас рекомендую нет.

**Как это обеспечивается.**
- Каждое сохраняемое поле объявляется явно (`persist: true` и тип). По умолчанию поле не пишется на диск; новое поле случайно не утечёт.
- Перед записью значение проходит проверку типа: строки допускаются только из набора разрешённых значений (перечисления) или UUID; произвольный текст отбрасывается. Юнит-тест падает, если в снимок попала строка вне белого списка.
- Тест-страж: снимок для набора экранов не содержит имён и сумм (проверка на тестовых данных с именем ребёнка).
- Хранилище только на устройстве, на сервер не уходит; состояния устройств независимы.

**Очистка.**
- Выход из аккаунта (`Profile.tsx`, `supabase.auth.signOut`) и событие `SIGNED_OUT` — удаляются все ключи `ks.nav.*`.
- Смена пользователя: при старте сравниваем `userId` с ключом; чужие ключи `ks.nav.*` удаляются.
- Несовместимая версия `v` или повреждённый JSON — ключ удаляется, приложение стартует с экрана по умолчанию.
- Выход из предпросмотра администратора — удаляется ключ `preview-*`.
- Запись/чтение в `try/catch` (хранилище может быть недоступно): без него приложение работает, просто без восстановления.
- Состояние авторизации: если сессия истекла и не обновилась, снимок не применяется и удаляется.

### 8. Несохранённые формы и ограничения платформы

- Внутри приложения (Назад, смена вкладки, пункт «Ещё», открытие другого экрана) предупреждение работает везде одинаково через `useDirtyGuard` и `ConfirmSheet`.
- Браузер/PWA: при обновлении и закрытии вкладки используем `beforeunload` (браузер показывает свой стандартный диалог без нашего текста) и перехват `popstate` для системной «Назад».
- Telegram: перехватить закрытие приложения крестиком/свайпом и перезагрузку нельзя. Доступно `WebApp.enableClosingConfirmation()`, оно включает стандартное подтверждение закрытия; включаем его, пока есть несохранённая форма, выключаем после сохранения. Поведение на iOS, Android и Desktop отличается (где-то подтверждение не показывается при перезагрузке из меню), это **ограничение платформы**: фиксируем в документации и проверяем на реальных устройствах (этап 3), результат записываем в PR. Если на каком-то устройстве защиты нет, это явно указываем, а не обещаем.
- Черновики не сохраняются ни при каких условиях.
