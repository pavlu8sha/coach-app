# Правила работы с репозиторием

## Ветки

- `master` — стабильная интеграционная ветка.
- Новая работа начинается от актуального `master`.
- Имена веток: `feat/<short-name>`, `fix/<short-name>`, `perf/<short-name>`, `design/<short-name>`, `chore/<short-name>`.
- Не использовать одну ветку для несвязанных задач.
- Старые ветки не удалять до проверки, что уникальные коммиты либо сохранены в другой ветке, либо явно признаны ненужными.

## Pull Request

Каждый PR должен содержать:
- что и зачем меняется;
- связанные Issue (например, `Closes #12`, только если PR действительно закрывает задачу);
- тесты, выполненные и не выполненные;
- риск для данных, платежей, посещаемости и совместимости;
- статус deployment: не выполнялся / запланирован / опубликован и проверен.

Перед слиянием:
- CI зелёный;
- diff просмотрен;
- нет неразрешённых критичных замечаний;
- изменяющие данные операции проверены без записи в production;
- изменения авторизации и прав доступа проверены отдельно;
- понятно, как откатить изменение.

Не вливать PR только потому, что тесты прошли. Прохождение CI не заменяет code review.

## Безопасность production

- Не выполнять тесты, миграции и экспериментальные операции, записывающие в боевые таблицы.
- `/dev` production Apps Script использует те же таблицы, что и `/exec`; не считать его изолированной тестовой средой.
- Не запускать `clasp push` и не публиковать новую версию без явного решения о готовности.
- Перед deployment сверять целевую ветку, commit SHA и ожидаемый набор изменений.
- Не добавлять в логи PIN-коды, токены, персональные данные игроков/родителей или содержимое платежей.

## Проверки

Локальный запуск полного набора Node.js-тестов:

```bash
node --test tests/*.mjs
```

Для изменений, требующих Google Apps Script runtime, использовать безопасные моки/статический анализ и отдельную тестовую среду, если она будет создана. Не заменять это проверками записи в production.

## Завершение задачи

Issue считается завершённой, когда:
1. изменения объединены в `master` либо явно отменены;
2. проверки и review зафиксированы;
3. статус deployment указан отдельно;
4. документация/статус обновлены, если изменился рабочий процесс или архитектурное решение.
