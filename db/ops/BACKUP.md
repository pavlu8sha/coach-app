# Резервные копии боевой базы (REL-01)

Статус: **копий сейчас нет.** Supabase на бесплатном тарифе не делает автоматических бэкапов (`docs/LAUNCH_READINESS_2026-11.md`, `docs/LAUNCH_AUDIT.md`). Ошибочный `delete`, неудачная миграция или потеря доступа к проекту сейчас означают потерю данных. Этот документ и скрипты закрывают пробел без платного тарифа.

Скрипты:

| Файл | Что делает | Трогает боевую БД? |
|---|---|---|
| `db/ops/backup-pg-dump.sh` | логический дамп (`pg_dump -Fc`), manifest, шифрование age, ротация | только читает (pg_dump, select) |
| `db/ops/backup-manifest-counts.sql` | число строк по таблицам `public` | только select |
| `db/ops/backup-restore-check.sh` | поднимает копию в **локальном** PostgreSQL, сверяет счётчики, запускает `preflight.sql` | нет |
| `db/ops/BACKUP_ACCEPTANCE.md` | условия приёмки, по которым написаны тесты | нет |
| `tests/ops/backup-scripts.test.mjs` | статические проверки скриптов (без подключения к БД) | нет |

## 1. Что входит в копию и чего в ней нет

**Входит** (схемы): `public` (все таблицы приложения), `auth` (учётные записи Supabase Auth: используются в `supabase/functions/tg-login` и `tg-auth`), `storage` (метаданные файлов), `cron` (расписания pg_cron из `db/ops/*cron*.sql`), `snap_*` (снимки перед импортом, например `snap_20261031`).

**Не входит, это надо знать:**
- **Файлы Storage** (например PDF документов сборов в бакете `camp-docs`). В дампе только метаданные. Сами файлы качать отдельно (Dashboard → Storage или API) или признать риск.
- **Edge Functions** (код) лежат в репозитории (`supabase/functions/`), восстанавливаются деплоем.
- **Секреты** (токен Telegram-бота, service-role ключи, переменные Cloudflare Pages) в дампе не попадают. Список, где они заданы, вести отдельно у владельца, значения не в репозитории и не в чате.
- **Google Таблицы старого приложения** живут у Google, версии доступны в «История версий».

## 2. Настройка (один раз, делает Павел)

1. **Клиент PostgreSQL версии не ниже сервера.** Версию сервера видно в Dashboard → Project Settings → Database. Скрипт проверяет это сам и остановится, если клиент старее. Для восстановления проверкой нужен локальный PostgreSQL той же или более новой версии.
2. **Ключ age** (шифрование копий):
   ```
   mkdir -p ~/.config/kickstart && age-keygen -o ~/.config/kickstart/age-key.txt
   ```
   Строка `# public key: age1…` идёт в `AGE_RECIPIENT`. **Приватный ключ (`age-key.txt`) сохранить во втором месте** (менеджер паролей или распечатка в сейфе). Без него все копии не открываются. Файл в репозиторий и в облако без шифрования не класть.
3. **Строка подключения.** Supabase → Connect → **Session pooler**, порт 5432. Пароль базы: Project Settings → Database (если не помните, сбросьте его и обновите строку). В чат пароль не присылать.
4. **Файл настроек** `~/.config/kickstart/backup.env` (права 600):
   ```
   SUPABASE_DB_URL='postgresql://postgres.<ref>:<пароль>@<хост>:5432/postgres'
   AGE_RECIPIENT='age1…'
   BACKUP_DIR="$HOME/kickstart-backups"
   ```
   `chmod 600 ~/.config/kickstart/backup.env`. Скрипт откажется работать с другими правами.
5. **Локальная копия репозитория** на компьютере, с которого будут запускаться копии (`git pull` перед запуском).

## 3. Расписание

Ручной запуск:
```
cd ~/coach-app && db/ops/backup-pg-dump.sh
```
Автоматически, ежедневно в 03:30 (cron на Mac/Linux):
```
30 3 * * * cd $HOME/coach-app && git pull -q && db/ops/backup-pg-dump.sh >> $HOME/kickstart-backups/backup.log 2>&1
```
Компьютер должен быть включён в это время. Если не был, копия не сделана: проверяйте дату последней копии в `BACKUP_DIR` раз в неделю. Для надёжности нужна вторая точка (см. раздел 6).

**Перед каждой миграцией** копия делается вручную, отдельным типом:
```
BACKUP_KIND=premigration db/ops/backup-pg-dump.sh
```
Такие копии лежат в `premigration/` и автоматически не удаляются.

## 4. Хранение и ротация

| Где | Что | Сколько |
|---|---|---|
| `BACKUP_DIR/daily/` | ежедневные копии | 14 дней (`KEEP_DAILY`) |
| `BACKUP_DIR/weekly/` | воскресная копия | 8 недель (`KEEP_WEEKLY`) |
| `BACKUP_DIR/premigration/` | копии перед миграциями | вручную, не реже чем через 180 дней |

Каждая копия состоит из `kickstart-ГГГГ-ММ-ДД_ЧЧММ.dump.age` и `.manifest.age` (число строк по таблицам и sha256 открытого дампа). Файлы только в зашифрованном виде.

**Вторая точка хранения** (обязательна до 1 декабря): раз в неделю копировать последние файлы на внешний диск или в облачную папку. Облако допустимо только для уже зашифрованных файлов. Доступ к папке только у владельца.

## 5. Проверка восстановления

Копия, которую не восстанавливали, не считается копией. Проверка:
```
TEST_PG_URL=postgresql://postgres@localhost:5432 \
AGE_IDENTITY=$HOME/.config/kickstart/age-key.txt \
db/ops/backup-restore-check.sh "$HOME/kickstart-backups/daily/kickstart-ГГГГ-ММ-ДД_ЧЧММ.dump.age"
```
Скрипт: проверяет sha256 по manifest, читает оглавление, создаёт роли `anon`, `authenticated`, `service_role`, восстанавливает в локальную базу `kickstart_restore_check`, сверяет счётчики строк по всем таблицам `public`, запускает `db/ops/preflight.sql` и удаляет тестовую базу. Код выхода 0 означает «пройдено». Адреса Supabase скрипт отвергает.

Частота: **раз в месяц** и **после каждого изменения скриптов**. Первая успешная проверка на реальной копии обязательна до 1 декабря. Результат вписать в раздел 8.

## 6. Восстановление: что делать

Главное правило: **не восстанавливать всю базу поверх боевой.** С 01.11 тренеры отмечают посещаемость и матчи в новом приложении; полный откат к копии сотрёт их работу (см. `docs/SATURDAY_IMPORT_CHECKLIST.md`, строка про «Восстановление»).

| Ситуация | Действие |
|---|---|
| Ошибочно удалена или испорчена одна таблица | Восстановить копию локально, выгрузить нужные строки, вернуть точечно вместе с разработчиком. Сначала на тестовой копии. |
| Испорчена большая часть данных | Поднять копию в **новом** Supabase-проекте (или отдельной базе), сверить счётчики, решить вместе с владельцем, что переключать. |
| Проект Supabase недоступен или удалён | То же, что выше, плюс восстановление секретов из списка владельца и повторный деплой Edge Functions из репозитория. |

Перед любым восстановлением сделать свежую копию текущего состояния (`BACKUP_KIND=premigration`).

## 7. Цели восстановления

- **RPO** (сколько данных можно потерять): до 24 часов при ежедневной копии, меньше при копии перед миграцией.
- **RTO** (сколько времени на восстановление): не измерено. Заполнить после первой проверки на реальной копии: время `backup-restore-check.sh` и отдельно время восстановления в новый проект.

## 9. Решение владельца (не технический вопрос)

Два пути, их можно комбинировать:

- **Скрипты (бесплатно):** ежедневный дамп на компьютер Павла плюс вторая точка. Даёт RPO до 24 часов и восстановление своими силами. Требует включённого компьютера и ручной работы при восстановлении.
- **Платный тариф Supabase:** Pro (ежедневные автоматические бэкапы, около $25 в месяц) и PITR (восстановление на момент времени, около $100 в месяц, по `docs/LAUNCH_AUDIT.md`). Даёт восстановление без участия компьютера Павла, но не заменяет внешней копии.

Рекомендация: начать со скриптов сразу, решение о Pro принять до 1 декабря. Вопрос владельцу: нужен ли PITR на старте.
