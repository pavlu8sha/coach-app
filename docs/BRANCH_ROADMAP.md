# Карта веток и дорожные карты Coach App

Актуально на 2026-10-21. Документ для Павла, Claude, OpenCode и технического ревью. Описывает все ветки, найденные в репозитории на момент инвентаризации, и точку возобновления работы.

> **Перед началом любой работы:** сверить актуальный HEAD ветки, master, открытые PR/Issues, CI и рабочее дерево. Состояние в этом документе — снимок на дату выше. Если GitHub расходится с документом, проверить фактическое состояние и обновить его.

## Быстрый старт для разработчика

1. Прочитать этот файл, [PROJECT_STATUS.md](PROJECT_STATUS.md), [AGENT_WORKFLOW.md](AGENT_WORKFLOW.md) и связанный Issue/PR.
2. Проверить актуальные SHA ветки и base, открытые PR, CI и git status.
3. Не продолжать старую ветку только потому, что она существует. Исторические ветки ниже не возобновлять без нового решения владельца.
4. На одну область кода — один активный исполнитель. Не редактировать stage-abc параллельно с OpenCode.
5. Никаких clasp push, deployment, production-записей, merge или удаления веток без отдельного решения владельца. /dev production Apps Script использует боевые таблицы.

## Дорожные карты активных направлений

### A. OpenCode — PR #2 / этапы A и B

**Возобновлять с:** фактического состояния stage-abc и незакрытых пунктов [Issue #4](https://github.com/pavlu8sha/coach-app/issues/4), а не с повторной реализации сделанного.

1. Проверить git status, HEAD, diff и коммиты относительно актуального master.
2. Завершить контрольную проверку этапа A и тестов; указывать только реально запущенные проверки.
3. Составить матрицу серверных функций: endpoint, требуемая роль, фактическая проверка, доступ к данным, побочные эффекты и тест.
4. Проверить каждую операцию записи на соблюдение DRY_RUN без обращения к боевым данным.
5. Проверить clubSource_: валидацию ID, повторное использование файла, ошибки доступа и совместимость.
6. Проверить пересечение CI с PR #3 и предложить разрешение, не меняя параллельно чужую ветку.
7. Описать этап B отдельными PR, с зависимостями и критериями готовности. Не начинать массовый рефакторинг app*-функций, внедрение actor, ключей кэша клубов или таблицы clubs без отдельного согласования.
8. Отчитаться и остановиться до решения владельца.

### B. Документация и CI — PR #3

**Возобновлять с:** [PR #3](https://github.com/pavlu8sha/coach-app/pull/3) и текущего HEAD chore/repository-governance.

1. Проверить все файлы PR и убедиться, что бизнес-кода в нём нет.
2. Проверить workflow именно на актуальном HEAD; прежний успешный запуск не доказывает результат для новых коммитов.
3. Согласовать единственное место для .github/workflows/test.yml. Не редактировать stage-abc в обход OpenCode.
4. Проверить, что README ведёт к карте веток и статусу.
5. Оставить PR draft до завершения проверок и решения владельца.
6. После merge проверить workflow на master и настроить required status check. Не считать это deployment.

### C. Производительность — Issue #5

**Возобновлять с:** статического review perf-phase1; не cherry-pick вслепую.

1. Проверить актуальные base/head SHA, уникальные коммиты и CI.
2. Принять решение по каждой оптимизации: перенести, заменить уже существующим кодом или отклонить.
3. Проверить эквивалентность в платежах, посещаемости, составе групп, каталоге экипировки и индивидуальных занятиях.
4. Сделать PERF_LOG выключенным по умолчанию; не писать в логи персональные или платёжные данные.
5. Перенести только подтверждённые изменения в свежую ветку от актуального master, добавить тесты и открыть PR.
6. Сопоставить измерения до/после. Не выполнять замеры сценариями, которые пишут в production.

## Как оформлять новые ветки

Для каждой новой ветки создать/обновить Issue и добавить запись с назначением, ожидаемым результатом, ответственным, base SHA, сделанным (коммиты/файлы), оставшимися шагами, тестами с фактическими результатами, рисками, критерием завершения, следующим владельцем и отдельным статусом deployment.

После существенного изменения обновлять эту карту в том же PR, который меняет статус, либо в отдельном согласованном documentation PR.
