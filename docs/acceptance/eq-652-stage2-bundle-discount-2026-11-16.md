## Разбиение и порядок (важно)
Три части, три миграции, **порядок применения строгий**: 2a → 2c → 2b.
- **2a (0205): модель и расчёт.** Поля и таблицы, чистая функция расчёта, ручной пересчёт и предпросмотр. Расчёт не подключён к созданию, правке, отмене, восстановлению. Снят запрет «итог ниже оплаченного».
- **2c (0206): исторические заказы.** Данные: ручная корректировка и заморозка 14 исторических комплектов, отказ у 9 заказов в рассрочку. Выполняется Павлом с до- и после-сверкой; ставит отметку `freeze_2c`.
- **2b (0207): автоматический пересчёт.** Вызовы расчёта из `eq_create_order`, правок строк, смены способа оплаты, `eq_cancel_order`, `eq_restore_order`; предпросмотр при восстановлении; клиент перестаёт писать итог.

Причина порядка: если включить автоматический пересчёт (2b) до заморозки старых комплектов (2c), первый же пересчёт добавит вторую скидку 95 к 14 уже сниженным заказам (итог 525 → 430). Поэтому 2b отказывается включаться, пока не пройдена проверка 2c (условие Б1). Номера 0205–0207 перед каждым пушем сверяются со свежим master на занятые.

## Общие инварианты (все части)
**И1.** Платёжный журнал `service_payments` и `paid` никогда не меняются расчётом, пересчётом, заморозкой или сбросом: отпечаток журнала и сумма `paid` до и после каждого перехода идентичны. `opening_balance` не затрагивается.
**И2.** Заказы разных детей никогда не участвуют в одном расчёте.
**И3.** Производственный статус, строки и выдача не меняются расчётом (только поля итога и корректировок).
**И4.** `total = сумма (unit_price × quantity) + manual_adjustment + bundle_adjustment` у любого заказа после любой операции; `bundle_adjustment ≤ 0`.
**И5.** Расчёт воспроизводим: результат зависит только от входных данных (план v5, 2.9) и не от истории отмен и восстановлений.
**И6.** Повторный запуск при тех же входных данных не меняет заказы, записи комплектов и события (пишется только журнал запуска).
**И7.** Права на новые функции проверены на базе с привилегиями по умолчанию Supabase (`alter default privileges ... grant execute ... to anon, authenticated, service_role`).

## Часть 2a (0205): модель и расчёт

**А1. Поля заказа.** `discount_forfeited boolean not null default false` (необратимо автоматически), `manual_adjustment numeric not null default 0`, `bundle_adjustment numeric not null default 0 check (bundle_adjustment <= 0)`, `discount_state text` (`ok` / `unchecked`). Миграция 0205 сама заполняет `manual_adjustment = total − сумма строк` у всех существующих заказов (включая отменённые; защита отменённого заказа на время заполнения снимается внутри миграции), поэтому И4 выполняется сразу, а `total` не меняется. Остальные новые поля имеют значения по умолчанию. Для заморозки добавлены `legacy_bundle_id` и таблица `equipment_legacy_bundles` (данные в 2c). Прямая запись `bundle_adjustment`, `discount_forfeited`, `legacy_bundle_id`, `discount_state` вне функций расчёта закрыта защитой заказа. Правка `total` напрямую или функциями `eq_edit_order`/`eq_edit_line`/`eq_add_line`/`eq_delete_line` сохраняет И4: расхождение уходит в `manual_adjustment` (триггер).
**А2. Таблицы (только добавление записей, права по образцу `equipment_order_events`).** `equipment_bundles` (замыкающий заказ, состав по строкам, база, процент, округление, скидка, `active`/`revoked`, причины создания и отзыва; у ребёнка не более одной `active`), `equipment_bundle_status` (состояние ребёнка `none`/`active`/`unchecked`, причина), `equipment_bundle_runs` (журнал запусков со снимком входных данных).
**А3. Чистая функция расчёта** по правилам плана v5 п. 2.2 и 2.5: член комплекта по группе `equip.discNeedOwn` (самая ранняя единица); `equip.fullPrice` вне комплекта; база = исходные `unit_price` членов; проверка `equip.discNeedAll` по строкам замыкающего заказа; замыкающий = участвующий заказ с наибольшим (`created_at`, `ordered_on`, `id`); отказ действует по заказу (R2); отменённые заказы не участвуют (R1); скидка = база − округление(база × (1 − pct/100)) до `equip.discRound`, «половина вверх», в `numeric`.
**А4. Контрольные значения.** Расчёт воспроизводит таблицу переходов этапа 0 (A1…H4) и, в частности: комплект 620 → 525; оплачено 300 остаётся на своём заказе; остаток 225; третий заказ «Дождевик» 110 стоит 110 (дефект «15 ₾» устранён); Ф в рассрочку и КД полная: скидки нет; Д2 в рассрочку после комплекта: скидка остаётся.
**А5. Настройки.** Значения по умолчанию в SQL совпадают с `clubSettings.ts` (15, 5, правила, `equip.fullPrice`), тест паритета. Некорректное значение: скидки нет, состояние `unchecked`, автоматический пересчёт его не снимает, ручной снимает только после успешной проверки.
**А6. Порядок и ничья.** Выбор «самая ранняя единица» и «замыкающий» идут по (`created_at`, `ordered_on` по возрастанию с пустыми первыми, `id`). Если порядок определился только по `id`, в журнале запуска стоит отметка `tie_break_id` (у 110 прод-заказов без даты это возможно).
**А7. Ручной пересчёт и предпросмотр.** `eq_bundle_preview(player)` (только чтение, глобальный администратор: функции `eq_*` в этом модуле требуют `is_admin()`) возвращает итоги заказов ребёнка до и после, переплату, замыкающий заказ, причину. `eq_bundle_recalc(player, 'manual')` только глобальный администратор, применяет результат одной транзакцией с блокировкой ребёнка, затем заказов по возрастанию `id`.
**А8. Снятие запрета «итог ниже оплаченного» (Q4).** `eq_edit_order`, `eq_edit_line`, `eq_delete_line` не отклоняют итог меньше `paid`; переплата показывается (`eq_order_overpaid`); `eq_add_payment` по-прежнему отклоняет оплату сверх итога (`paid above total`). Тест `rls_equipment_admin_test.sql:50` и тексты клиента обновлены.
**А9. Ручной сброс отказа (Q3).** `eq_forfeit_reset(order, reason)`: только глобальный администратор, причина обязательна, запись в события заказа, платежи не затрагиваются; сам по себе итог не меняется до пересчёта.
**А10. Охрана отменённого заказа.** Пересчёт может менять у отменённого заказа только `bundle_adjustment` и `total` (ветка `eq.op = 'recalc'` в `eq_orders_guard`, тело берётся из 0188); остальные поля остаются замороженными.
**А11. Отмена и восстановление без пересчёта в 2a.** Поведение `eq_cancel_order`/`eq_restore_order` не меняется до 2b.
**А12. Сводка по ребёнку (Q5).** `eq_player_equipment_summary(player)`: оплачено на отменённых заказах и сверх итога, к оплате по действующим; права как у чтения заказов. Показывается в карточке заказа.

**А13. Предохранитель до заморозки.** Пока в `equipment_bundle_steps` нет отметки `freeze_2c`, `eq_bundle_preview` и `eq_bundle_recalc` отвечают `bundle freeze not applied` (иначе первый же ручной пересчёт добавил бы вторую скидку 95 к 14 историческим заказам). Отметку ставит только 2c.
**А14. Причины.** `none`: `not_complete`, `no_discount` (процент 0 или скидка не больше 0), `need_all_failed`, `forfeited_order`; `unchecked`: `settings_invalid`. Причины отзыва: `closing_order_cancelled`, `member_order_cancelled`, `composition_changed`, `forfeited_order`, `need_all_failed`, `settings_invalid`, `restore_recalc`, `manual`.

## Часть 2c (0206): исторические заказы (данные, выполняет Павел)

**В1. Классификация.** Для каждого заказа `delta = total − сумма строк`. `exact`: ничего. `manual_up`/`manual_down`: `manual_adjustment = delta` (уже записана миграцией 0205), не комплект. `legacy_confirmed`: полный комплект, замыкающий, без рассрочки, `delta` равна минус расчётной скидке в пределах 0,01: `manual_adjustment = delta` (уже записана 0205), комплект записывается как исторический и **заморожен целиком** (`legacy_bundle_id`). `legacy_review`: заморожен «на разбор», автопересчёт не трогает.
**В2. Отказ (F4).** У заказов с `installment = true` ставится `discount_forfeited = true`; исторический `installment` не меняется.
**В3. Сохранность.** После миграции отпечатки заказов (id, total, paid, status, installment, location, ordered_on), строк и журнала совпадают с контрольными (разрешены только новые колонки); `total` каждого заказа не изменился; сумма `total` 38015, `paid` 32135. Любое расхождение откатывает миграцию целиком (один блок, самопроверка внутри).
**В4. Ожидаемый результат на проде.** 14 заказов с `manual_adjustment = −95` и замороженным комплектом, у остальных 135 корректировка 0, 9 заказов с отказом. Если фактическое число классов отличается, миграция останавливается, не применяя ничего.
**В5. Заморозка защищает от двойной скидки.** Тест: у замороженного комплекта автоматический и ручной пересчёт не добавляют вторую скидку; итог заказа 525 остаётся 525.
**В6. Снятие заморозки** только глобальным администратором с подтверждением и предпросмотром (поведение описано в 2b, Б5).
**В7. Откат.** Скрипт отката возвращает корректировки к 0, снимает заморозку и отказ; платежи не затрагиваются.

## Часть 2b (0207): автоматический пересчёт

**Б1. Предохранитель.** Функции с автоматическим пересчётом не работают, пока в базе нет отметки применённой 2c (иначе исключение `bundle freeze not applied`): защита от двойной скидки. Отметка `freeze_2c` ставится в `equipment_bundle_steps` (создана в 0205). Окно между 2c и 2b: заказы, созданные прежним клиентом с итогом со скидкой, попадают в `manual_adjustment` и не заморожены; 2b перед включением повторяет классификацию и отказывается включаться (`unfrozen legacy discount`), пока такие заказы есть (их замораживает или разбирает Павел).
**Б2. Вызовы.** `eq_bundle_recalc(player, 'auto')` внутри транзакции после: создания заказа, изменения состава/количества/строки, изменения способа оплаты, отмены, восстановления. Не запускается из-за смены настроек, каталога, статусов, выдачи и платежей. Единый порядок блокировок во всех функциях `eq_*`.
**Б3. Рассрочка.** Выбор рассрочки ставит `discount_forfeited` (необратимо автоматически); смена действующего заказа комплекта на рассрочку снимает скидку (F2); возврат на полную оплату скидку не возвращает.
**Б4. Отмена.** Отмена любого участвующего заказа отзывает запись комплекта и пересчитывает по оставшимся (S14–S16); у отменённого замыкающего `bundle_adjustment = 0`; платежи не меняются, возврат не создаётся.
**Б5. Восстановление (Q6).** `eq_restore_order` не выполняется молча: клиент сначала вызывает предпросмотр (итоги до и после, переплата, куда переезжает скидка) и требует явного подтверждения; серверная функция принимает подтверждение параметром и при его отсутствии отвечает `confirm required` с предпросмотром. Способ оплаты и отказ восстановленного заказа сохраняются (R3).
**Б6. Идемпотентность.** Повторное создание с тем же ключом (этап 1) не пересчитывает дважды; параллельные операции над одним ребёнком сериализуются.
**Б7. Клиент.** «Новый заказ» и кнопка «Пересчитать» показывают результат серверного предпросмотра; браузер больше не передаёт итог со скидкой (`custom_total` только у глобального администратора как ручная корректировка, Q8).
**Б8. Ошибки настроек.** Заказ создаётся без скидки с меткой «скидка не проверена»; создание не блокируется.
