# Условия приёмки: защита платежей абонементов от повторного INSERT (#724, миграция 0214)

Деньги, суммы, тарифы, расчёт долга, права и история платежей не меняются. Добавляется только ключ операции.

## Модель

- В `payments` добавляется `request_id uuid` и уникальный частичный индекс `(recorded_by, request_id) where request_id is not null`
  (как у `service_payments` в 0188). Ключ задаёт клиент; автор берётся из сессии триггером `stamp_payment_author`.
- Запись платежа идёт через функцию `payment_add(req, pid, amt, d, mth, fm)`: `security invoker`, то есть те же права и RLS,
  что у прямого INSERT (пишет только администратор). Вставка: `insert ... on conflict (recorded_by, request_id) do nothing`.
  Защита работает на уровне PostgreSQL: два параллельных запроса с одним ключом ждут друг друга на уникальном индексе.
- Возврат функции: `{id, duplicate}`. `duplicate = true` означает «эта операция уже записана ранее», новой строки нет.
- Платёж без ключа (прямой INSERT, импорт, отмена с `cancels`) работает как раньше: `request_id` остаётся `null`.
  Отмена платежа уже идемпотентна по `cancels unique` (0097) и в эту задачу не входит.

## Условия

1. **Обычная запись.** Вызов с новым ключом создаёт ровно одну строку с теми же полями, что прямой INSERT:
   игрок, сумма (до 2 знаков), `paid_on`, `for_month`, `method`; `recorded_by` и `recorded_at` из сессии; `pay_month` считается как раньше.
   Результат `duplicate = false`. Отрицательная сумма (исправление) допускается, как сейчас; ноль и `null` отклоняются.
2. **Повтор того же запроса.** Тот же автор, тот же ключ, те же данные: новых строк нет, возвращается `id` первой строки и `duplicate = true`, ошибки нет.
3. **Потерянный ответ.** Первая запись зафиксирована, клиент ответа не получил и повторил: результат как в п. 2; долг и касса считают платёж один раз.
4. **Параллельные запросы с одним ключом** (отдельные сессии, одновременно): одна строка в `payments`, один запрос получает `duplicate = false`,
   остальные `duplicate = true`, ошибок нет. Если первая транзакция откатилась, повтор записывает платёж.
5. **Ключ с другим содержимым.** Тот же автор и ключ, но другой игрок, сумма, дата, месяц или способ: ошибка `request id reused` (22023), строк не добавляется, исходная строка не меняется.
6. **Разные ключи.** Два одинаковых по содержимому платежа с разными ключами записываются оба (легальные два платежа подряд).
7. **Ключ принадлежит автору.** Другой администратор с тем же ключом создаёт свою строку, чужую строку не получает.
8. **Права.** Вызов без входа и вошедшим не администратором (родитель, тренер) отклоняется RLS; `anon` функцию не выполняет;
   у `authenticated` EXECUTE есть. Проверка на базе с привилегиями по умолчанию Supabase (`alter default privileges ... grant ... to anon, authenticated, service_role`).
9. **История.** `request_id` после записи не меняется (триггер 0179 отклоняет UPDATE); DELETE и TRUNCATE по-прежнему запрещены. Существующие строки получают `request_id = null`, ничего не удаляется и не объединяется.
10. **Ключ обязателен у функции**: `req is null` отклоняется (`request id required`), чтобы вызов через функцию всегда был защищён.

## Клиент

11. Экраны «Оплаты за месяц» (`MonthPayments`), «Платежи игрока» (`AdminPayments`), «Должники» (`Debtors`) и «Касса» (`CashDesk`, платёж абонемента)
    пишут платёж через `payment_add` с ключом. Остальные запросы экранов не меняются.
12. Ключ создаётся на одну подтверждённую операцию и сохраняется, пока нет успеха: после ошибки или потери связи повтор с теми же данными
    уходит с тем же ключом. Другие данные получают новый ключ. После успеха ключ сбрасывается, следующий платёж получает новый.
    Ключ хранится только в памяти страницы до 30 минут (браузерное хранилище разрешено лишь в местах из `nav/guard.test.ts`);
    после перезагрузки страницы ключ теряется, это ограничение описано в PR.
13. Если сервер вернул `duplicate = true`, пользователь видит «Этот платёж уже был записан ранее, второй не создан», а не ошибку, и список обновляется.
14. Ошибка `request id reused` показывается понятным текстом (операция с такими данными уже записана с другими параметрами, проверьте список платежей), а не сырым кодом.
15. Остальное поведение экранов (проверки сумм, даты, способа, подтверждение, исправление с минусом, закрытие без оплаты) не меняется.

## Вне объёма

Отмена платежа (`cancels`, уже защищена `unique`), платежи сборов, матчей, событий и экипировки (свои функции и ключи), перенос исторических платежей на ключи, backfill, уведомления.
