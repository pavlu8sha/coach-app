# Условия приёмки: #471 PR-0, контрольные значения экипировки до миграций (12.11.2026)

Задача: Issue #471 (самостоятельный заказ экипировки). План: `/mnt/project-files/equipment-471/tech-plan-471-v5-final-2026-11-11.md`, разделы 8, 2.10, 12, 12.1.
Цель PR-0: до первой миграции #471 снять контрольные значения по заказам, оплатам, выдаче, отчётам и правам, чтобы после каждой миграции подтвердить, что исторические данные не изменились незаметно. Схема базы и данные не меняются.

## Состав
- `db/ops/readonly-eq-baseline-471.sql` — один запрос `select`, результат «раздел / показатель / значение».
- `db/tests/eq471_baseline_test.sql` — pgTAP на синтетических данных.
- `tests/eq471-pr0.test.mjs` — статические проверки запроса и защиты тестов базы.
- `scripts/lib/local-db-guard.sh` + вызов в `scripts/run-db-tests.sh` — защита от запуска тестов на удалённом сервере.

## Условия

**Б1. Заказы.** Число заказов, суммы `total`, `paid`, сумма строк (`unit_price × quantity`), заказы без игрока, без строк, без даты, в рассрочку, `paid > total`, распределение по статусам и локациям, число строк; отпечатки md5 заказов и строк для сравнения «до/после».

**Б2. Журнал оплат.** Строки и суммы `service_payments` по видам, экипировка по месяцам, строки с минусом, отпечаток журнала экипировки; сколько заказов имеют `paid` = сумме журнала, `paid` больше (кандидаты на `opening_balance`, с суммой разницы) и `paid` меньше (аномалия, каждая показана отдельной строкой; автоматически не исправляется, разбирает владелец).

**Б3. Итог против суммы строк, классы по плану 2.10.** По каждому заказу `delta = total − сумма строк` и класс: `exact` (0), `manual_up` (> 0), `manual_down` (< 0, у игрока нет полного комплекта), `legacy_confirmed` (< 0, полный комплект, заказ замыкающий, без рассрочки, `equip.discNeedAll` выполнено и `delta` равна минус расчётной скидке в пределах 0,01 ₾), `legacy_review` (остальные < 0 при полном комплекте). Итоги по классам и строка с объяснением по каждому заказу с `delta ≠ 0` (имя игрока, суммы, полнота комплекта, расчётная скидка, замыкающий ли, рассрочка, `discNeedAll`). Правила комплекта читаются из `club_settings` (`equip.discNeedOwn`, `equip.discNeedAll`, `equip.fullPrice`, `equip.discPct`, `equip.discRound`), при отсутствии ключа берутся значения по умолчанию из `web/src/lib/clubSettings.ts`; некорректные процент или округление показываются как «ОШИБКА». Порядок заказов: дата заказа (пустая раньше всех), затем id заказа и id строки.

**Б4. Выдача.** Число строк выдачи, строки заказов с количеством > 1 и отметкой выдачи (каждая отдельно, для решения T7), заказы со статусом «Выдан», где выдано не всё, и наоборот, число записей истории статусов.

**Б5. Отчёты.** Функции `cash_report`, `cash_day_service`, `parent_dues` требуют входа пользователя приложения, поэтому их суммы по экипировке повторены прямым запросом к журналу: с 01.10.2026 по месяцу, способу и локации; долг по экипировке (`total − paid > 0`).

**Б6. Права и защита.** Права `anon`, `authenticated`, `service_role` на таблицы экипировки и `service_payments`, политики, пользовательские триггеры и их состояние, локальные админы по локациям (без имён), правило удаления по внешним ключам (`cascade` и т. п.).

**Б7. Только чтение.** Файл содержит ровно один запрос (`with … select`), без операций записи, DDL, управления транзакциями и вызова функций приложения (только встроенные функции PostgreSQL). Проверяется статически (`tests/eq471-pr0.test.mjs`) и выполнением всего файла внутри `begin read only` в pgTAP-прогоне.

**Б8. Очередь уведомлений.** Число строк `notifications` по виду и состоянию (после миграций #471 их не должно стать больше из-за самих миграций).

**Б9. Защита тестов базы.** `scripts/run-db-tests.sh` до первой команды `psql` отказывается работать (код 2), если `PGHOST`/`PGHOSTADDR` не локальные, задан `PGSERVICE`, `PGDATABASE` содержит строку подключения или в `PSQL` указан нелокальный хост (`-h`, `--host`, `host=`, URL). Разрешены unix-сокет, `localhost`, `127.0.0.1`, `::1` и хост не задан (так работают CI и локальный прогон).

## Как выполняет владелец
1. Supabase → SQL Editor → вставить весь `db/ops/readonly-eq-baseline-471.sql` → Run. Запрос только читает.
2. Export → CSV, сохранить как «baseline-471-до-ГГГГ-ММ-ДД.csv». Строки раздела «3 классы» и аномалии раздела «2 журнал» показать разработчику до миграции PR-5.
3. После каждой миграции #471 повторить и сравнить по колонкам «раздел» и «показатель».

Ожидаемые изменения по этапам (остальное должно совпасть):
- PR-1: появятся новые колонки и статусы, но разделы 1–5 и 7 совпадают полностью (отпечатки md5 считаются по прежним колонкам). В разделе 6 добавятся объекты PR-1.
- PR-2: в журнале появятся строки `opening_balance` на сумму из Б2 «paid > суммы журнала»; строки «касса» не меняются (`opening_balance` в кассу не входит, это проверит PR-2).

## Среда
Отдельной тестовой копии production нет, `/dev` изолированной средой не считается (`docs/DECISIONS.md`). Тесты PR-0 идут на локальной одноразовой PostgreSQL 16 с pgTAP (`scripts/run-db-tests.sh`) и в CI, на синтетических данных. На production запрос запускает только владелец.

## Вне PR-0
Изменение схемы и данных, исправление аномалий, перенос `opening_balance`, классификация с записью в базу (это PR-2 и PR-5).
