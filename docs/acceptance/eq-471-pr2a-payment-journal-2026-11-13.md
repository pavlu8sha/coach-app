## Условия

**Ж1. Поля журнала.** В `service_payments`: `op` (`payment` / `reversal` / `refund` / `opening_balance`, обязательное), `request_id uuid`, `note text`. Старые строки: сумма > 0 → `payment`, сумма < 0 → `reversal` (в том числе исправления без `cancels`). Суммы, даты, способы, авторы и `cancels` старых строк не меняются; обновление метки `op` в миграции выполняется при временно отключённых триггерах 0179 в той же транзакции, после неё триггеры включены, в `audit_log` одна сводная запись.

**Ж2. Ограничения по видам.** `payment` > 0; `reversal` < 0; `refund` < 0, без `cancels`, только `kind = 'equipment'`; `opening_balance` > 0, только `equipment`. Новая запись: сумма > 0 → `payment`; сумма < 0 с `cancels` → `reversal`; сумма < 0 без `cancels` допустима только как `refund` из `eq_refund`, иначе `22023`. Остальные виды платежей (индивидуальные, доп., разовые посещения) работают как раньше.

**Ж3. Кэш `paid`.** `equipment_orders.paid` меняется только триггером на вставку в журнал (на сумму строки, строки `opening_balance` в кэш не добавляются, он уже их содержит). Прямое изменение `paid` отклоняется (`42501`) для всех ролей, кроме владельца, который отключает триггер осознанной командой. `eq_add_payment` больше не пишет `paid` сам.

**Ж4. `eq_add_payment(o, amt, d, mth, req)`.** Только положительная сумма (отрицательная: `use reversal or refund`), оплата больше итога и на отменённый заказ отклоняется; права как раньше (админ и локальный админ своей локации). `req` (ключ идемпотентности): повтор с теми же заказом и суммой того же автора возвращает прежний результат и строку не добавляет; тот же ключ с другими данными: `request id reused`; параллельные повторы дают одну строку.

**Ж5. `eq_reverse_payment(payment_id, note, req)`.** Только глобальный администратор. Сторнирует оплату `op = 'payment'` заказа экипировки: строка `reversal` на минус сумму, `cancels` на исходную, дата сегодня, способ исходной. Одну оплату нельзя сторнировать дважды; если `paid` стал бы меньше нуля, отказ. Работает и у отменённого заказа.

**Ж6. `eq_refund(o, amt, d, mth, note, req)`.** Только глобальный администратор, сумма > 0, причина (`note`) обязательна, не больше текущего `paid`; строка `refund` на минус сумму. Работает у отменённого заказа (возврат после отмены). `total` и статус не меняются.

**Ж7. `opening_balance` приложение создать не может (четыре слоя).** (1) У `anon`, `authenticated` и `service_role` нет `insert/update/delete/truncate` на `service_payments`. (2) Триггер на вставку отклоняет `opening_balance` (`42501`), если в транзакции не стоит `eq.backfill_gate = 'on'` или нарушены условия строки. (3) Функции записи не принимают `op` от клиента. (4) Тест-инвентарь по `pg_proc`: ни одна функция схемы `public`, кроме служебного триггера, не содержит `opening_balance` как вставляемое значение и не задаёт `eq.backfill_gate`.

**Ж8. Отчёты.** `cash_report` и `cash_day_service` не включают `opening_balance` (это не деньги периода); `reversal` и `refund` остаются отрицательными. Без строк `opening_balance` результаты отчётов не меняются.

**Ж9. Прямая запись закрыта.** У `authenticated` нет `insert/update/delete` на `equipment_orders`, `equipment_order_lines`, `equipment_issues`, `equipment_order_status_history`; политики `for all` заменены политиками чтения (админ читает всё, как раньше). Запись идёт только функциями `eq_*`.

**Ж10. Права функций.** Новые функции доступны `authenticated` (проверка роли внутри), закрыты для `anon` и `public`; служебные триггерные функции закрыты для всех.

**Ж11. Интерфейс.** В оплате заказа сумма только положительная; у каждой оплаты кнопка «Сторно», отдельная форма «Возврат» (сумма, причина); ошибки на русском.
