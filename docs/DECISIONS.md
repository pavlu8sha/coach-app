# Журнал ключевых решений

Этот файл фиксирует решения, влияющие на безопасность и процесс работы. Технические детали реализации остаются в соответствующих PR.

## 2026-10-21 — GitHub как единый реестр состояния

**Решение:** Issues используются для задач и дефектов; PR — для изменения кода; `master` — стабильная интеграционная ветка; deployment в Apps Script фиксируется отдельно.

**Причина:** ранее состояние работы было распределено между несколькими чатами и ветками, из-за чего трудно определить, что сделано, что влито и что опубликовано.

## 2026-10-21 — Запрет тестовых записей в production

**Решение:** не выполнять тесты, проверки или эксперименты, которые могут записывать в боевые таблицы.

**Причина:** отдельной изолированной тестовой среды пока нет; `/dev` production-проекта использует те же таблицы, что и `/exec`.

## 2026-10-21 — Обязательное ревью перед слиянием

**Решение:** успешный CI необходим, но недостаточен для слияния. Авторизация, платежи, посещаемость, источники данных и любые операции записи проверяются отдельно по риску.

**Причина:** автоматические тесты не гарантируют, что все production-сценарии покрыты.

## 2026-10-21 — Ветки не удаляются без проверки уникальной работы

**Решение:** перед удалением ветки проверить её уникальные коммиты и подтвердить, что нужная работа сохранена в другой ветке или явно отменена.

**Причина:** старые ветки могут содержать работу, которую ещё не перенесли в `master`.

## 2026-10-22 — Прямой push в master разрешён

**Решение:** ruleset `Protect master` снят; PR для слияния в master не обязателен. Прямой push разрешён. Коммиты пишутся с тестами и понятным сообщением, риски указываются в описании коммита. Публикация в Apps Script остаётся отдельным решением.

**Причина:** проект ведёт один разработчик и владелец. Обязательный PR добавлял шаг без пользы, а хук и рабочий процесс ожидали push в master.

**Последствие:** коммит `d132774` (лист оплат нового месяца: удаление ушедших игроков) ушёл в master напрямую; его проверка — отдельная задача.

## 2026-10-23 — Приложение для родителей: Supabase + Cloudflare Pages

**Решение:** родительское приложение — Vite/React в `web/`, хостинг Cloudflare Pages, данные и права в Supabase (RLS). Вход через Telegram: Edge Function `tg-auth` проверяет подпись `initData` и выдаёт одноразовый токен, сессию создаёт сам Supabase Auth (свои JWT не выпускаем).

**Причина:** проект использует асимметричные ключи подписи JWT; RLS проверяет `users.id` = id пользователя Auth.

## 2026-10-23 — Связь родитель–ребёнок только через администратора

**Решение:** родитель ищет ребёнка по имени (от 3 букв, до 5 результатов, имя и группа) и подаёт запрос с согласием; связь создаёт только администратор. Весь список игроков родителям не показывается. Согласие хранится версией и временем; текст — черновик до юридической проверки.

**Причина:** любой пользователь Telegram может войти, поэтому без подтверждения нельзя раскрывать данные детей.

## 2026-10-23 — Тренер пишет только через функции базы

**Решение:** посещаемость, матчи, баллы и занятия тренер вносит только через функции (`open_session`, `mark_attendance`, `save_match`, `award_bonus`, `revoke_bonus`; миграции 0018–0020). Прямая запись тренера в `sessions`, `attendance`, `point_events` закрыта, прямую запись в таблицы сохраняет только администратор. Ручные баллы: от 1 до 5 за раз, комментарий обязателен, отрицательных нет (границу правит владелец).

**Причина:** при прямой записи через API можно отметить посещаемость без баллов, создать лишние занятия или начислить любое число баллов.

**Последствие:** автобаллы за посещаемость и матчи пересчитываются этими функциями при исправлении отметок. Это единственное исключение из «журнал баллов только добавляется»: функция удаляет и заново создаёт только автоначисления того занятия или матча, который правят; ручной балл отменяется отдельной функцией с записью в аудит.

## 2026-10-23 — Контакты родителей тренеру и версии согласия

**Решение:** тренер видит Telegram (имя и ID) родителей игроков своей группы. Показ привязан к версии согласия: `consent_versions.coach_contacts` (миграция 0021), текст версии `draft-2026-10-v2` сообщает родителю об этом. Родители, согласившиеся на прежний текст, в контактах не показываются.

**Причина:** прежний текст говорил, что Telegram родителя нужен «только для входа и связи с ребёнком».

**Последствие:** старые (тестовые) связи в контакты не попадают, пока родитель не согласится заново. Юридическая проверка текста по-прежнему не пройдена (`docs/CONSENT.md`).

## 2026-10-23 — Цены и долг по абонементу

**Решение:** цены по умолчанию: абонемент 165 ₾, группа `weekends` 130 ₾, индивидуальное 50 ₾ (с сентября 2026). Долг за месяц = цена группы минус внесённое за месяц; скидка плюс платёж = оплачено. Долг считается с сентября 2026; прошлые месяцы — только если за месяц есть строка абонемента. Родителю долг показывается только после включения администратором настройки `parent_debt_enabled` (миграция 0023, `docs/DEBT_RULES.md`).

**Причина:** скидки из старого приложения ещё не перенесены, без выключателя у детей со скидкой появился бы неверный долг.

**Последствие:** известное ограничение по доп. программам (платежи суммируются по игроку); перед включением сверить экран «Должники» со старым приложением.

## 2026-10-23 — Чтение матчей и расписания только своей группой

**Решение:** матчи видят администратор, тренер и родитель игрока группы-команды, а также родитель или тренер участника матча; расписание — администратор, тренер группы, родитель игрока группы (миграция 0024). Справочники без личных данных (правила рейтинга, цены, клуб, сезоны) читаются всеми вошедшими.

**Причина:** прежняя политика позволяла любому вошедшему читать все матчи и всё расписание клуба.

**Последствие:** матч связан с группой по тексту (`matches.team` = название группы); несовпадение названий скрывает матчи от родителей и тренеров.

## 2026-10-23 — Вход из браузера и PWA (в работе: PR «Вход из обычного браузера»)

**Решение:** вход вне Telegram идёт через виджет Telegram Login и Edge Function `tg-login` (тот же пользователь `tg<id>@telegram.invalid`, те же лимиты, что у `tg-auth`; рабочая `tg-auth` не менялась). PWA: манифест и сервис-воркер без кэширования.

**Причина:** родителям без Telegram на телефоне нужен вход, а свои пароли и email-вход создали бы вторую личность для того же человека.

**Последствие:** включается владельцем (`/setdomain` в BotFather, деплой функции, `VITE_TG_BOT_USERNAME`). Кэша нет, устаревших данных детей не бывает.

## 2026-10-23 — Управление данными родителем (в работе: PR «Согласие: отзыв, выгрузка, запрос на удаление»)

**Решение:** родитель сам отзывает согласие по ребёнку, скачивает свои данные и подаёт запрос на удаление; администратор выполняет его функцией `erase_parent` (связи, запросы, имя). Данные игроков, строка `users` с Telegram ID, учётная запись Authentication и аудит автоматически не удаляются (`docs/DATA_REQUESTS.md`, миграция 0025).

**Причина:** без юридической проверки сроков хранения безопасная механика — действия самого родителя и ручное решение администратора.

**Последствие:** остаются открытые вопросы к владельцу (срок обработки запроса, судьба данных ребёнка).

## 2026-10-23 — Уведомления: очередь в базе и отправитель по расписанию (в работе: PR «Уведомления в Telegram»)

**Решение:** события пишутся триггерами в очередь `notifications`, функция `tg-notify` по расписанию (`pg_cron`/`pg_net`) отправляет их ботом; родитель может отключить (миграция 0026, `docs/NOTIFICATIONS.md`). Существующие функции для этого не менялись.

**Причина:** триггеры не меняют проверенные функции и не теряют события; очередь переживает недоступность Telegram.

**Последствие:** бот пишет только тем, кто его запускал; у администратора и тренера нет переключателя (отключение в базе).

## 2026-10-23 — Баллы за матч: победа 2, лучший 3, поражение 1; администратор правит всё

**Решение:** баллы за матч начисляются один раз за результат: победа — 2 каждому, кто играл, лучшему игроку матча — 3 (вместо 2); поражение и ничья — 1 каждому, кто играл; гол +1 отдельно. Баллы за результат начисляются, когда внесён счёт. Администратор может править любой матч, добавлять в состав любого игрока клуба, удалять матч и пересчитывать баллы (миграция 0027). Ничья приравнена к поражению (1 балл): решение по умолчанию, владелец может изменить.

**Причина:** прежняя схема давала и за участие, и за победу; в импортированных матчах не все сыгравшие и забившие, их нужно дополнять.

**Последствие:** прежние начисления за матчи остаются по старым правилам, пока администратор не запустит пересчёт; пересчёт перезаписывает автобаллы матчей с составом (ручные не трогает).


## 2026-10-23 — Роль «Ребёнок»: доступ по одноразовому коду от родителя

**Решение:** аккаунт с ролью «Ребёнок» привязывается к игроку кодом (8 символов, 3 дня, одноразовый), который создаёт родитель с действующим согласием (миграция 0028). Ребёнок видит только своего игрока, его баллы, матчи и название группы; оплаты и данные родителя закрыты. Отзыв согласия родителем отключает доступ ребёнка, родитель может отвязать аккаунт.

**Причина:** личные данные привязаны к родителю; код сохраняет контроль родителя над данными ребёнка без участия администратора.

## 2026-10-24 — Код ребёнка: криптостойкая генерация и лимит попыток

**Решение:** код для ребёнка строится из `gen_random_uuid()` (CSPRNG) без смещения алфавита; ввод кода ограничен 8 попытками за 10 минут с аккаунта и 200 на весь клуб (`rate_limits`). Неверный или устаревший код возвращает пусто, а не ошибку (миграция 0029).

**Причина:** `random()` не криптостоен, а ввод кода не был ограничен; ошибка при неверном коде откатывала транзакцию вместе со счётчиком попыток, поэтому лимит не мог работать.

**Последствие:** клиент `ChildHome` обрабатывает пустой ответ как «код не подошёл»; новая ошибка `too many attempts` показывается как «подождите 10 минут».
## 2026-10-24. Новые родители приходят через бота («Хочу в KickStart»)
- **Решение Павла:** воронка «Новые игроки» из старого приложения не переносится. Новый родитель идёт в бота, заполняет данные и нажимает «Хочу в KickStart».
- **Реализация (0039):** диалог бота собирает согласие, имя и год рождения ребёнка, телефон родителя; заявка попадает в `trials`, администратору приходит сообщение, в приложении «Ещё → Заявки» меняется статус (новая, связались, пробное, в клубе, отказ) и пишется заметка.
- **Защита и риск:** не больше 3 заявок в сутки с одного Telegram; черновики видит только служебная роль. Диалог выключен, пока владелец не задаст `LEADS_ENABLED=1`. Текст согласия в диалоге требует юридической проверки перед включением.

## 2026-10-24. Баллы считаются с запуска приложения для родителей
- **Решение Павла:** родители получают приложение «с нуля»: уже набранные баллы им не показываются.
- **Реализация (0040):** дата старта в `club_settings` (`points_start`), задаётся в «Ещё → Старт подсчёта баллов». Баллы раньше этой даты не видит никто через приложение (политика чтения `point_events` и рейтинг группы); записи не удаляются, историю можно вернуть, сняв дату.
- **Что делать владельцу:** в день запуска для родителей задать дату старта. Пока дата не задана, видна вся история. «Матчей сыграно» и голы ребёнка считаются по самим матчам и датой старта не ограничены.

## 2026-10-24. Тренеры видят и ведут все группы
- **Решение Павла:** как в старом приложении, любой тренер отмечает посещаемость любой группы, видит матчи всех команд с составами, участием и голами, расписание и статистику по всем группам (и по матчам, и по тренировкам). От тренеров скрыты только взносы и платежи. Дополнительно тренерам открыт просмотр посещаемости тренеров (кто проводил занятия), без правки и без часов; в обоих приложениях.
- **Реализация (0042):** `is_any_coach()`; расширено чтение игроков, групп, занятий, посещаемости, матчей, составов и расписания; `open_session`, `mark_attendance`, `save_match` разрешены любому тренеру; `trainer_attendance(from, to)` отдаёт журнал тренировок без часов. Остаётся ограниченным по своим группам: ручные баллы (`award_bonus`), контакты родителей (`group_parents`), всё про деньги. В старом приложении: страница «Посещаемость тренеров» для тренера (`tatt`), методы `appTrainerMonths`, `appTrainerAttendance` (код тренера подходит, часов нет).
- **Риск и что проверить:** тексты согласия родителя (`lib/consent.ts`) пишут, что данные ребёнка видят «тренеры его группы»; теперь их видят тренеры всех групп, формулировку и версию согласия нужно обновить вместе с юридической проверкой.

## 2026-10-26. Старое приложение: тренер видит «Учёт тренеров» целиком, но только на просмотр
- **Решение Павла:** тренеру на странице «Посещаемость тренеров» показываются те же четыре вкладки, что и администратору (Тренировки с часами, Игры со штатом матчей, Статистика, Расписание), только без кнопок изменения. Это отменяет прежнее «без часов» от 24.10.
- **Реализация:** `appAccountMonths`, `appTrainingsList`, `appGamesData`, `appDailySchedule` проверяют `checkPin_` (код тренера подходит); все изменяющие методы остались на `checkAdmin_` (это проверяет тест). Методы `appTrainerMonths` и `appTrainerAttendance` удалены.
- **Не затронуто:** родительское приложение (Supabase) и экран тренера в нём.
