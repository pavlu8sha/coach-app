5. Проверить, не редактирует ли другой исполнитель те же файлы. Один активный исполнитель на одну область.

## Очередность работы

### До отчёта OpenCode

- Не редактировать `stage-abc`, не удалять и не перезаписывать его коммиты.
- Не начинать работу с авторизацией, `DRY_RUN` или `clubSource_`, если она пересекается с PR #2.
- Допустимо изучать репозиторий и подготовить план, но не создавать конкурирующий код в той же области.

### После отчёта OpenCode

1. Координатор сверяет отчёт с фактическим diff, тестами и CI.
2. Павел/координатор указывает Claude конкретный независимый следующий Issue и список разрешённых файлов.
3. Claude реализует задачу в отдельной ветке от актуального `master`, добавляет/обновляет локальные тесты с моками и открывает PR.
4. Если задача зависит от PR #2 или #3, дождаться решения по зависимости, не строить код на непроверенной ветке.

### Производительность

- Не переносить `perf-phase1` целиком и не редактировать эту ветку параллельно с аудитом.
- После аудита координатор выдаст конкретный список оптимизаций, которые можно переносить в свежую ветку.
- Для `PaymentsV3.js` обязательно подтвердить эквивалентность финансового результата; для мемоизации даты тестировать и результат, и количество вызовов форматирования. Для `Individual.js` проверять состав и порядок групп.

## Безопасность и запреты

- Отдельного тестового окружения нет. `/dev` production-проекта использует боевые таблицы.
- Разрешены локальные тесты с моками, статический анализ, CI и read-only проверки.
- Без отдельного явного разрешения запрещены: `clasp push`, deployment, merge PR, удаление веток, тестовые записи в production-таблицы и любые проверки с неизвестными побочными эффектами.
- Не считать наличие `DRY_RUN` доказательством, что все write-paths безопасны; проверять каждый endpoint и каждую запись.
- Не утверждать, что production соответствует `master`, если опубликованный SHA/версия не подтверждены отдельно.
