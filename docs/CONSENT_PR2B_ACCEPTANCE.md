# #238, PR 2b: условия приёмки (миграция 0173)

Основание: спецификация #238, решения владельца от 09.11.2026, техплан `consent-238/pr2b-technical-plan-2026-11-11.md` (решения раздела 9 владелец 11.11 доверил исполнителю; приняты варианты, рекомендованные в плане). Тесты пишутся от этих условий до миграции и падают на текущем коде.

Граница PR 2b: проверки доступа и выбор получателей переходят на один предикат с режимом. Режим не включается, данные не переносятся, отправка уведомлений (проверка при отправке) — PR 2c, шлюз в приложении — PR 3.

## Режим
- **Р1.** Режим клуба задаётся ключом `consent.mode` в `club_settings` (`scope ''`): `off`, `test`, `all`. Нет ключа или другое значение — `off`. Регистр и пробелы не важны.
- **Р2.** Тестовые родители — таблица `consent_test_parents` (явный список). В `test` новая модель действует только для родителей из списка, для остальных — прежние правила.
- **Р3.** Ключ `consent.mode` и список меняет только владелец базы (SQL Editor): запись из приложения (любой запрос с JWT, в том числе администратора и `service_role`) отклоняется. У `consent_test_parents` нет прав у `anon`, `authenticated`, `service_role`.

## Предикат
- **Д1.** `parent_access_ok(parent, player)`: на новой модели — действующее `data_processing` текущей версии у этого родителя по этому ребёнку (`has_consent`); на прежних правилах — связь с `consent_revoked_at is null` и нет нового отзыва `data_processing` от родителя или администратора. Системный отзыв (удаление связи) при прежних правилах доступ не закрывает.
- **Д2.** Новый отзыв `data_processing` закрывает доступ в любом режиме, включая `off`; переключение режима в `off` его не отменяет. После повторного принятия доступ возвращается без новой привязки.
- **Д3.** `consent_revoked_at` сам по себе не считается отзывом новой модели; на новой модели старый отзыв не мешает доступу после принятия.
- **Д4.** `media_publication` не влияет на доступ ни в каком режиме.
- **Д5.** Внутренние функции (`parent_access_ok`, `consent_new_model_for`, триггер защиты режима) недоступны `anon`, `authenticated`, `service_role`, PUBLIC.

## Матрица двух родителей (Р1/Р2 одного ребёнка, режим `all`; `test` для родителей из списка)
- **М1.** Родитель видит данные ребёнка (`is_guardian_of`, политики таблиц, функции родителя) только при личном согласии.
- **М2.** Детский аккаунт (`is_self_player`, `is_guardian_in_group`) имеет доступ, если согласие есть хотя бы у одного родителя; без согласий нет. Вход по коду ребёнка (`redeem_child_code`) — так же.
- **М3.** Контакты тренеру (`group_parents`): строка родителя показывается, только если у него лично есть согласие и версия его `data_processing` разрешает контакты тренерам (`consent_doc_versions.coach_contacts`). При прежних правилах — как сегодня (`consent_versions.coach_contacts`).
- **М4.** Строки матрицы: у обоих; только у Р1; только у Р2; ни у кого; только `media_publication`; Р1 отозвал; Р1 принял устаревшую версию.

## Функции
- **Ф1.** Все 38 функций, где было условие `consent_revoked_at is null`, используют `parent_access_ok`; исключения перечислены в Ф2–Ф6. В `off` поведение существующих тестов не меняется.
- **Ф2.** `revoke_consent(p)` (кнопка в «Мои дети»): на новой модели не пишет `consent_revoked_at`; в любом режиме отзывает `data_processing` новой модели, если оно принято.
- **Ф3.** `decide_link`: подтверждение существующей связи родителя на новой модели не меняет её прежние поля; на прежних правилах — как сегодня.
- **Ф4.** `search_players_for_link`: родителю на новой модели не показываются дети, с которыми у него уже есть связь (в любом состоянии согласия).
- **Ф5.** `first_wave_list` показывает всех детей администратору и добавляет признак `consent_missing` (ни у одного родителя нет доступа); родитель, тренер и аноним получают отказ. `first_wave_add` и `first_wave_friday` не включают родителей без доступа.
- **Ф6.** `export_my_data`: данные (посещаемость, баллы, оплаты, матчи) выгружаются только по детям с доступом; блок `children` со старыми полями остаётся как история.
- **Ф7.** `consent_doc_versions.coach_contacts` (по умолчанию `false`) нельзя менять после первого подтверждения версии.

## Страж и порядок
- **С1.** Тест-страж: `consent_revoked_at` нет ни в одной функции, политике, представлении, индексе, ограничении и значении по умолчанию, кроме белого списка (`parent_access_ok`, `decide_link`, `revoke_consent`, `export_my_data`, `parental_consent_status`).
- **С2.** Ни одна миграция с номером больше 0173 не содержит `consent_revoked_at` (статический тест).
- **С3.** Клиент: `.is('consent_revoked_at'` встречается только в 8 известных местах (заменит PR 3).
- **С4.** `preflight.sql` содержит строку 0173; `readonly-consent-prereq-0173.sql` подтверждает 0159, 0162 и миграции сборов, чьи функции пересоздаёт 0173; повторный запуск 0173 проходит.
- **С5.** Полный `scripts/run-db-tests.sh` проходит с полным выводом.
