# Подтверждение участия в матчах (RSVP), Issue #274, этап 1

Миграция `0134_match_rsvp_base.sql`. PR 1 содержит только базу данных и серверные проверки. Интерфейс — PR 2a, уведомления, кнопки в боте и cron — PR 2b (раздел ниже).

## Состояния матча (`matches.lifecycle_status`)

```
legacy            старые матчи; приглашений нет, остаётся legacy навсегда
draft ──publish──> published ──cancel──> cancelled (необратимо)
  └─ delete_draft (окончательно)     └─ reschedule (остаётся published, ответы сбрасываются)
```

Переходы защищены триггером: другие переходы и удаление опубликованного/отменённого матча невозможны даже прямой записью.

## Таблицы

| Таблица | Назначение |
|---|---|
| `matches` (+ колонки) | `lifecycle_status`, `starts_at` (timestamptz), `venue`, `address`, `notes`, `rsvp_deadline_at` (вычисляемый: начало − 24 ч по Asia/Tbilisi), метки публикации/отмены/переносов |
| `match_invitations` | одно приглашение на пару (матч, игрок): `status` invited/removed, `response` yes/no/null («Не ответил»), `responded_by`, `answer_until` |
| `match_activity` | журнал: created, published, details_changed, rescheduled, cancelled, players_invited, players_removed, coach_response, manual_reminder |
| `match_reminder_log` | основа единого лимита напоминаний 24 ч (ручные и автоматические вместе) |

Фактическое участие (`match_players`), взносы (`match_fees`) и баллы не затрагиваются.

## Окно ответа родителя

`answer_until` = дедлайн (начало − 24 ч), а если дедлайн уже прошёл к моменту публикации/добавления игрока/пересчёта — начало матча.
Родитель отвечает только пока матч опубликован, `now < starts_at` и `now <= answer_until`. Тренер может ставить ответ до начала матча (после дедлайна — с отметкой в журнале).

## Функции (все `security definer`, доступ проверяется внутри)

Тренер клуба / администратор: `match_rsvp_create_draft`, `match_rsvp_update`, `match_rsvp_seed`, `match_rsvp_invite`, `match_rsvp_remove`, `match_rsvp_publish`, `match_rsvp_delete_draft`, `match_rsvp_cancel`, `match_rsvp_reschedule`, `match_rsvp_coach_set`, `match_rsvp_remind_unanswered`, `match_rsvp_summary`, `match_rsvp_roster`.
Родитель: `match_rsvp_answer`, `match_rsvp_answer_many`, `match_rsvp_my_matches`.
Служебные (клиентам закрыты): `rsvp_assert_staff`, `rsvp_lock_match`, `rsvp_log`, `rsvp_claim_reminder` (только `service_role`; с 0137 сам ставит сообщение в очередь).

## Конкурентность

Порядок блокировок везде один: сначала строка матча, потом приглашения по `player_id`. Staff-операции берут матч `FOR UPDATE`, ответы родителей — `FOR SHARE` (ответы не мешают друг другу, но ждут перенос/отмену). Проверки времени идут по `clock_timestamp()`, а не по началу транзакции. Проверка: `db/tests/concurrency_match_rsvp.sh` (параллельные сессии).

## Перенос и фактические отметки (миграция 0136)

Если у переносимого матча есть отметки или счёт, `match_rsvp_reschedule` сначала сохраняет снимок в `match_mark_snapshots` (строки `match_players` целиком, счёт, технический результат, старая дата), затем обнуляет `played`, `goals`, `best` и счёт. Строки не удаляются; баллы за матч пересчитывают существующие триггеры 0122 (прежние начисления остаются в журнале закрытыми строками). `match_rsvp_restore_marks(snapshot)` возвращает отметки и счёт, пока на матче нет новых.

## Уведомления, кнопки в боте и автонапоминания (миграция 0137, PR 2b)

Сообщения идут через существующую очередь `notifications` (0026) и функцию `tg-notify`. Новое поле `notifications.buttons` хранит кнопки ответа; `claim_notifications` теперь отдаёт его отправителю.

| Событие | Кому | Кнопки |
|---|---|---|
| Публикация матча, перенос, игрока пригласили в опубликованный матч | родителям приглашённых детей (одно сообщение на родителя, все его дети) | «Будет» / «Не будет» на каждого ребёнка |
| Напоминание (ручное тренера и автоматическое) | родителям не ответивших детей | только за не ответивших |
| Отмена матча | родителям приглашённых детей, с причиной | нет |

Нажатие кнопки обрабатывает `tg-bot` (данные кнопки `r:<id приглашения>:y|n`): функция `rsvp_answer_by_telegram` (только `service_role`) находит родителя по Telegram-аккаунту и вызывает тот же `match_rsvp_answer`, что и приложение. Связь с согласием, срок ответа, статус матча и один общий ответ на ребёнка проверяются там же. Бот отвечает всплывающим «Записано: …» и отмечает выбранную кнопку ✅; ответ можно изменить, пока приём открыт. Кнопки из старого сообщения после переноса или отмены ответ не запишут: отказ показывается нажавшему.

Автонапоминания: `rsvp_auto_reminders()` (только `service_role`, расписание в `db/ops/match_rsvp_cron.sql`, каждые 10 минут). Вид `auto_48h` — начиная с 48 часов до матча, `auto_24h` — начиная с 25 часов до матча (миграция 0140: час запаса до закрытия приёма ответов вместо прежних 15 минут). Не напоминаем: если приглашение или перенос были меньше 3 часов назад (0140; раньше 12), приём ответов закрыт, матч начался, ребёнок уже ответил. Лимит «одно напоминание родителю за 24 часа по всем матчам» (ручные и автоматические вместе) и уникальность по матчу, получателю, виду и версии расписания проверяет `rsvp_claim_reminder`; ближайший матч идёт первым.

Родитель, отключивший уведомления (`users.notifications_enabled`), сообщений не получает. Приглашение в уведомлении не заменяет приложение: «Открыть приложение» остаётся под кнопками.

Что делает владелец: применить 0137 после `db/ops/preflight.sql`; задеплоить `tg-notify` и `tg-bot` (`--no-verify-jwt`); для кнопок у `tg-bot` нужен `SUPABASE_SERVICE_ROLE_KEY` (уже задан для заявок); выполнить `db/ops/match_rsvp_cron.sql`. Откат: `cron.unschedule('match-rsvp-auto-reminders')`, триггеры `matches_rsvp_notify`, `match_invitations_notify`, затем функции 0137; прежний `rsvp_claim_reminder` — из 0134.

## Уведомления об изменении и исключении (миграция 0139, PR 4)

- Изменены данные опубликованного матча без переноса (время того же дня, место, адрес, заметка, соперник): каждому родителю приглашённых детей приходит сообщение «Изменились данные матча» со строками «было → стало», «Прежние ответы сохранены» и кнопками «Будет» / «Не будет» за не ответивших детей. Перенос по-прежнему даёт только сообщение о переносе, без дублирования.
- Игрок исключён из опубликованного матча до его начала: его родителям приходит сообщение «Игрок исключён из состава», без кнопок. Возврат исключённого игрока даёт новое приглашение.
- Одна операция — одно сообщение на родителя: события приглашения и исключения копятся в `rsvp_notice_stage` (таблица закрыта для приложения), а отложенный триггер `rsvp_notice_flush` в конце транзакции объединяет их по матчу и виду. Дети одной семьи в одной операции попадают в одно сообщение. Черновик сообщений не создаёт.
- Старый список «Матчи» тренера показывает матч с подтверждением только после начала (для отметок игроков и счёта); дату и соперника в старой форме менять нельзя.
- Экран тренера: «Отменить матч» и «Перенести матч» доступны и после начала матча (новая дата должна быть в будущем).

## Миграция 0140 и доработки экрана тренера

- `0140_match_rsvp_reminder_window`: окно автонапоминания «за 24 часа» стало шире (с 25 часов до матча, час запаса до закрытия приёма), пауза после публикации и переноса сокращена с 12 до 3 часов. Остальные правила (лимит один раз в 24 часа, уникальность, срок ответа) прежние.
- Экран «Матчи с подтверждением»: фильтр приглашённых (все, будут, не будут, не ответили) со счётчиками; блок «История» (журнал `match_activity`, подгружается по кнопке); кнопка «Вернуть отметки до переноса» (`match_rsvp_restore_marks`) показывается, пока есть неиспользованный снимок (`match_mark_snapshots`).

## Автозаполнение состава при создании (ТЗ §1)

Экран «Новый матч» сразу после создания черновика добавляет состав: у матча чемпионата с выбранным событием — список события (`match_rsvp_seed` без группы), иначе игроки групп команды. Для товарищеского матча, если у команды несколько групп, тренер выбирает «Основную группу» (по умолчанию все группы команды). Если добавить не удалось, черновик всё равно создан, состав заполняется кнопкой на экране матча. Миграций нет.
