# Запись на индивидуальные, вратарские и дополнительные тренировки (Issue #274, сценарии A и B)

Правила: комментарии владельца в Issue #274 от 06.11.2026. Сверка с кодом и декомпозиция: `rsvp-274/trainings-spec-reconciliation-2026-11-06.md` в файлах проекта.

## PR 2: надёжность записи (миграция 0141)

- `ind_book` блокирует строку занятия (`for update`): одновременные записи не превышают вместимость. Проверка: `db/tests/concurrency_booking.sh` (30 занятий на одно место, два родителя параллельно; без блокировки переполнялось 20 из 30).
- `booking_signup` (запись родителем): ребёнок должен быть в статусе «Занимается» (ошибка `player not active`). Запись на дополнительную закрывается в момент `starts_time`, если время задано; без времени запись открыта до конца дня (прежнее поведение).
- `ind_slot_member_set`: постоянным нельзя назначить игрока не в статусе «Занимается».
- `ind_regulars_overflow(mth)`: слоты, где постоянных больше мест; экран «Постоянные» показывает предупреждение (спецификация A7), ничего не блокируется.

## PR 3: модель дополнительных тренировок (миграция 0142)

- Уникальность «одна дополнительная в день» снята: в день может быть несколько тренировок.
- Вместимость на тренировку (`extra_sessions.capacity`, 1–100); пусто — значение клуба `extra.cap`. `extra_set_capacity(s, cap)` возвращает, на сколько записано больше лимита; записи не удаляются (решает администратор).
- Дату и место можно менять и при наличии оплат (записи и оплаты сохраняются, перезапись не нужна); сумму при оплатах менять нельзя.
- Отмена: `extra_cancel_session(s, p_reason)` (только администратор). Записи и оплаты остаются; новые записи, отметки и посещение закрыты; баллы не начисляются (`points_reconcile_extra`); отменённая не попадает в доску записи, долги и календарь родителя. Что делать с оплатой отменённой тренировки — отдельным PR (решение администратора: оставить / перенести / вернуть).
- Журнал изменений: `extra_activity` (создание, правки, время, вместимость, отмена), виден администратору.
- Известно: `db/ops/import_extra.sql` использует `on conflict (club_id, starts_on)` и после снятия уникальности не работает (одноразовый исторический скрипт).

## PR 1: настройки уведомлений по направлениям (миграция 0144)

- Таблица `notification_prefs` (пользователь, направление `ind_sat` / `ind_sun` / `goalkeeper` / `extra`, включено, откуда: `self` или `admin`). Доступ только через функции: `notify_prefs_get()` и `notify_pref_set(d, on_)` у самого родителя.
- Значения по умолчанию: «дополнительные» включены (решение владельца); индивидуальные суббота и воскресенье и вратарские выключены и включаются явно (родителям первой волны администратор, PR 8; остальным после однократного информационного сообщения).
- Общий выключатель `users.notifications_enabled` приоритетнее: при выключенном бот не пишет ничего. Для информационных рассылок по направлениям служебная функция `enqueue_direction_notification(u, d, kind, text)`: сначала проверка направления, затем `enqueue_notification` (проверка общего выключателя). Операционные сообщения (оплата, запросы, подтверждения) направлениям не подчиняются.
- В профиле родителя под общим выключателем четыре переключателя; при выключенном общем они скрыты.
- Сами рассылки (запись открыта, автозапись, места, очередь) подключаются в PR 4–6 и пока ничего не отправляют.
