### 4.2 P0-кандидаты — потенциальный риск неверных денег после миграции

#### A1. `equip.discNeedOwn` и `equip.discNeedAll` означают противоположное

Старое приложение:

- `equip.discNeedAll` — позиции, которые должны быть **в новом заказе** (`6e6280e^:Settings.js:71-74`).
- `equip.discNeedOwn` — полный набор **с учётом прошлых заказов** (`6e6280e^:Settings.js:75-78`).
- Использование: `EquipLinks.js:144-151`, проверки `:181` и `:184`.

Новое приложение после #489:

- `equip.discNeedAll` — проверка **нового заказа** (`web/src/lib/equipmentDiscount.ts`, `satisfied(..., inOrder)`).
- `equip.discNeedOwn` — проверка **полного набора** с учётом прошлых заказов (`web/src/lib/equipmentDiscount.ts`, `satisfied(..., all)`).
- `priorAmount` считает прошлые заказы по старому правилу: полная сумма `o.sum` заказов, где есть хотя бы одна позиция из `discNeedOwn`, включая full-price позиции.

Импорт сохраняет исходные имена ключей (`scripts/import/camps.mjs:111-122`, `scripts/import/run-camps-settings.mjs:104-106`). После #489 новые имена читаются по старой семантике; перестановка значений в БД не выполнялась.

**Потенциальное последствие (устранено):** до #489 непустые импортированные значения могли считаться по обратному правилу. Сейчас код соответствует старой семантике, а эквивалентность закреплена тестами.

**Проверка данных (2026-11-04):** обе строки есть, `scope = ''`, `value = null`, `updated_at = 2026-10-20`. Новое приложение трактует `null`/пустое как отсутствие значения и берёт дефолт (`web/src/lib/clubSettings.ts:45-48`).

**Сопоставление дефолтов:**

- Старый `equip.discNeedAll` по умолчанию требует любую одну из пяти позиций в новом заказе; новый `equip.discNeedOwn` по умолчанию требует то же самое. Функционально эквивалентно.
- Старый `equip.discNeedOwn` по умолчанию требует все четыре группы позиций с учётом прошлых заказов; новый `equip.discNeedAll` по умолчанию требует все четыре группы. Функционально эквивалентно.

**Статус:** **закрыто в #489.** Код читает старые имена по старой семантике, поэтому перестановка значений не нужна. Для проверенного клуба оба значения `null`, используются эквивалентные дефолты. Остаточный риск — только исторические/кастомные значения в непроверенных клубах; история не выгружалась.

**Что сделано:** `priorAmount`, проверка `discNeedAll` по текущему заказу и `discNeedOwn` по полному набору, регрессионные тесты на дефолты, старый custom-пример, прошлые заказы и full-price. Решение владельца: слепую перестановку и миграцию значений не делать.

#### A3. Изменены диапазоны значений; молчаливой подмены больше нет

- `equip.discPct`: старый максимум `100` (`Settings.js:65-66`), новый — `90` (`clubSettings.ts`).
- `extra.cap`: старый максимум `200` (`Settings.js:61-64`), новый — `100` (`clubSettings.ts`); `0` и пусто означают «без ограничения».
- `ind.capIndividual` / `ind.capGoalkeepers`: старый максимум `50` (`Settings.js:55-60`), новый — `100` — расширение безопасно.

После #489 `settingNumber` не возвращает дефолт при недопустимом сохранённом значении: он возвращает `NaN`, а `settingNumberError`/экраны показывают явную ошибку. После #519 SQL `extra_cap` для нечисла, дроби, отрицательного значения или `>100` выбрасывает `22023` (`invalid setting extra.cap: ...`); `0` и пусто остаются «без ограничения».

**Проверка данных (2026-11-04):** `extra.cap = 18` (`updated_at = 2026-11-03`) — значение входит в оба диапазона. `equip.discPct` не найден, используется дефолт `15`. Фактического значения вне нового диапазона в выборке нет.

**Статус:** A3 в части `extra.cap` **закрыт #519** (явная ошибка вместо молчаливого снятия лимита). Для `equip.discPct` остаётся продуктовый вопрос: старые `91..100` теперь не подменяются, а явно предупреждаются и не дают скидку. Диапазоны без отдельного решения владельца не менялись.

**Решение владельца (2026-11-05):** при выходе сохранённого значения за допустимый диапазон приложение не должно молча подменять его дефолтом; нужна явная ошибка/предупреждение и безопасная обработка. Это реализовано в #489 для web и в #519 для `extra.cap`.

**Предложение:** добавить `updated_by` и `updated_at timestamptz`; для критичных ключей — таблицу истории или audit trigger. Минимум — писать `updated_by` из `current_user_id()`.
