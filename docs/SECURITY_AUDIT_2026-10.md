## 3. Подробности находок

### A-01. Анонимный Apps Script и перебор PIN

**Где:** `appsscript.json:8-11` — `executeAs: USER_DEPLOYING`, `access: ANYONE_ANONYMOUS`; `NavCode.js:3-10` — публичный `appWho(pin)`; `NavCode.js:13-18` — `failDelay_`; `NavCode.js:22-24` — `checkPin_`; `NavCode.js:59-68` — `doGet` без авторизации.

**Сценарий:** любой человек открывает URL web app, получает HTML и вызывает `google.script.run.appWho('0000')`. Функция сравнивает PIN с `APP_ADMIN_PIN`/`APP_PIN` и возвращает `admin`/`trainer`/пустую строку. После 20 неудач добавляется задержка до 5 секунд, но нет блокировки, привязки к IP/аккаунту и нет требования к длине PIN. При 4-значном PIN перебор практически реален; при длинном случайном PIN — нет. Успешный подбор даёт доступ к данным и записи старого приложения.

**Проверено:** статически. Прямые вызовы `google.script.run.prop_()` и других функций с `_` **невозможны** по документации Apps Script; прежние находки C2–C5/H1 об анонимном вызове `prop_`, `saveAttendance_`, `addEventCore_` и т.п. **опровергнуты**. Публичные обёртки `appAdminInit`, `appDailySchedule`, `appEquipOrders`, `appTodayPayments`, `appStatsRange`, `appAttInit`, `appRoster`, `appSave` внутри вызывают `checkAdmin_`/`checkPin_`. `appPageHtml`/`doGet` отдают только HTML без данных. Остаётся именно PIN-оракул.

**Рекомендация:** немедленно проверить длину и энтропию `APP_PIN`/`APP_ADMIN_PIN` (12+ случайных символов, разные значения), ротировать; добавить серверную блокировку после N неудач и журнал; по возможности ограничить `access` или перенести вход в Supabase. Не считать `failDelay_` заменой блокировке.

**Можно ли исправить без остановки школы:** да — смена PIN и ограничение доступа выполняются в настройках deployment; блокировку/аудит можно добавить в `appWho`.

### S-01. Перечисление детей через поиск

**Где:** `db/migrations/0014_link_requests.sql:24-41`.

**Сценарий:** вошедший пользователь без роли (гость/ребёнок/посторонний) вызывает `search_players_for_link('Ива')` и получает до 5 активных детей: ФИ и группу. Ограничения: 3 символа, 5 результатов, нет лимита запросов. При нескольких клубах фильтра `club_id` нет — видны дети другого клуба. Прямой `select from players` при этом возвращает 0 строк.

**Воспроизведение:** локальная БД, роли как в `db/tests/rls_link_test.sql`; два клуба A/B, дети `S01 Secret A` и `S01 Secret B`; от имени родителя A:

```sql
select * from search_players_for_link('S01 Secret');
-- S01 Secret A / U9 A
-- S01 Secret B / U9 B
select count(*) from players; -- 0
```

**Рекомендация:** добавить `p.club_id = current_club()` (или клуб текущего пользователя), лимит поисков через `rate_limit_hit`, маскирование/точное совпадение, аудит. При одном клубе проблема остаётся перечислением PII, при нескольких — межклубной утечкой.

**Уверенность:** высокая, воспроизведено.

### S-02. Поток уведомлений через request/cancel

**Где:** `0015_consent.sql:18-33` (`request_link`), `0017_link_cancel_retry.sql:7-13` (`cancel_link`), `0026_notifications.sql:43-60` (триггер).

**Сценарий:** родитель с действующим/отозванным согласием создаёт и сразу отменяет запрос. Каждый цикл вставляет `link_requests` и срабатывает `notify_link_request`, создавая уведомление администратору. Лимит `pending >= 5` обходится отменой; `cancel_link` не ограничен.

**Воспроизведение:** после approval и `revoke_consent` выполнить 20 циклов `request_link` → `cancel_link`; в `notifications` у админа 21 запись `link_request` (включая исходную).

**Рекомендация:** лимит на `request_link`+`cancel_link` (например, 5/час на пользователя и 20/час на клуб), дедупликация уведомлений по `(user_id, player_id)` за окно, не уведомлять о запросе, отменённом в течение N секунд.

**Уверенность:** высокая, воспроизведено.

### S-03. Stale `child_links` после удаления родителя

**Где:** `0025_consent_controls.sql:87-103`, `0028_child_access.sql:28-37`.

**Сценарий:** `erase_parent` удаляет `player_guardians`, `link_requests` и имя, но не `child_links`. После этого ребёнок не видит игрока (`is_self_player` требует действующего guardian), `players=0`, `points=0`. Доступа к данным **нет**. Остаётся строка `child_links`, которая может блокировать привязку новой детской учётки (`already linked`) и создаёт неполное удаление.

**Воспроизведение:** единственный guardian, `erase_parent`; child: `players=0`, `point_events=0`, `is_self_player=false`, `child_links=1`.

**Рекомендация:** удалять `child_links` при `erase_parent` (или помечать неактивной) и добавить проверку в тест удаления.

**Уверенность:** высокая, воспроизведено.

### S-04. Отмена прошедшей/посещённой записи

**Где:** `0045_booking_parents.sql:61-80`.

**Сценарий:** `booking_cancel` проверяет только `was_paid` и настройку `booking.cancelHours`. При default `0` (в комментарии — «отмена в любое время») родитель может отменить неоплаченную запись после начала занятия, даже если `attended=true`; строка `individual_bookings`/`extra_bookings` удаляется вместе с отметкой посещаемости. Теряются attendance и основание для долга.

**Воспроизведение:** создать занятие, записать ребёнка, перенести занятие в прошлое, `ind_set_attended(..., true)`, затем от имени родителя `booking_cancel(...)`; `count(*)=0`, `attended` lost.

**Рекомендация:** запретить отмену после `starts_at`/`starts_on` для родителя; если `attended` уже стоит — только администратор; сохранять attendance/долг при отмене; явно описать политику `cancelHours`.

**Уверенность:** высокая, воспроизведено.

### S-05. Потеря и дубли уведомлений в `tg-notify`

**Где:** `supabase/functions/tg-notify/index.ts:24-41`, `0026_notifications.sql:95-116`.

**Сценарий:** `claim_notifications(20)` увеличивает `attempts` и закрепляет строки на 2 минуты. При `classify(...).stop` (429) функция делает `break`; для остальных уже claim-нутых строк `finish_notification` не вызывается. После трёх запусков у них `attempts=3`, `state='pending'`, `claimed_at` заполнен, и `claim_notifications` их больше не выбирает (`attempts < 3`). Сообщения навсегда зависают. Если Telegram принял сообщение, а `finish_notification` упал, строка остаётся `pending` и будет отправлена повторно — дубль.

**Воспроизведение:** 2 уведомления, три раза `claim_notifications(20)` с `claimed_at = now() - 3 min` без `finish`; четвёртый claim возвращает 0, обе строки `pending/attempts=3`.

**Рекомендация:** при `stop` вызывать `finish_notification` для всех claim-нутых строк или отдельный `release_notifications`; различать «не отправлено» и «неизвестно»; idempotency key; не считать claim без finish потерей попытки; метрика stuck-pending.

**Уверенность:** высокая, воспроизведено на SQL; поведение 429 подтверждено тестами `tests/deno/`.

### S-06. Synthetic-email takeover при публичной регистрации

**Где:** `supabase/functions/tg-auth/index.ts:45-77`, `supabase/functions/tg-login/index.ts:49-81`.

**Сценарий:** email аккаунта — `tg<telegram_id>@telegram.invalid`. Если в Supabase Auth включена публичная Email-регистрация и выключено подтверждение email, атакующий регистрирует этот адрес с паролем. При первом входе жертвы через Telegram `createUser` возвращает «уже есть», `generateLink` выпускает ссылку для auth-пользователя атакующего, `authId` совпадает, и в `users` создаётся строка с `telegram_id` жертвы. Атакующий входит по своему паролю и получает доступ к данным жертвы.

**Проверено:** конфигурация Supabase Auth в репозитории отсутствует, боевой проект не читался. Если подтверждение email включено или регистрация закрыта — сценарий не воспроизводится.

**Рекомендация:** закрыть публичную Email-регистрацию; включить подтверждение email; проверять, что `link.data.user.id` — ожидаемый auth-пользователь; при существующем email требовать административную проверку; не создавать `users` с чужим `authId`.

**Уверенность:** средняя, условная.

### S-07. Межклубная доска и запись на дополнительные

**Где:** `0045_booking_parents.sql:13-34` (`booking_board`), `37-58` (`booking_signup`).

Для `individual` `ind_book` проверяет клуб игрока и отказывает, но для `extra` `booking_signup` вставляет `extra_bookings` без проверки клуба. Родитель A записывает ребёнка A на дополнительное занятие клуба B.

**Воспроизведение:** два клуба, extra-занятие B; от имени родителя A `booking_board()` показывает B; `booking_signup('extra', <B>, <ребёнок A>)` создаёт вторую запись.

**Рекомендация:** фильтровать `booking_board` по клубу текущего пользователя; в `booking_signup` проверять `players.club_id = session.club_id` и для extra; в `booking_cancel` — то же.

**Уверенность:** высокая, воспроизведено; актуально при multi-club.

### S-08. Тренер видит игроков всех клубов

**Где:** `0042_coach_all_groups.sql:15-26`.

**Сценарий:** `players_read` использует `is_any_coach()` без привязки к клубу. Тренер одного клуба читает ФИ, дату рождения и группу игроков другого клуба. Это соответствует решению владельца «тренеры видят все группы» в single-club, но при multi-club становится межклубной утечкой PII.

**Рекомендация:** зафиксировать решение; при multi-club ограничить `is_any_coach()` клубом тренера или явно разрешить только свои/назначенные клубы.

### S-10. `club_photos`: проверка только префикса

**Сценарий:** `revoke_bonus` разрешает админу или любому тренеру игрока удалить ручной балл (`source_type='coach'`), не проверяя, кто его начислил. Два тренера одной группы могут отменять баллы друг друга.

**Рекомендация:** хранить `created_by` и разрешать отмену автору/админу; либо журналировать и ограничить.

**Уверенность:** высокая по коду.

### S-12. Часы тренера через `trainer_attendance`

**Где:** `0042_coach_all_groups.sql:159-170`.

**Сценарий:** `trainer_attendance` возвращает `starts_at`/`ends_at`; тренер может вычислить часы, хотя `trainer_stats.hours` намеренно `NULL` для не-админа. Это обход решения «часы не показывать».

**Рекомендация:** не отдавать точное время или округлять/маскировать; либо считать это допустимым и зафиксировать.

**Уверенность:** высокая по коду.

### S-13. `group_rating` для любой группы

**Где:** `0040_points_start.sql:17-29`.

**Сценарий:** любой authenticated получает `total_points` и `players_count` любой группы по UUID; проверки членства нет. Это агрегат, не персональные данные, поэтому Info.

**Рекомендация:** ограничить группами пользователя/клубом или оставить осознанно.

### S-14. `lead_submit_app` без роли

**Где:** `0044_lead_submit_app.sql:4-16`.

**Сценарий:** любая authenticated-роль, включая ребёнка, может отправить заявку (3/сутки на `telegram_id`). Это спам админу, не доступ к данным. Лимит и дедупликация есть в `lead_submit`.

**Рекомендация:** разрешить только роли guest/parent без привязки или добавить общий лимит на клуб; оставить как есть, если риск принят.

### S-15. `tg-bot` без повтора

**Где:** `supabase/functions/tg-bot/index.ts:59-70`, `supabase/functions/tg-bot/lead-logic.js:69-93`.

**Сценарий:** при 429/500 ответ Telegram не повторяется, функция всегда возвращает 200. Шаг черновика (`step`) уже записан; пользователь не получил следующий вопрос/подтверждение и может застрять. Заявка при сбое `lead_submit` остаётся в `confirm`, повтор возможен.

**Рекомендация:** повтор с backoff для 429/500, идемпотентность по `update_id`, не продвигать шаг до успешной отправки; метрика.

**Уверенность:** высокая по коду/тестам.

### S-16. Replay `initData`

**Где:** `tg-auth/init-data.js:26-38`, `tg-login/login-widget.js:29-46`.

**Сценарий:** подпись принимается 1 час; повторный запрос с той же `initData` выпускает новый magic link в пределах лимита 10/10 мин. Это свойство Telegram; риск проявляется при краже `initData` (XSS/устройство).

**Рекомендация:** одноразовый nonce/сессия, более короткий `maxAgeSec` при возможности, привязка к устройству; текущий `auth_date` уже проверяется.

**Уверенность:** высокая; severity Info.

### S-17. Возможный токен в логах Edge

**Где:** `tg-bot/index.ts:60,65,68` (URL содержит `bot${token}`), `tg-notify/index.ts:32`.

**Сценарий:** при исключении `fetch` сообщение может содержать URL с токеном; в `tg-bot` оно логируется. В `tg-notify` ошибка уходит в `notifications.last_error`, но таблица закрыта для `authenticated` и читается только `service_role`. Прямого чтения токена родителем нет.

**Рекомендация:** не логировать URL/`e.message` целиком, редактировать `bot<token>`; использовать `TELEGRAM_API_BASE` только из доверенной конфигурации.

**Уверенность:** средняя; severity Info.

### S-18. `npm audit`: dev-only critical

**Где:** `web/package.json`; `npm audit` на временном lockfile (не коммитился).

**Результат:** 3 уязвимости: 2 critical (`tinypool`, `vitest`), 1 moderate (`@vitest/mocker`). Все — dev-зависимости, в production-бандл не входят. `fixAvailable` — `vitest@5` (major).

**Рекомендация:** обновить `vitest`/`tinypool` в отдельном PR, проверить тесты; не блокирует запуск.

### S-19. Противоречие в документации про `_`

**Где:** `docs/PROJECT_STATUS.md:44`; официальная документация Apps Script: функции с суффиксом `_` приватны и не вызываются через `google.script.run`.

**Рекомендация:** исправить документ; добавить тест-энумератор публичных функций (уже есть `private-maintenance.test.mjs`); проверить, что боевой deployment собран из текущего кода.
