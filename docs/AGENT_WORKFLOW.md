# Рабочий регламент агентов Coach App

Актуально на 2026-10-21. Этот файл дополняет `CONTRIBUTING.md` и `docs/PROJECT_STATUS.md`.

## Единый источник статуса

- GitHub `master` — стабильная интеграционная ветка, но не обязательно текущая production-версия.
- GitHub Issues — задачи и решения, которые ещё требуются.
- Pull Requests — предлагаемые изменения и место для review.
- Google Apps Script deployment — отдельное действие; состояние `master` не доказывает, что этот код опубликован.
- Если статус в чате расходится с GitHub, сначала проверить фактические SHA, PR, Actions и документы, затем обновить реестр.

## Роли

- **Владелец продукта (Павел):** определяет приоритеты и принимает решения по рискованным действиям, слиянию, удалению веток и deployment.
- **Claude — разработчик:** реализует согласованные задачи в отдельной ветке, пишет/обновляет локальные тесты и PR, сообщает точные SHA, тесты, риски и оставшиеся вопросы.
- **OpenCode — исполнитель аудита/рефакторинга по отдельному заданию:** продолжает только назначенную ему задачу и ветку; не расширяет объём работ без согласования.
- **ChatGPT — координатор и технический reviewer в этом рабочем процессе:** ведёт статус GitHub, выявляет пересечения, проверяет отчёты и diff, помогает определить безопасный порядок PR. Отдельный дизайн-чат отвечает за UX/UI.

Роли не дают права обходить защиту `master` или публиковать приложение.

## Границы текущих веток

| Ветка | Назначение | Правило |
|---|---|---|
| `master` | Стабильная интеграционная ветка | Не коммитить напрямую; изменения только через PR и review |
| `stage-abc` | Аудит OpenCode, PR #2 | Не редактировать параллельно, пока OpenCode не закончит и изменения не будут проверены |
| `chore/repository-governance` | Документация, шаблоны, CI, PR #3 | Изменения процесса/документации; не добавлять бизнес-код приложения |
| `perf-phase1` | Независимые изменения производительности | Не сливать напрямую; сначала разобрать уникальные коммиты и перенести нужные изменения в свежую ветку от актуального master |
| Старые design/settings-ветки | Исторические ветки-кандидаты на очистку | Не удалять до решения владельца и повторной проверки |

Перед началом любой новой задачи сверить актуальные ветки и PR в GitHub: этот список — снимок, а не замена проверки.

## Протокол передачи задачи

Каждая задача должна иметь:

1. Issue с целью, ограничениями, критериями готовности и зависимостями.
2. Одну назначенную ветку, ответственного агента и чёткую границу файлов/логики.
3. Проверку текущего `master` и открытых PR до изменения кода.
4. Отдельный PR с кратким описанием, рисками, тестами и статусом deployment.
5. Финальный отчёт: ветка, base/head SHA, список коммитов и файлов, команды/тесты с фактическим результатом, известные ограничения и следующий шаг.

Не начинать одну и ту же область параллельно в двух ветках. Если обнаружено пересечение — остановиться, сообщить координатору и согласовать владельца изменений.

## Безопасность и тестирование

- Отдельной тестовой среды нет. `/dev` production-проекта использует боевые таблицы и не считается изолированным окружением.
- Разрешены локальные тесты с моками, CI и read-only проверки, если они не вызывают запись в production.
- Запрещены без отдельного согласования: `clasp push`, deployment, тестовые записи в боевые таблицы, слияние PR, удаление веток и изменения production-данных.
- Перед любым потенциально пишущим тестом установить, куда он пишет; при сомнении тест не запускать.
- Успешный CI не заменяет ревью авторизации, платежей, посещаемости, источников данных и побочных эффектов.
- Не заявлять о проверке, если есть только статическое чтение или если результат инструмента не был получен.

## Порядок ближайших действий

1. Дождаться завершения аудита OpenCode по PR #2; проверить его отчёт против фактического diff, CI и тестов.
2. Разрешить дублирование `.github/workflows/test.yml` между PR #2 и PR #3 без параллельного редактирования активной ветки.
3. Провести review PR #3 как отдельного набора изменений документации/CI.
4. Проверить уникальные изменения `perf-phase1`; не переносить ветку целиком вслепую.
5. После отдельного решения владельца включить обязательный CI status check и решить вопрос об удалении исторических веток.
