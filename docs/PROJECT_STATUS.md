## Карта работы — кто за что отвечает

Это карта координации, а не разрешение на параллельное редактирование одних файлов.

| Участник | Зона ответственности | Рабочая ветка/артефакт | Граница |
|---|---|---|---|
| Владелец продукта | Приоритеты и решения о рисках/слиянии/deployment | GitHub Issues и PR | Не считать предложенное решение принятым без явного подтверждения |
| OpenCode | Аудит/работа по текущему заданию этапа A и подготовка этапа B | `stage-abc`, PR #2 | Не менять `master`, не сливать PR, не запускать `clasp push`, не писать в production-таблицы; остановиться после отчёта |
| ChatGPT — GitHub/координация | Документация, карта веток/PR/Issues, независимый аудит и координация | `chore/repository-governance`, PR #3; комментарии/issues | Не редактировать `stage-abc` параллельно с OpenCode; не сливать PR и не публиковать |
| Claude — разработка | Начинать только после передачи актуального handoff и подтверждения задачи | Отдельная ветка от актуального `master`, если не согласовано иное | Сначала прочитать карту статуса, проверить GitHub и согласовать область; не брать одновременно те же файлы, что и OpenCode |
| Техническое ревью | Независимая проверка кода, безопасности, тестов и регрессий | Комментарии к конкретному PR/Issue | Успешные тесты не заменяют ревью |

### Правило передачи работы между агентами

1. До завершения текущего задания OpenCode не назначать Claude параллельную реализацию в `stage-abc` и не давать ему менять те же файлы.
2. После отчёта OpenCode проверить `git status`, diff, список коммитов и CI; затем принять решение, какие изменения остаются в PR #2.
3. Claude получает отдельную задачу с точным Issue/PR, базовой веткой, разрешёнными файлами, запретами и критериями завершения.
4. Один активный исполнитель на одну область кода. Если работа пересекается, сначала согласовать владельца файлов и порядок интеграции.
5. Любой агент в конце сообщает: ветка и base SHA, новые коммиты, изменённые файлы, тесты и точный результат, риски/непроверенные сценарии, состояние PR, deployment (по умолчанию не выполнялся).

## Ветки

На момент инвентаризации были найдены 19 веток (master, три активные рабочие ветки и 15 исторических). Для 15 старых веток дизайна/настроек сравнение с `master` показало `ahead_by = 0`: уникальных коммитов, отсутствующих в `master`, не обнаружено. Это позволяет рассматривать их как кандидатов на удаление, но сами ветки **ещё не удалены**. Перед удалением нужно повторно сверить состояние и убедиться, что ветки не стали активными.

Ветки, которые необходимо сохранить:
- `master` — стабильная интеграционная ветка.
- `stage-abc` — изменения OpenCode; не удалять до завершения review PR #2.
- `perf-phase1` — уникальная работа по производительности; не удалять до решения по Issue #5.
- `chore/repository-governance` — ветка текущего PR #3.

Список проверенных старых веток и результаты сравнения ведутся в [Issue #7](https://github.com/pavlu8sha/coach-app/issues/7). Удаление веток в рамках этой работы не выполнялось.

## Production и deployment

- Production — Google Apps Script web app.
- `/dev` production-проекта использует боевые таблицы и **не является изолированным тестовым окружением**.
- Deployment не выполнялся в рамках организационного PR и не должен подразумеваться по состоянию GitHub.
- Production deployment SHA/версия должны фиксироваться вручную после контролируемой публикации; не выводить их из состояния GitHub.
