# Coach App — типовые дефекты код-ревью и правила их предотвращения

Адресат: Claude Code
Проект: pavlu8sha/coach-app
Дата: 27 ноября 2026
Назначение: снизить количество повторяющихся дефектов, которые обнаруживаются только на независимом код-ревью.

Документ является инженерным стандартом самопроверки разработчика. Он не меняет продуктовые требования и не даёт разрешения на merge, deploy или production-миграции.

Цель — переносить обнаружение таких проблем с этапа независимого ревью на этап разработки. Главная проблема — не отдельные ошибки программирования, а недостаточно полная проверка изменений: защищается основная функция, но забываются связанные RPC; проверяется миграция, но не её rollback; тестируется успешный сценарий, но не потеря ответа, повтор или параллельное выполнение; ошибка загрузки превращается в пустой список или ноль; не учитывается пагинация; исправление ломается на узком мобильном экране; CI проходит, но права доступа и важные сценарии фактически не проверены.

Нумерация разделов (2–8) сохранена из исходного документа. Записи об инцидентах («Уроки») остаются в `CLAUDE.md` и здесь не дублируются.

## 2. Повторяющиеся категории дефектов

### 2.1. Безопасность SECURITY DEFINER и search_path

Приоритет: критический.

Это одна из наиболее заметных повторяющихся проблем.

Примеры:

- PR #820 — обнаружен риск подмены объектов через pg_temp.
- PR #821 — исправлена функция is_admin(), но аудит остальных SECURITY DEFINER функций оставался незавершённым.
- PR #830 — аналогичный риск обнаружен в remove_match_player и save_match.
- PR #855 — замечания по новой функции и rollback.
- PR #866 — повторные замечания по camp_refund, rollback и preflight.

Типовые ошибки:

- SECURITY DEFINER с неполным или небезопасным search_path;
- неявные обращения к таблицам и функциям без `public.`;
- rollback восстанавливает старую небезопасную конфигурацию;
- preflight проверяет наличие функции, но не подтверждает её security-конфигурацию.

Обязательные правила:

1. Для SECURITY DEFINER использовать принятый в проекте безопасный `search_path = public, pg_temp`.
2. Критичные обращения к объектам схемы квалифицировать явно: `public.table_name`, `public.function_name`.
3. Проверять не только новую миграцию, но и rollback.
4. Preflight должен проверять:
   - наличие нужной сигнатуры;
   - prosecdef;
   - proconfig;
   - необходимые EXECUTE grants;
   - отсутствие нежелательных прав у anon.
5. Добавлять регрессионные тесты на попытку подмены объектов через pg_temp.
6. Не считать исправление одной функции завершением аудита остальных функций.

### 2.2. Неполная проверка RLS, RPC и серверных прав

Приоритет: критический.

Примеры:

- PR #819 — широкий аудит SECURITY DEFINER и EXECUTE grants; объём проблемы включал сотни функций.
- PR #821 — исправление is_admin() не означало завершения всего аудита.
- PR #830 — клубная изоляция в remove_match_player и save_match.
- PR #843 — серверная проверка принадлежности к клубу.
- PR #846 — серверная проверка статуса матча.

Типовые ошибки:

- интерфейс скрывает действие, но RPC всё равно позволяет его выполнить;
- проверка роли есть, но проверка клуба отсутствует;
- is_admin() используется там, где требуется более строгое право владельца;
- права на RPC выданы шире необходимого;
- тестируется только штатный пользователь, но не попытки обхода через прямой RPC.

Обязательные правила:

1. UI не является механизмом безопасности.
2. Все значимые ограничения должны проверяться на сервере.
3. Для каждой RPC определить:
   - кто может вызвать функцию;
   - какие данные пользователь может изменять;
   - к какому клубу должны относиться данные;
   - какие роли имеют доступ.
4. Проверять не только разрешённые сценарии, но и запрещённые.
5. Проверять прямой вызов RPC в обход интерфейса.
6. Для финансовых операций отдельно проверять права владельца/Super Admin.
7. Не расширять доступ через GRANT без обоснования.

### 2.3. Конкурентные операции, транзакции и идемпотентность

Приоритет: критический для финансовых операций.

Примеры:

- #722 — риск двойного начисления платежей при конкурентных запросах.
- #721 / PR #866 — идемпотентность возвратов за сбор.
- #830 — защита операций с учётом клубной изоляции.
- PR #842 — гонка между сохранением результата матча и отменой/переносом.

Типовые ошибки:

- повторный запрос создаёт вторую финансовую запись;
- потеря ответа от сервера приводит к повторной операции с новым ключом;
- проверка состояния выполняется до блокировки, а изменение — после;
- разные RPC блокируют одни и те же сущности в разном порядке;
- нет проверки сценария, когда одна операция завершается одновременно с другой.

Обязательные правила:

1. Финансовые операции должны быть идемпотентными там, где возможен повтор запроса.
2. Проверки и изменения данных должны выполняться атомарно.
3. Использовать блокировки и повторную проверку состояния после получения блокировки.
4. Зафиксировать единый порядок захвата блокировок для связанных операций.
5. Проверять сценарии:
   - два одинаковых запроса одновременно;
   - повтор после потери ответа;
   - два разных запроса одновременно;
   - откат первой транзакции;
   - конфликт изменения состояния.
6. Уникальные ограничения БД должны защищать от дублей, а не только клиентский код.
7. При изменении ключей идемпотентности проверять, что незавершённый ключ не теряется при смене параметров операции.

### 2.4. Ошибки загрузки, ложные пустые состояния и нулевые значения

Приоритет: высокий, особенно для финансов и посещаемости.

Примеры:

- #763 / #764 — ошибки загрузки журнала и риск обрезания истории после 1000 записей.
- #761 — ошибки запросов и устаревший список детей.
- #730 — риск некорректного пустого расписания родителя.
- TECH-17 / TECH-18 / TECH-19 — аналогичные проблемы с fallback в сценариях Booking.
- PR #863 — сохранённый фильтр турнира мог скрывать все матчи при ошибке загрузки справочника.

Типовые ошибки:

- error не проверяется;
- `data ?? []` превращает ошибку запроса в пустой результат;
- ошибка финансового запроса отображается как нулевой долг или нулевая выручка;
- интерфейс не различает «нет данных» и «не удалось загрузить данные»;
- после ошибки остаётся активным фильтр, который пользователь не может сбросить.

Обязательные правила:

Каждый запрос должен явно обрабатывать четыре состояния:

1. Loading.
2. Success с данными.
3. Success без данных.
4. Error.

Запрещено:

- показывать пустой список вместо ошибки;
- показывать нулевые финансовые показатели вместо ошибки;
- считать отсутствие строки эквивалентом успешного запроса, если это не предусмотрено логикой;
- скрывать возможность сброса фильтра при ошибке загрузки справочника.

Для финансовых данных это особенно важно: ложный ноль может привести к неправильным управленческим решениям.

### 2.5. Пагинация и ограничения количества записей

Приоритет: высокий.

Примеры:

- #763 / #764 — риск ограничения истории 1000 строками.
- #847 — обнаружено ограничение списка матчей 150 записями.
- #763 — риск неполного отображения журнала баллов.

Типовая ошибка: разработчик проверяет работу на небольшом объёме данных и не замечает, что запрос возвращает только первую часть истории.

Обязательные правила:

1. Для каждого списка определить ожидаемый максимальный объём.
2. Проверять лимиты Supabase и PostgREST.
3. Для исторических и финансовых журналов предусматривать полноценную пагинацию.
4. Не использовать limit без объяснения, почему ограничение безопасно.
5. Проверять работу при количестве записей больше установленного лимита.
6. Проверять сортировку и отсутствие пропусков или дублей между страницами.

### 2.6. Устаревшие асинхронные ответы и состояние интерфейса

Приоритет: высокий.

Примеры:

- #761 — устаревший список детей после запросов.
- PR #841 — раскрытый список тренировок не обновлялся при смене периода; старый ответ мог перезаписать новый.
- PR #840 — до завершения загрузки суммы матча появлялся временный путь ручного ввода.
- PR #863 — сохранённый фильтр продолжал действовать после ошибки загрузки справочника.

Типовые ошибки:

- пользователь меняет фильтр или период, а старый запрос завершает работу позже нового;
- результат старого запроса перезаписывает актуальное состояние;
- UI временно показывает действие, которое не должно быть доступно до завершения загрузки;
- изменение одного параметра не сбрасывает зависимые состояния.

Обязательные правила:

1. Проверять жизненный цикл каждого асинхронного запроса.
2. Использовать cleanup, cancellation или идентификатор актуального запроса.
3. Старый ответ не должен изменять состояние после смены параметров.
4. Проверять переключение фильтров и периодов до завершения предыдущего запроса.
5. Не показывать опасные действия до завершения загрузки необходимых данных.
6. Сбрасывать или корректно пересчитывать зависимые состояния.

### 2.7. Адаптивность мобильного интерфейса

Приоритет: высокий.

Примеры:

- PR #831 — переполнение ConfirmSheet и сжатие имени участника на узких экранах.
- В последующих UI-ревью неоднократно проверялись ширина 320–390 px, длинные имена и кнопки.

Типовые ошибки:

- длинные слова и имена выходят за границы;
- кнопки сжимаются или становятся неудобными;
- карточки переполняют экран;
- модальные окна не помещаются по ширине;
- CSS grid/flex не учитывает min-width: 0.

Обязательные правила:

Проверять интерфейс минимум на ширинах:

- 320 px;
- 360 px;
- 375 px;
- 390 px;
- 430 px.

Особенно проверять:

- длинные имена;
- длинные названия групп;
- кнопки действий;
- ConfirmSheet и другие модальные окна;
- списки с несколькими колонками;
- горизонтальную прокрутку;
- перенос текста и доступность основных действий.

Для grid/flex внимательно проверять min-width, `minmax(0, 1fr)`, overflow-wrap и поведение длинного содержимого.

Автоматические тесты и сборка не заменяют визуальную проверку.

### 2.8. Недостаточное покрытие регрессионными тестами

Приоритет: высокий.

Повторяющаяся проблема — тесты покрывают основной сценарий, но не граничные условия.

Примеры:

- #821 — проверка pg_temp и security-конфигурации.
- #830 — проверки клубной изоляции и прав обеих RPC.
- #842 — конкурентные операции cancel/save/reschedule.
- #855 — проверки SECURITY DEFINER, preflight и rollback.
- #866 — сценарий A → B → A для ключей идемпотентности.

Обязательные правила:

Для каждой значимой бизнес-операции проверять:

- успешный сценарий;
- отсутствие прав;
- неверные входные данные;
- отсутствие связанных данных;
- ошибку запроса;
- повтор операции;
- конкурентное выполнение;
- откат транзакции;
- исторические данные;
- границы допустимых значений.

Если исправляется найденный баг, сначала добавить тест, который воспроизводит дефект, затем исправить код и убедиться, что тест проходит.

## 3. Отдельные требования для финансовой логики

Финансовые операции Coach App требуют повышенного уровня контроля.

Перед изменением финансового кода необходимо проверить:

1. Может ли операция создать дубль?
2. Может ли повтор запроса изменить итоговую сумму второй раз?
3. Что произойдёт, если ответ сервера потеряется после успешного commit?
4. Может ли ошибка загрузки отобразиться как ноль?
5. Не учитывается ли одно обязательство или платёж дважды?
6. Сохраняется ли история операций?
7. Не меняются ли задним числом исторические данные?
8. Проверяется ли право пользователя на сервере?
9. Сохраняется ли клубная изоляция?
10. Есть ли тест конкурентного выполнения?

Нельзя считать финансовую операцию надёжной только потому, что обычный пользовательский сценарий работает.

## 5. Требования к preflight и rollback

Для SQL-изменений нельзя считать миграцию законченной только после успешного применения.

Нужно проверять три независимых части:

Миграция

- корректно создаёт и изменяет объекты;
- задаёт правильные права;
- сохраняет совместимость.

Preflight

- проверяет фактическое состояние объектов;
- проверяет security-конфигурацию;
- обнаруживает неполную или небезопасную установку.

Rollback

- восстанавливает корректную структуру;
- не возвращает старые уязвимости;
- не удаляет финансовую или историческую информацию без отдельного согласования.

## 6. Требования к отчёту разработчика при открытии PR

В описании каждого PR Claude должен указывать:

1. Что изменено.
2. Какие существующие механизмы переиспользованы.
3. Какие права и ограничения проверены.
4. Какие связанные функции и сценарии затронуты.
5. Какие негативные и конкурентные сценарии протестированы.
6. Какие миграции и rollback добавлены.
7. Какие тесты запущены и их результат.
8. Какие ограничения остались.
9. Какие проверки требуют ручного участия владельца.

Нельзя писать «всё проверено», если фактически проверена только сборка или один успешный сценарий.

Если тест не был выполнен, это нужно прямо указать.

## 7. Порядок разработки

Обязательный порядок:

1. Перед изменением изучить текущую архитектуру и связанные участки.
2. До написания кода определить потенциальные ошибки и граничные сценарии.
3. Сразу добавить тесты на важные негативные и конкурентные сценарии.
4. Реализовать изменение.
5. Выполнить самопроверку по разделу 4.
6. Запустить обязательные тесты и дождаться завершения CI.
7. Проверить diff целиком, а не только изменённый основной файл.
8. Только после этого открывать PR.

При исправлении замечания независимого ревью необходимо проверять не только конкретную строку, но и аналогичные места, где может повторяться тот же дефект.

## 8. Критерий успеха

Цель документа — не увеличить количество тестов ради количества и не замедлить разработку.

Нужно добиться того, чтобы:

- SECURITY DEFINER больше не создавались с небезопасным search_path;
- серверные ограничения не оставались только в UI;
- финансовые операции не допускали дублей;
- ошибки запросов не превращались в ложные нулевые или пустые состояния;
- старые асинхронные ответы не перезаписывали актуальные;
- история не обрезалась незаметно из-за лимитов;
- rollback не возвращал устранённые уязвимости;
- мобильные дефекты обнаруживались до независимого ревью;
- каждый исправленный дефект имел регрессионный тест.

Ожидаемый результат: меньше повторных циклов «PR → замечания → исправления → повторное ревью», меньше блокирующих замечаний и более предсказуемое качество изменений.
