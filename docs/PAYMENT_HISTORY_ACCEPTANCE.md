# Условия приёмки: история платежей не стирается каскадом (DATA-01)

Источник: `audit-general/audit-2026-11-11.md`, находка DATA-01 (P1). Миграция 0179, тесты `db/tests/rls_payment_history_guard_test.sql`.

## Проблема

Удаление игрока (`players`) каскадно удаляет строки `payments`, `match_payments` (через `match_fees`), `tournament_payments` (через `tournament_fees`), `service_payments` и `subscriptions`. Триггеров защиты от DELETE и UPDATE на этих таблицах нет. Администратор может удалить платёж или игрока прямым запросом к API: `authenticated` имеет DELETE на `players`, `match_payments`, `tournament_payments`, `subscriptions`, а политики `*_admin` дают ALL. Сумма платежа исчезает без записи в `audit_log`.

Исправление следует шаблону сборов (0165, `camp_payments`): история неизменяема, исправление делается новой строкой (отрицательный платёж «Исправление», как уже делает команда), а не правкой или удалением.

## Решения (приняты владельцем 12.11)

- **Удаление игрока с платежами запрещено** целиком: ни игрок, ни платежи не удаляются. Архивирование через статус `inactive` уже есть и остаётся основным путём.
- **Правка платежа:** разрешены только даты и способ оплаты (`paid_on`, `for_month`, `method`) и комментарий журнала матчей/турниров. Сумма, игрок, родительская ссылка, `cancels`, `subscription_id` и `legacy_ref` не меняются никем. Каждая разрешённая правка пишется в `audit_log` (before/after).
- **Закрытую подписку** (скидка или списание, `discount`/`written_off`) удалить нельзя. Открытую можно, как раньше.
- **Удаление игрока без платежей** разрешено и пишет запись в `audit_log` (действие `player_delete`) с минимальным набором полей (`id`, `club_id`, `status`), без ФИО, чтобы не сохранять персональные данные после удаления.
- **Долги не пропадают каскадом:** игрок с взносом матча или турнира (даже неоплаченным) не удаляется.
- **DELETE на `players` у `authenticated` отозван:** удаление игрока только владельцем в SQL Editor, в интерфейсе и API остаётся архив (`inactive`).

## Условия

У1. Прямой DELETE строки в `payments`, `match_payments`, `tournament_payments`, `service_payments` отклоняется ошибкой `P0001` для любой роли (администратор, локальный администратор, `service_role`, владелец в обычной сессии). Строка остаётся.

У2. Удаление игрока, у которого есть хотя бы одна строка платежа (в том числе через `match_fees` и `tournament_fees`), отклоняется целиком: игрок и все его платежи остаются. Удаление игрока без платежей проходит как раньше.

У3. TRUNCATE четырёх таблиц платежей отклоняется для всех ролей.

У4. UPDATE, меняющий `amount`, `player_id`, родительский идентификатор (`match_id`, `tournament_id`, `kind`/`ref_id`), `cancels`, `subscription_id`, `legacy_ref`, `created_at`, отклоняется. UPDATE только `paid_on`, `for_month`, `method`, `comment` проходит, и в `audit_log` появляется строка `payment_correct` с before и after.

У5. DELETE закрытой подписки (`discount` или `written_off`) отклоняется. DELETE открытой подписки проходит.

У6. DELETE игрока без платежей пишет в `audit_log` строку `player_delete` с полями `id`, `club_id`, `status` и без ФИО и контактов.

У7. Штатные сценарии не меняются:
- отмена платежа записью с `cancels` (`payments`, `match_payments`) работает;
- `match_fee_remove` и `event_roster_remove` отказывают для оплаченного взноса с прежним текстом `fee already paid` и удаляют неоплаченный;
- исправление минусовой записью работает (`rls_admin_edit_test`).

У8. Новые функции (`payment_history_guard`, `payment_history_audit`, `subscription_closure_guard`, `player_delete_audit`) не выполняются ролями `anon`, `authenticated` (EXECUTE отозван). Триггерные функции не имеют гранта для прикладных ролей.

У9. Строка `0179_payment_history_guard` в `db/ops/preflight.sql` показывает `t` только когда все 16 триггеров включены (`tgenabled = 'O'`), функции существуют и у `authenticated` нет DELETE на `players`. Владелец, который отключает триггер для ручной правки, увидит `f`.

У10. Откат `db/ops/rollback-0179-payment-history.sql` снимает триггеры и функции, возвращает `authenticated` DELETE на `players` и тем самым поведение master. Данные не меняются.

У11. Полный `scripts/run-db-tests.sh` на чистой PostgreSQL 16 с pgTAP проходит без `not ok`. Вывод сохраняется в лог.

У12. Игрок, у которого есть взнос матча или турнира (`match_fees`, `tournament_fees`), даже неоплаченный, не удаляется: долг не пропадает каскадом. Штатное снятие неоплаченного взноса (`match_fee_remove`, `event_roster_remove`, пересчёт гостевых взносов) и удаление самого матча или турнира работают как раньше.

У13. У `authenticated` нет DELETE на `players`: администратор через API получает `42501`. Перевод игрока в архив (`status = 'inactive'`) работает как раньше. Удаление игрока остаётся владельцу в SQL Editor.

Решения владельца 12.11: все четыре варианта по умолчанию приняты (запрет удаления игрока с платежами, правка дат с журналом, отзыв DELETE на `players`, защита долгов).

## Вне этой задачи (не делается)

- Скрипт `scripts/import/payment-dates.mjs` делает `update payments` и `delete from payments`. После 0179 он не пройдёт без явного отключения триггера владельцем (как для сборов).
- REL-01 (бэкап) и PAY-01 (единая RPC платежей).
