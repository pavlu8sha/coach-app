# Очередь уведомлений не зависает (REL-02, миграция 0184): условия приёмки

Источник: общий аудит 11.11 (`audit-general/audit-2026-11-11.md`, REL-02, п. 3 в списке блокеров к 1 декабря).

## Проблема
`claim_notifications` при каждой выдаче увеличивает `attempts` и не берёт строки с `attempts >= 3`. Состояние меняет только
`finish_notification`, который вызывает `tg-notify`. Если `finish` не пришёл (Telegram ответил 429 и функция прервала пачку,
функция упала посреди пачки, `finish` вернул ошибку), строка остаётся `pending` и через три такие выдачи навсегда застревает:
не отправляется, не помечается `failed`, в журнале рассылок сборов числится «в очереди».

## Условия
- **Q1.** Строка `pending` с `attempts >= 3`, чья последняя выдача истекла (`claimed_at` старше 2 минут или пусто), при следующем
  `claim_notifications` переводится в `failed`; `last_error` = `stalled` (прежняя ошибка сохраняется после `stalled: `). Она не выдаётся.
- **Q2.** Строка `pending` с `attempts >= 3`, выданная меньше 2 минут назад (отправка идёт), не трогается: `finish` ещё может прийти.
- **Q3.** Строки `pending` с `attempts < 3`, а также `sent`, `failed`, `skipped` правило Q1 не меняет.
- **Q4.** Новая функция `release_notifications(ids uuid[], token uuid)` возвращает выданные, но не обработанные строки: только `pending` с
  `claimed_at is not null`; `attempts` уменьшается на 1 (не ниже 0), `claimed_at = null`. Возвращает число возвращённых строк.
  Строки в других состояниях и невыданные не меняются. Повторный вызов ничего не меняет. Вызывает только `service_role`.
- **Q4а** (замечание к PR #623). Каждый вызов `claim_notifications` помечает выданные строки своим токеном (`notifications.claim_token`,
  возвращается вместе со строкой). `release_notifications` снимает только строки, которые всё ещё держит выдача с этим токеном.
  Сценарий: запуск A выдал строку, обрабатывал пачку дольше 2 минут, запуск B выдал ту же строку заново, A получил 429 и вызвал
  release: выдача B, её попытки и токен не меняются, строка не выдаётся третьему запуску. Без токена (`null`) release ничего не делает.
- **Q5.** `tg-notify` при ответе Telegram 429 вызывает `release_notifications` с токеном своей выдачи для строк пачки после текущей: они не теряют попытку и
  уходят следующим запуском. Сама строка с 429 закрывается `finish_notification`, как раньше. Ошибка `release` пишется в лог,
  ответ функции не ломается. В ответе функции добавляется поле `released`.
- **Q6.** Проверка согласия при выдаче (0176), порядок выдачи (рассылки после обычных), лимит 50 и удаление `sent` старше 30 дней не меняются;
  существующие тесты 0176 проходят без правок ожиданий.
- **Q7.** Права: `release_notifications` и `claim_notifications` недоступны `public`, `anon`, `authenticated`.
- **Q8.** Read-only диагностика `db/ops/readonly-notifications-health.sql`: состояния очереди, `pending` старше 15 минут, зависшие строки
  (как до 0184), `failed` за 7 дней по видам и причинам, расписание `tg-notify` в `cron.job` (если есть `pg_cron`). Ничего не меняет.
- **Q9.** `preflight.sql` содержит строку 0184; откат `db/ops/rollback-0184-notifications-queue.sql` возвращает
  `claim_notifications` из 0176 и удаляет `release_notifications` и столбец `claim_token`; откат проверен в тестовой БД.

## Решения (принял сам, в пределах поручения)
- Зависшая строка становится `failed`, а не возвращается в работу: три выдачи без ответа означают системную проблему, повторная
  отправка рискует дублем (Telegram мог принять сообщение до сбоя). Прежний тест «остаётся в очереди для разбора» заменён на Q1:
  `pending` без пути вперёд вводил в заблуждение и журнал рассылок, и диагностику.
- Чистку `failed`/`skipped` (аудит предлагал 90 дней) не делаю: объём очереди при 226 игроках мал, а эти строки нужны для разбора;
  удаление данных отдельным решением.
- Строки пользователей без `telegram_id` не трогаю: Telegram ответит ошибкой, после трёх попыток строка станет `failed`, как сейчас.

- Тип результата `claim_notifications` расширен полем `claim_token` (последним). Это меняет условие У14 из #238 PR 2c (там зафиксировано
  «поля не меняются»); У14 и его тест обновлены. Прежние поля и порядок те же, поэтому `tg-notify` прежней версии работает с 0184 без изменений,
  а новая версия без 0184 просто не вызывает release (нет токена). Обёртка с прежним типом не подошла: тело ушло бы из
  `claim_notifications(integer)`, и строки preflight 0176 стали бы ложными.

## Не входит
Миграция не применяется; `tg-notify` не разворачивается; cron и реальные рассылки не трогаются.
