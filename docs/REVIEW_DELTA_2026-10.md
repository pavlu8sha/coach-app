### D-01. Функции событий и матчей не ограничены клубом

**Уровень:** высокий при multi-club, низкий для текущего single-club.
**Уверенность:** высокая (локальное репро на двух клубах; текущий single-club не затронут).

**Где:**

- `db/migrations/0051_events.sql:13-24` — `event_list` возвращает все турниры;
- `0051_events.sql:27-48` — `event_create` берёт клуб по имени группы или первый клуб;
- `0051_events.sql:51-96` — `event_roster`, `event_roster_add/remove`, `event_add_game`;
- `0055_match_team_base_name.sql:5-66` — `save_match` принимает любую группу/матч;
- `0056_coach_ind_marks.sql:5-33` — `ind_roster_list`, `ind_set_attended`;
- `0057_coach_extra_marks.sql:4-32` — `extra_roster_list`, `extra_set_attended`;
- `0060_event_roster_stats_kind.sql:17-45` — `match_stats`;
- `0061_coach_match_fees.sql:4-86` — `match_assert_fees`, `match_fees_list`, `match_set_fee`,
  `match_pay`.

**Причина:** функции ищут объект по UUID и проверяют только роль (`event_assert_staff`,
`is_any_coach`), но не сравнивают клуб объекта с клубом пользователя. RLS на `players` и
`tournaments` после `0042` тоже пропускает любого тренера.

**Репро (тренер Club One, данные Club Two):**

```
events_visible        = 1
event_roster_visible  = Player Two
individual_visible    = Player Two
extra_visible         = Player Two
match_fee_visible     = Player Two

new_event_club        = c002
new_game_club         = c002
individual_attended   = t
extra_attended        = t
match_fee_after_coach = 40.00
```

**Влияние:** тренер одного клуба читает состав, индивидуальные/дополнительные занятия и взносы
другого клуба, создаёт там событие/игру, меняет посещаемость и взнос матча. Для текущего одного
клуба эффекта нет; при появлении второго клуба это критично.

**Рекомендация:** в каждой функции брать клуб текущего пользователя (`current_club()` или
аналог) и проверять `club_id` турнира/матча/игрока; добавить multi-club RLS-тесты на чтение и
запись.

**Критерий исправления:** тренер Club One получает `forbidden`/пустой результат на всех
перечисленных RPC для объектов Club Two; multi-club тесты на чтение и запись проходят.

### D-02. Частичная оплата импортированного взноса сбрасывает `paid`

**Уровень:** средний (деньги/учёт).
**Уверенность:** высокая (воспроизведено на event и match).

**Где:**

- `db/migrations/0054_match_fees.sql:5-13` — `tp_paid` использует `tournament_fees.paid`, только
  если строк оплат нет;
- `0054_match_fees.sql:15-20` — `event_fee_recalc` считает только сумму `tournament_payments`;
- `0054_match_fees.sql:34-53` — `event_pay`;
- `0054_match_fees.sql:89-97` — `mp_paid`;
- `0054_match_fees.sql:99-104` — `match_fee_recalc`;
- `0054_match_fees.sql:169-188` — `match_pay`.

**Причина:** импортированный взнос хранится как `paid = true` без строк оплат. После первой
явной оплаты появляется строка `tournament_payments`/`match_payments`, и `*_paid` перестаёт
учитывать исходный флаг; `*_fee_recalc` сравнивает только сумму новых строк с полной суммой.

**Репро:**

```
event: due 50.00, paid 20.00, flag_paid = false
match: due 30.00, paid  5.00, flag_paid = false
```

**Влияние:** админ видит долг там, где импортированная оплата уже была; возможны повторные
списания/неверная дебиторка. Затрагивает только импортированные `paid=true` без строк оплат.

**Рекомендация:** при импорте материализовать `paid` в строку оплаты либо учитывать
импортированный флаг как кредит, не суммируя его с новыми строками дважды. Исправлять новой
миграцией, не редактируя уже применённые `0053`/`0054`; добавить тест «импорт paid + частичная
оплата».

**Критерий исправления:** импортированный `paid=true` на 50 и явная оплата 20 дают итог 50 и
`paid=true`, без двойного учёта; тест на event и match проходит.

### D-03. Удаление импортированного оплаченного взноса события

**Уровень:** средний (потеря данных).
**Уверенность:** высокая (локальное репро).

**Где:** `db/migrations/0053_event_fees.sql:130-138` — `event_roster_remove` проверяет только
наличие `tournament_payments`, но не `tournament_fees.paid`.

**Причина:** `0051_events.sql:75-83` проверял `paid`; `0053` заменил функцию и проверку потерял.
Для `match_fee_remove` в `0054` защита корректна.

**Репро:** импортированный `tournament_fees.paid = true` без строк оплат; вызов
`event_roster_remove` → `tournament_fees` count `1 → 0`.

**Влияние:** удаляется импортированный оплаченный взнос; восстановление требует повторного
импорта/ручного ввода.

**Рекомендация:** вернуть проверку `paid` вместе с проверкой `tournament_payments`, либо
материализовать импорт в строки оплат (см. D-02); добавить тест на импортированный `paid=true`.

**Критерий исправления:** `event_roster_remove` для импортированного `paid=true` возвращает
`fee already paid` или сохраняет взнос; тест на импортированный `paid=true` проходит.

### D-04. Дубли `player_id` в массиве оплаты дают двойное списание

**Уровень:** низкий.
**Уверенность:** высокая (локальное репро).

**Где:** `db/migrations/0054_match_fees.sql:34-53` (`event_pay`) и `:169-188` (`match_pay`):
`foreach pid in array ids` без дедупликации.

**Репро:** `event_pay(t, array[p2, p2], 20, ...)` → 2 строки оплаты, итого `40.00`.

**Влияние:** двойное списание. `event_pay` доступен только админу; `match_pay` доступен тренеру
для friendly, но текущий UI присылает уникальные id. Риск — при новом UI/ручном вызове RPC.

**Рекомендация:** дедуплицировать (`select distinct unnest(ids)`) или отклонять дубли с
`22023`; добавить тест на повтор id.

**Критерий исправления:** `event_pay(t, array[p2, p2], 20, ...)` создаёт одну строку на 20 или
возвращает `22023`; аналогичный тест для `match_pay` проходит.
