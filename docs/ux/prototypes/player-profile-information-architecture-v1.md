# Профиль игрока — единая информационная архитектура v1

**Issue:** #266  
**Статус:** PROPOSAL для UX-ревью. Не является разрешением на реализацию.  
**Основа:** сверка текущего `master`, согласованных решений Issue #266 и существующих макетов.

## 1. Цель

Сделать профиль игрока единым местом, где родитель/ребёнок понимает состояние футбольной жизни и развитие ребёнка, а тренер/администратор быстро получает служебную информацию и инструменты работы. При этом интерфейсы не должны смешивать доступы и выдавать отсутствующие данные за существующие.

## 2. Навигация и вход

### Родитель / ребёнок

- Существующую нижнюю навигацию приложения не меняем в рамках этого предложения.
- Точка входа — текущий экран «Мой ребёнок» / карточка ребёнка.
- Нажатие на карточку открывает полноценный профиль выбранного ребёнка.
- Если у родителя несколько детей, каждый профиль открывается отдельно; переключение ребёнка доступно в заголовке профиля.
- Ребёнок открывает собственный профиль из своего домашнего экрана. Чужие профили недоступны.
- Не добавляем новую постоянную вкладку нижней навигации: это сохраняет текущую архитектуру приложения и не перегружает мобильный интерфейс.

### Тренер / администратор

- Точка входа — существующий список игроков / служебная карточка игрока.
- Служебный профиль не является родительским профилем с дополнительными кнопками: он имеет отдельные действия и таблицы.
- Тренер видит только игроков и группы в пределах назначенных полномочий; администратор — игроков клуба в рамках административных прав.
- Предпросмотр роли не расширяет реальные права.

## 3. Информационная архитектура родительского профиля

| Раздел | Содержание | Доступность данных |
|---|---|---|
| Обзор | Коллекционная карточка; группа и основные сведения; ближайший матч/тренировка; краткий прогресс; последние события | Карточка, группа, баллы и матчевая сводка частично существуют. Ближайшие события и сводка тренировок требуют проверки источников |
| Матчи | Список матчей ребёнка, участие и личные показатели, если есть персональная запись | Основа существует через `match_players`; отсутствие строки не доказывает отсутствие участия |
| Тренировки | Персональная история групповых, индивидуальных, вратарских и дополнительных занятий | Индивидуальные/вратарские и дополнительные записи частично существуют; полная персональная история групповых занятий не подтверждена. До появления надёжного источника раздел не должен изображать её заполненным |
| Прогресс | Физические и технические тесты, личная динамика, цели, анонимное сравнение | Новая продуктовая область из #266; показывать только опубликованные сопоставимые результаты |
| Достижения | Подтверждённые достижения игрока | Концепция/источник достижений не утверждены. Не превращать баллы или место в рейтинге в достижения автоматически |

**Важно:** «Баллы» — существующий отдельный журнал мотивационных начислений. Это не рейтинг тестов, не оценка тренера и не достижения. Не объединять их в общий рейтинг игрока.

## 4. Информационная архитектура служебного профиля

Сохраняем текущую служебную карточку и её разделы: «Абонемент», «К оплате», «Занятия», «Экипировка», «Матчи», «Баллы». В рамках UX-предложения добавляем отдельную область «Развитие» с доступом к тестированиям, целям и истории, но только после продуктового/технического согласования.

Служебный обзор:
- имя, группа, номер и позиция — только если значения реально заполнены;
- текущие административные статусы и быстрые переходы к существующим разделам;
- блок развития показывает последние опубликованные результаты и активные цели;
- черновики, исправления и аудит доступны только уполномоченным сотрудникам;
- действия сотрудника должны соответствовать его роли и группе.

## 5. Правила отображения данных

1. Нет данных — показываем честное пустое состояние с объяснением, а не нули, фиктивные графики или заглушки, похожие на реальные показатели.
2. Черновик тестирования не показывается родителю/ребёнку.
3. Несопоставимые тесты не соединяются линией динамики и не сравниваются.
4. Исправленный опубликованный результат отображается актуальным; информация об исправлении доступна согласно правам.
5. Групповое сравнение содержит только собственный результат/место и анонимные агрегаты, без имён, фото, списка мест и чужих индивидуальных результатов.
6. Родитель и ребёнок видят одинаковые сведения о прогрессе.
7. Фото загружает только родитель добровольно. Публичное использование требует отдельного согласия.
8. Не показывать пользователю действия, которые ему недоступны.

## 6. Состояния

- Загрузка профиля: скелетон основных блоков без скачков макета.
- Ошибка загрузки: понятное сообщение и повторная попытка; не показывать устаревшие данные как актуальные без маркировки.
- Профиль без фото: завершённая фирменная карточка, без серого пустого силуэта.
- Недостаточно данных: текстовое объяснение, что будет доступно после появления результатов/записей.
- Нет опубликованных тестов: объяснить, что тренер ещё не опубликовал результаты.
- Нет сопоставимого предыдущего теста: показать текущий результат без тренда.
- Нет индивидуальных целей: спокойное пустое состояние; родитель может предложить цель, но не создать активную.
- Несколько детей: переключатель в контексте профиля, без смешивания их данных.
- Недоступный профиль/отозванная привязка: закрытый экран без утечки сведений.

## 7. Адаптивность

- 320–430 px: одна колонка; вкладки горизонтально прокручиваемы только внутри своей полосы (без переполнения всей страницы); ключевые действия доступны без горизонтального скролла.
- Планшет: карточка и краткая сводка могут располагаться в две колонки.
- Desktop служебного интерфейса: широкая таблица, закреплённая колонка игрока, узкие формы/диалоги.
- Светлая и тёмная темы используют существующие токены; переключение темы остаётся ручным.

## 8. Что не меняем

- Действующую нижнюю навигацию и правила ролей.
- Двухэтапное подтверждение платежей.
- Существующие права доступа и серверные проверки.
- Согласованные правила рейтинга, тестирований, попыток, исправлений и анонимного сравнения.
- Не вводим новые бизнес-правила по достижениям, фото-согласиям или истории тренировок.

## 9. Критерии приёмки UX

- Путь от «Мой ребёнок» до профиля понятен без дополнительного пункта нижнего меню.
- При нескольких детях контекст выбранного ребёнка всегда очевиден.
- Родитель и ребёнок не видят чужие индивидуальные результаты.
- Сотрудник видит только доступных ему игроков и действия.
- Баллы, тесты, цели и достижения визуально и смыслово разделены.
- Пустые/ошибочные состояния не маскируются фиктивными данными.
- На 320 px нет горизонтального переполнения страницы.
- Существующие разделы не теряют доступность и не дублируются без причины.

## 10. Открытые вопросы перед передачей в разработку

- Источник полной персональной истории групповых тренировок.
- Продуктовое определение «достижения» и источник их подтверждения.
- Разрешённые поля публичной коллекционной карточки и итоговый формат экспорта — с учётом оригинальной презентации Kickstart, которую ещё предстоит приложить к Issue.
- Три открытых вопроса по фото/согласиям уже перечислены в основной спецификации #266; макеты не должны самостоятельно выбирать за владельца продукта.
