# Условия приёмки: раздел «Мероприятия» (Issue #677), MVP

Версия: 2026-11-16 (v4, N1–N5 закрыты), для утверждения Павлом. Реализации, миграций и PR нет.
Порядок по CLAUDE.md: условия приёмки → тесты от условий → код. Тесты ниже пишутся до кода; каждый ID = один тест (или группа в одном файле `db/tests/rls_club_events_*_test.sql`, параллельные — `db/tests/concurrency_club_events_*.sh`).
Проверка считается пройденной только с полным выводом `scripts/run-db-tests.sh` (CLAUDE.md). Независимой проверки второй моделью нет (решение владельца 2026-11-11), в PR писать это прямо.
Все проверки прав и функций гоняются на базе с привилегиями Supabase по умолчанию (`alter default privileges ... grant ... to anon, authenticated, service_role`), а не только на пустой.

## 0. Утверждённые решения (источник: сообщение Павла 2026-11-16 + ТЗ #677)

D1 Базовая цена меняется для всех без индивидуальной цены, включая записанных; баланс считается динамически; каждое изменение в истории цен; платежи не меняются.
D2 Смена базовой или индивидуальной цены требует причину, не короче 3 символов после trim.
D3 Переплата допускается, показывается отдельно от долга, операции не блокирует.
D4 Перенос: только тот же игрок; только на другое мероприятие со статусом «Активное»; только если у игрока уже есть активная запись на целевое; между игроками и между типами услуг нельзя.
D5 Частичные возвраты и переносы; сумма возвратов и переносов по платежу ≤ его неиспользованного остатка; каждая операция отдельной строкой; исходный платёж не меняется.
D6 Платежи: черновик — нельзя; активное — можно; завершённое — можно; отменённое — новые платежи нельзя; отменённая запись — можно, если по ней остался долг. Возвраты и переносы по правилам журнала.
D7 Переходы мероприятия: черновик→активное, черновик→отменённое, активное→завершённое, активное→отменённое, отменённое→активное. «Завершённое» конечное, в черновик возврата нет.
D8 Лимит можно снизить ниже числа активных записей: предупреждение, не блок; новые записи сверх лимита нельзя; существующие не отменяются.
D9 Все даты, время, дедлайны и проверки по Asia/Tbilisi.
D10 Участники только игроки клуба.
D11 Восстановление записи сохраняет индивидуальную цену, платежи и историю; перед ним проверяются статус мероприятия, дедлайн, лимит; восстановление записи и реактивация мероприятия независимы.
D12 Пилот FC Kickstart: один клуб. До подключения второго клуба обязательны полная клубная изоляция и привязка админов к клубам (условие масштабирования, не пожелание).
D13 Раздел называется «Мероприятия», отдельно от «События».
T1 Отдельная сущность `club_events` и объекты `club_event_*`; `tournaments` не расширяется.
T2 Журнал `club_event_payments` (append-only): `payment`, `refund`, `transfer_out`, `transfer_in`; `request_id`; связь возврата с платежом (`refund_of`); пара переноса по `transfer_id`; физического удаления нет.
T3 Перенос в кассовые итоги не входит; платежи и возвраты входят по общей модели (возврат уменьшает кассу в день возврата).
Из ТЗ: один игрок — одна запись на мероприятие, включая отменённые (восстановление, не новая запись); отмена записи/мероприятия сама по себе возвратов и переносов не создаёт; физического удаления мероприятия нет; завершение вручную; уведомлений и родительской части нет.

## 1. Определения

- Цена записи = индивидуальная цена, если задана, иначе базовая цена мероприятия (замена, не сумма).
- Засчитано = Σ(payment) + Σ(transfer_in) − Σ(refund) − Σ(transfer_out) по записи.
- Долг = max(цена − засчитано, 0). Переплата = max(засчитано − цена, 0). Одновременно ненулевыми они не бывают.
- Остаток платежа P = сумма P − Σ(refund с refund_of=P) − Σ(transfer_out с источником P).
- Активная запись: статус `active`. В лимит входят только активные.
- Цена 0 допустима (бесплатное мероприятие); на неё платёж не обязателен, долга нет.
- Суммы: numeric(10,2), в операциях строго > 0 по модулю; знак хранится по `op` (payment/transfer_in плюс, refund/transfer_out минус), знак вразрез с `op` отклоняется.

## 2. Матрица платежа (D6, проверяется целиком)

| Мероприятие | Запись | Новый платёж |
|---|---|---|
| draft | — (записей быть не может) | нельзя |
| active | active | можно (в том числе сверх долга, D3) |
| active | cancelled | только если по записи долг > 0 |
| finished | active | можно |
| finished | cancelled | только если по записи долг > 0 |
| cancelled | любая | нельзя |

Платёж на отменённую запись ограничен текущим долгом (U3, тест PAY10); на активную запись сверх долга можно (D3).

## 3. Тест-кейсы

Формат: ID — условие → ожидаемый результат. «Отказ» = исключение с кодом из соглашения проекта (42501 права, 22023 данные, P0002 не найдено, 55000 состояние, 23505 дубль), текст ошибки без персональных данных.

### EV. Мероприятие и жизненный цикл
- EV1 админ создаёт с названием, описанием, датой-временем, местом, базовой ценой ≥ 0 → строка создана, статус draft или active по выбору, club_id заполнен.
- EV2 пустое название, цена < 0, цена NULL → отказ.
- EV3 без групп → общеклубное (признак выводится функцией списка); с 1 и с несколькими группами → связи созданы; дубль группы в списке не создаёт вторую связь; группа другого клуба → отказ.
- EV4 допустимые переходы из D7 проходят; недопустимые (draft→finished, active→draft, finished→любой, cancelled→finished, cancelled→draft, cancelled→cancelled) → отказ 55000, статус не меняется.
- EV5 физического удаления нет: DELETE и TRUNCATE таблиц мероприятий, групп, участников → отказ у всех ролей (включая service_role); функции удаления не существует.
- EV6 завершение только вручную: наступление даты ничего не меняет (статус остаётся active после даты).
- EV7 реактивация cancelled→active: записи, платежи, цены, история те же, число строк в журналах не меняется (нет дублей); новые записи снова ограничены дедлайном и лимитом.
- EV8 отмена мероприятия: записи остаются в статусах как были, платежей, возвратов, переносов не появляется.
- EV9 редактирование названия, описания, места, даты-времени, цены, дедлайна, лимита, групп разрешено в draft, active, cancelled, finished; изменение пишется в журнал изменений (кто, когда, что было, что стало).
- EV10 (U13) смена даты-времени при наличии активных записей: вызов без `confirm` возвращает предупреждение (число затронутых) и ничего не меняет; вызов с `confirm = true` применяет; записи не отменяются. Без активных записей применяется сразу. Тот же контракт у снижения лимита ниже активных (LD4).
- EV11 дата/время хранятся и сравниваются в Asia/Tbilisi; события около полуночи UTC (20:00–23:59 UTC) показывают правильную дату Тбилиси.

### PR. Цена и история цен (D1, D2)
- PR1 запись без индивидуальной цены берёт базовую; с индивидуальной — её (не сумму).
- PR2 смена базовой цены меняет цену и долг у всех записей без индивидуальной цены, включая уже оплаченные частично; записи с индивидуальной ценой не меняются.
- PR3 смена индивидуальной цены одному игроку не меняет базовую и цены остальных.
- PR4 причина < 3 символов после trim (пустая, пробелы, 2 символа) → отказ, цена не меняется; для базовой и для индивидуальной.
- PR5 каждое изменение (базовая, индивидуальная, сброс индивидуальной на «по базовой») пишет строку истории цен: кто, когда, объект, старое, новое, причина; история не редактируется и не удаляется (update/delete/truncate → отказ).
- PR6 после смены цены платежей, возвратов, переносов не создаётся, строки журнала платежей не меняются (сравнить снимок до и после).
- PR7 снижение БАЗОВОЙ цены ниже засчитанного у записей без индивидуальной цены допустимо (D1+D3): долг 0, возникает переплата (возвращается только обычным возвратом); повышение выше засчитанного → долг > 0; платёжных строк не прибавилось.
- PR8 цена с тремя знаками после запятой, отрицательная, нечисловая → отказ.
- PR9 смена цены в завершённом и отменённом мероприятии разрешена (редактирование исторических данных), с причиной.
- PR10 повтор установки того же значения цены (базовой или индивидуальной) без изменения: новая строка истории и причина не требуются, ничего не пишется; сброс индивидуальной в «по базовой» — это изменение цены, требует причину и пишет строку истории.
- PR11 (N3/U10) индивидуальная цена ниже засчитанной суммы: у АКТИВНОЙ записи допускается и создаёт переплату (D3), долг 0, платёжных строк не прибавляется, переплата возвращается только обычным возвратом; у ОТМЕНЁННОЙ записи новая индивидуальная цена ниже засчитанной → отказ 22023 «price below counted», цена не меняется; равна засчитанной → долг 0, принято; выше → долг. Действует независимо от статуса мероприятия (активное, завершённое, отменённое). Граница: засчитано 0 → любая цена ≥ 0; сравнение с актуальным засчитанным (после возвратов и переносов).
- PR12 (U10) закрытие долга отменённой записи: (а) платёжом ≤ долга, (б) изменением индивидуальной цены на сумму ≥ засчитанного с причиной (PR4); списания долга как операции не существует (grep-тест: нет функции/значения op «writeoff»/«списание» в разделе). Восстановление отменённой записи (PT9) после снижения цены: цена и переплата сохраняются как есть.
- PR13 (U1) цена 0: запись создаётся, долг 0, статус «оплачено» (вычисляется), платёж на цену 0 допускается как переплата только по правилам PAY (активная запись); индивидуальная цена 0 допустима.

### PT. Участники (ТЗ 5.3)
- PT1 добавление игрока клуба в active → запись active.
- PT2 повторное добавление того же игрока (активного и отменённого) → дубля нет, отказ 23505 с понятной причиной; параллельное добавление двумя сессиями → ровно одна запись.
- PT3 добавление в draft, finished, cancelled → отказ.
- PT4 игрок не из выбранных групп: функция возвращает предупреждение и добавляет только после подтверждения; без групп мероприятия предупреждения нет; предупреждение не блокирует.
- PT5 (U6) игрок другого клуба, несуществующий, архивный/неактивный (статус не «активный» по `playerStatus`) → отказ при добавлении; уже записанный игрок, ставший архивным: запись, платежи, возвраты, переносы остаются, список показывает запись; восстановление отменённой записи архивного игрока → отказ (повторное включение = новое участие, только активным); платёж по существующей записи архивного игрока разрешён по матрице.
- PT6 родитель, ребёнок-пользователь, тренер, анонимный вызов → отказ (раздел ACL).
- PT7 отмена записи: статус cancelled, строка и платежи на месте, засчитано не меняется, возврата и переноса нет; повторная отмена → отказ или идемпотентный no-op (поведение закрепить в тесте).
- PT8 отмена записи в finished и cancelled мероприятии допустима (исторические данные); добавление и восстановление там запрещены.
- PT9 восстановление (D11): та же запись (тот же id), статус active, индивидуальная цена и платежи сохранены; новая строка не создаётся; повторное восстановление активной → отказ или no-op; восстановление архивного игрока запрещено (PT13).
- PT10 каждая смена статуса записи пишет строку истории участия (кто, когда, из какого в какой).
- PT11 удаление игрока с записью мероприятия, который имеет платежи в журнале → отклоняется (как 0179); удаление игрока без записей не затрагивается.
- PT12 список участников отсортирован по имени, без рейтингов, голов, мест, сравнений; запрос списка не возвращает данных, которых нет в разрешённом наборе.
- PT13 (N4) восстановление отменённой записи игрока со статусом архивный/неактивный → отказ 22023 «player not active», запись остаётся cancelled; платёж, возврат, перенос по существующей записи архивного игрока (активной или отменённой) разрешены по матрице и правилам D5; смена статуса игрока обратно на активный делает восстановление доступным.

### LD. Лимит и дедлайн (D8, D9)
- LD1 лимит не задан → без ограничения; дедлайн не задан → без ограничения.
- LD2 лимит N: N активных → добавление (N+1)-го отклонено; отменённые записи место не занимают; после отмены одной активной добавление проходит.
- LD3 восстановление записи при заполненном лимите → отказ; при свободном месте → успех.
- LD4 снижение лимита ниже числа активных → предупреждение (возвращается число превышения), изменение сохраняется, записи не отменяются; новые добавления отказ.
- LD5 лимит < 1 или нечисло → отказ (как `camps_capacity_check`).
- LD6 дедлайн: до момента — добавление проходит; в момент и после — отказ (граница: проверка `now >= deadline` по Тбилиси); восстановление после дедлайна — отказ; существующие записи, платежи, возвраты, переносы после дедлайна работают.
- LD7 дедлайн проверяется на сервере: прямой вызов функции после дедлайна → отказ независимо от веба.
- LD8 гонка: лимит 1, две параллельные сессии добавляют разных игроков → одна успешна, вторая отказ; гонка добавление/восстановление за последнее место → ровно одна запись активна. Скрипт `concurrency_club_events_seats.sh`.
- LD9 переход дедлайна между открытием формы и сохранением → отказ с кодом/текстом «дедлайн истёк».

### PAY. Платежи (D3, D6, ТЗ 5.5)
- PAY1 платёж по матрице раздела 2: все 6 строк × разрешено/запрещено → ожидаемый результат; в строках «cancelled-запись, долг > 0» граница: сумма = долгу → принят; долг + 0.01 → отказ.
- PAY2 несколько частичных платежей одной записи суммируются; засчитано, долг, переплата считаются по определениям.
- PAY3 платёж равен долгу → долг 0, «оплачено полностью»; платёж больше долга → переплата показана отдельно, платёж принят; следующие операции не блокируются.
- PAY4 сумма 0, отрицательная, NULL, > 2 знаков → отказ.
- PAY5 способ обязателен и только из существующего набора («Наличные», «Перевод»; подтверждение U5); неизвестный, пустой → отказ; способ сохраняется как фактический.
- PAY6 (U4) дата платежа: пусто → сегодня по Тбилиси; будущая (по Тбилиси) → отказ; прошлая любой давности → принимается; граница «сегодня 23:59 Тбилиси» не отклоняется из-за UTC.
- PAY7 платёж игрока из другого мероприятия/записи, не существующей записи → отказ; сумма платежа не влияет на другие записи.
- PAY8 флага «оплачено» в таблице нет: статус «оплачено/долг/переплата» вычисляется (тест на согласованность: после любой серии операций вычисленное совпадает с Σ из журнала).
- PAY9 автор (`recorded_by`) и время ставит сервер; клиент подделать не может.
- PAY10 (U3) платёж по отменённой записи: сумма ≤ текущему долгу; > долга → отказ; при долге 0 → отказ; по активной записи сверх долга разрешено (D3). Один платёж больше долга и серия платежей, суммарно превышающая долг, отклоняются на сумме, которая выводит за долг (параллельные платежи — через блокировку записи).

### RF. Возвраты (D5, ТЗ 5.6)
- RF1 возврат полной суммы платежа → строка refund со ссылкой `refund_of`, исходная строка не изменена (побайтово), засчитано уменьшилось.
- RF2 частичный возврат; два частичных возврата подряд; сумма возвратов = остатку платежа → остаток 0; ещё один возврат → отказ «выше остатка».
- RF3 возврат > остатка платежа → отказ; возврат по платежу другой записи/другого игрока → отказ; возврат по refund/transfer-строке (не по payment) → отказ.
- RF4 возврат разрешён для записей и мероприятий всех статусов, включая отменённое мероприятие и отменённую запись; возврат без предшествующей отмены допускается (U2).
- RF5 возврат допускается, даже если засчитано станет ниже цены (долг возникает); возврат не создаёт отрицательную переплату сверх логики формулы.
- RF6 способ возврата из набора, дата не будущая; авто-возврат при отмене записи/мероприятия/реактивации не создаётся (счётчик строк до и после).
- RF7 (U7/N1) исходный платёж и все строки журнала: UPDATE любого столбца (сумма, дата, способ, игрок, запись, op, ссылки, request_id, комментарий, автор, время) → отказ у authenticated, service_role, anon; DELETE и TRUNCATE → отказ; допустимых «разрешённых столбцов» нет (в отличие от 0179). Корректировки ошибочного платежа функцией «сторно/отмена платежа» нет (grep-тест: ни такой функции, ни op); исправление только обычным возвратом.
- RF8 (U11) переплата возвращается обычным refund (≤ остатка платежа); функции/операции «списать переплату» нет (grep-тест); возврат переплаты уменьшает переплату в точности на сумму.
- RF9 (U4/U5/U8) refund: дата выбирается админом, пусто → сегодня Тбилиси, будущая → отказ; способ выбирается админом из «Наличные»/«Перевод», не обязан совпадать со способом исходного платежа; способ и дата сохраняются в строке возврата.
- RF10 (N1) возврат фиксирует факт возврата денег: обязательны способ из набора и дата (не будущая), параметра «без выплаты/фиктивный/корректировка без движения денег» нет; обязателен комментарий-пояснение не короче 3 символов, который пишется в `audit_log` (RF11); попытка «вернуть» без способа/даты → отказ. Для прочих ошибок ручного исправления в разделе нет (вне MVP), тест: список функций раздела не содержит функций правки/удаления финансовых строк.
- RF11 (N2) пояснение к возврату и любые уточнения к операции пишутся функцией в `audit_log` (actor, действие, сущность = id операции, текст, время); `audit_log` не даёт править исходную строку журнала; у пользователей authenticated прямой записи в `audit_log` нет.

### TR. Переносы (D4, D5, ТЗ 5.6)
- TR1 успешный перенос: создаются ровно две строки (transfer_out у источника, transfer_in у цели) с общим `transfer_id` в одной транзакции; сумма равна; исходный платёж не изменён; засчитано источника −X, цели +X, итог системы по игроку не меняется (нет двойного учёта).
- TR2 частичный перенос; перенос + возврат из одного платежа в сумме ≤ остатка; превышение → отказ; два параллельных переноса на сумму > остатка → проходит максимум один (скрипт `concurrency_club_events_transfer.sh`).
- TR3 другой игрок (брат/сестра) → отказ; тот же мероприятие → отказ; цель не active (draft, finished, cancelled) → отказ; у игрока нет записи на цель → отказ; запись на цель cancelled → отказ (нужна активная); цель из другого клуба → отказ.
- TR4 цель — не мероприятие (сбор, занятие, взнос матча, событие-турнир, абонемент) → такой операции нет/отказ.
- TR5 после переноса источник мог получить долг, цель — переплату; операции не блокируются (D3).
- TR6 перенос разрешён из мероприятия и записи любого статуса (U2); перенос из «чужого» платежа по другой записи → отказ.
- TR7 пара неделима: сбой на второй строке откатывает обе (инъекция ошибки); у каждой transfer_out есть transfer_in и наоборот (проверка целостности, запрос возвращает 0 сирот).
- TR8 параллельные переносы A→B и B→A: нет взаимной блокировки (порядок блокировок по id), оба завершаются или один получает отказ по правилам.
- TR9 transfer_out/transfer_in нельзя создать напрямую, только функцией (прямая вставка → отказ у всех ролей); повторный перенос с тем же `request_id` → ничего нового, возвращает результат первого.
- TR10 (U8, исправлено противоречие) перенос: дата обеих строк `transfer_out`/`transfer_in` = текущая дата Asia/Tbilisi на момент операции (не дата исходного платежа, не задаётся клиентом); способ обеих строк = способ исходного платежа; клиент не может задать ни дату, ни способ переноса (параметров нет); у обеих строк тот же `transfer_id`, в журнале виден источник (платёж и запись) и цель (запись).

### CASH. Касса (T3)
- CASH1 `cash_report` и `cash_day_service` за день: платёж попадает, возврат попадает с минусом в день возврата, transfer_out/transfer_in не попадают ни в какие денежные итоги, даже если даты или способы разные.
- CASH2 итог кассы за день с набором payment+refund+transfer не отличается от итога без transfer.
- CASH3 подпись вида в ленте: «Мероприятие» (не «Доп. занятие» и не «Взнос события»); название мероприятия в детали.
- CASH4 локальный админ (location_admins) строк мероприятий не видит; обычный админ видит все.
- CASH5 регрессия: суммы по абонементам, сборам, экипировке, занятиям, взносам матчей и событий-турниров прежние (сверка до/после миграции на фикстуре).
- CASH6 тела функций кассы построены от текущего master (урок 2026-11-11): тест-страж на присутствие строк `tournament_payments`/`match_payments` в обоих функциях.

### IDEM. Идемпотентность и параллелизм
- IDEM1 тот же `request_id` для payment/refund/transfer → вторая попытка не добавляет строк и возвращает прежний результат; тот же `request_id` с другими параметрами → отказ (конфликт), не молчаливое принятие.
- IDEM2 параллельные вызовы с одним `request_id` → одна запись.
- IDEM3 `request_id` обязателен для денежных операций (NULL → отказ), чтобы повторный клик не мог задвоить.
- IDEM4 параллельные платежи по одной записи суммируются без потерь.

### HIST. Неизменяемость
- HIST1 (U7) `club_event_payments`: DELETE, TRUNCATE, UPDATE ЛЮБОГО столбца → отказ у authenticated, service_role, anon; в таблице нет триггера «разрешённых правок» и нет записи в `audit_log` типа payment_correct; owner может отключить триггер осознанно (как 0179), preflight показывает состояние триггеров (красный при отключённом).
- HIST5 (U7/N2) уточнения к финансовой операции хранятся только в `audit_log`: функция добавляет запись с id операции, автором, временем, текстом ≥ 3 символов; исходная строка журнала не меняется (снимок до и после побайтово равен); повторное уточнение добавляет новую запись, старые не правятся; вызывать функцию может только админ (ACL1).
- HIST2 таблицы записей, истории статусов, истории цен, журнала изменений мероприятия, переносов: update/delete/truncate запрещены для исторических столбцов.
- HIST3 каскады: удаление игрока, группы или мероприятия с платежами → отклоняется целиком; ни один внешний ключ не имеет `on delete cascade` к финансовым строкам.
- HIST4 откат миграции (скрипт rollback) удаляет объекты только до появления данных; после появления платежей откат отказывает с понятным текстом либо сохраняет таблицы (поведение указать в README откатов).

## 4. Права доступа и клубная изоляция (обязательная проверка)

Роли для теста: A1 админ клуба; A2 админ второго клуба (фикстура); LA локальный админ (location_admins); C тренер; C2 тренер другой группы; P родитель с ребёнком в мероприятии; K ребёнок-пользователь; G гость/без роли; N аноним (anon-ключ, без JWT); S service_role.

### ACL. Права
- ACL1 функции создания, редактирования, смены статуса, добавления/отмены/восстановления записи, смены цены, платежа, возврата, переноса: A1 — разрешено; LA, C, C2, P, K, G, N — отказ 42501; решение 13.11 (тренерам события создавать нельзя) соблюдено.
- ACL2 чтение таблиц и функций списков/карточек/участников/платежей/истории: A1 — можно; LA, C, P, K, G, N — пусто или отказ, без данных (в том числе имён игроков и сумм); P не видит даже мероприятия своего ребёнка (родительской части нет в MVP).
- ACL3 прямая запись в таблицы (INSERT/UPDATE/DELETE) из роли authenticated, включая A1, → отказ; запись только функциями (SECURITY DEFINER с проверкой `is_admin()` внутри).
- ACL4 `anon`: EXECUTE на все функции раздела отозван, SELECT на таблицы отозван; проверка через `has_function_privilege`/`has_table_privilege` для anon, authenticated, service_role, public на базе с default privileges Supabase и на чистой базе; вспомогательные функции недоступны authenticated.
- ACL5 service_role: SELECT на таблицы разрешён для импорта/бэкапа, прямая запись в журналы запрещена (как 0165).
- ACL6 админ без записи в users или с `is_admin=false` → отказ; вызов без JWT → «not authenticated».
- ACL7 тренер не получает прав через имеющиеся функции событий-турниров (`event_assert_staff`): функции «Мероприятий» отдельные, `is_any_coach()` в них не используется (grep-тест на текст функций).
- ACL8 ни одна функция не возвращает данные о доле, голах, рейтингах, местах (продуктовое правило «без сравнений детей»).

### ISO. Клубная изоляция
Принято (D12): пилот на одном клубе; полная изоляция по админам обязательна до второго клуба.
- ISO1 (обязательна сейчас) `club_id` есть у мероприятия, записей, платежей, истории; он выводится сервером (из мероприятия/игрока), клиентом не задаётся.
- ISO2 (обязательна сейчас) целостность между клубами: игрок из клуба 2 в мероприятие клуба 1 → отказ; группа клуба 2 у мероприятия клуба 1 → отказ; перенос между мероприятиями разных клубов → отказ; платёж/возврат со ссылкой на запись другого клуба → отказ (проверяется и в функциях, и CHECK/триггером по `club_id`).
- ISO3 (обязательна сейчас) при существовании второго клуба в фикстуре: все запросы списков и кассы фильтруют по клубу мероприятия там, где клуб известен, без утечки строк чужого клуба через join.
- ISO4 (сторож масштабирования, красный при втором клубе) preflight-строка и тест: если в `clubs` больше одной строки, а админы не привязаны к клубам (нет `users.club_id` или аналога), проверка красная и блокирует подключение клуба. Тест фиксирует нынешнее допущение явно, а не молча.
- ISO5 (после реализации привязки админов, до второго клуба — отдельная задача; тесты написать сразу, отметить как отложенные, не пропущенные) A1 не читает и не пишет мероприятия, записи, платежи и кассу клуба 2; A2 то же с клубом 1; `is_admin()`-политики таблиц мероприятий заменены на клубные; location-админы и тренеры привязаны к клубу; service_role-импорт получает клуб явно.
- ISO6 (отложенный набор, сквозной) RLS и функции раздела не используют глобальный `is_admin()` без проверки клуба; тест-страж ищет такие вызовы в телах `club_event_*` (в MVP — белый список с комментарием «до D12»).
- ISO7 (U12, обязательна сейчас) один клуб: создание мероприятия берёт единственный клуб; `clubs` > 1 и админ не привязан к клубу (привязки в схеме нет) → создание отказывает 55000 «club binding required»; чтение и остальные операции существующих мероприятий не затрагиваются этим отказом.

### NOSIDE. Побочные эффекты и смежные модули
- NOSIDE1 ни одна операция раздела не создаёт строк в очереди уведомлений, в `camp_*`, `points_ledger`, `booking_cancellations`, `service_payments`, `tournament_*`, `match_*`, `payments`; счётчики этих таблиц до и после полного сценария равны.
- NOSIDE2 мероприятия не попадают в `event_list`, `my_tournaments`, «Добавить матч», родительский календарь, статистику посещаемости и рейтинг (запросы этих функций до и после создания мероприятия возвращают то же).
- NOSIDE3 общие долги игрока и родителя (`DEBT_RULES`, `debtSeason`) не меняются от мероприятий в MVP (отдельное решение, U9).
- NOSIDE4 нигде не включаются реальные уведомления и не трогается `consent.mode` и `camps.notify`.

### UI. Веб (тесты Vitest, `web/src/screens/ClubEvents*.test.tsx`)
- UI1 (U15) раздел «Мероприятия» в админ-меню рядом с «События», отдельный пункт и отдельные экраны; «События» не изменились; тренеру, локальному админу, родителю пункта нет; навигация и «Назад» двух разделов не смешиваются (тест nav).
- UI6 (U14) список мероприятий показывает: активных участников, лимит (или «без лимита»), свободных мест = max(лимит − активные, 0); при превышении после снижения лимита — отметка превышения; отменённые записи в счётчик активных не входят.
- UI7 (U13) смена даты/времени: первый вызов без confirm возвращает предупреждение с числом затронутых активных записей и ничего не меняет; второй с confirm применяет; снижение лимита ниже активных — аналогично предупреждение и confirm.
- UI8 (N3) при изменении индивидуальной цены показывается засчитанная сумма; у отменённой записи она служит нижней границей (поле не принимает меньше), у активной показывается предупреждение «возникнет переплата X», не блокирует.
- UI2 предупреждение при смене даты/времени (с числом затронутых); предупреждение «игрок не из целевой группы»; предупреждение при снижении лимита; все не блокируют после подтверждения.
- UI3 поле «причина» обязательно и проверяется до отправки (≥ 3 символа), сервер всё равно проверяет.
- UI4 кнопки платежа/возврата/переноса неактивны там, где сервер откажет (по матрице), но сервер остаётся источником правды; повторный клик не шлёт второй запрос с новым `request_id` (один `request_id` на одно действие формы).
- UI5 долг и переплата показываются отдельно; список участников без сортировки по успехам.

### REG. Регрессия
- REG1 полный `scripts/run-db-tests.sh` на master до и после: все существующие тесты зелёные; новые зелёные; полный вывод прикладывается к PR.
- REG2 `db/ops/preflight.sql`: строки для каждой новой миграции, функции, триггера неизменяемости, права; preflight на master с миграциями — все `ok`, до миграций — красные (как у 0173).
- REG3 тест на «чистой» базе и на базе с default privileges Supabase (оба прогона).
- REG4 миграции с пересозданием `cash_report`/`cash_day_service` сливаются по одной, перед слиянием ветка обновляется от master, тела пересобираются (урок 2026-11-11).
- REG5 `backup-manifest-counts.sql` включает новые таблицы; откатные скрипты `db/ops/rollback-02xx-*.sql` есть для каждой миграции.

## 6. Принятые ответы U1–U15 (Павел, 2026-11-16) и оставшиеся вопросы

U1 цена 0 → долг 0, оплачено. U2 возврат и перенос без обязательной отмены. U3 платёж по отменённой записи ≤ текущего долга. U4 будущие даты запрещены, прошлые любые. U5 способы «Наличные» и «Перевод». U6 новые записи только активным игрокам; записанные сохраняют записи после архивации.
U7 журнал append-only: сумма, дата, способ, игрок, запись, op неизменяемы, комментарий в исходной операции не правится, уточнения отдельно в аудите, ошибки исправляются корректирующими операциями. U8 перенос: способ от исходного платежа, дата — текущая по Тбилиси. U9 долги мероприятий вне общих долгов. U10 долг отменённой записи остаётся, закрывается оплатой или индивидуальной ценой с причиной, цена не ниже засчитанного, списания нет.
U11 переплата только обычным возвратом. U12 один клуб; при >1 клубов без привязки админа создание запрещено. U13 `confirm`. U14 активные, лимит, свободные. U15 «Мероприятия» рядом с «События», два раздела.

### Закрытые вопросы N1–N4 (Павел, 2026-11-16)

N1 Корректировка ошибочного платежа — только обычный возврат и только при фактическом возврате денег; фиктивные возвраты запрещены; прочие ошибки исправляются отдельным ручным способом вне MVP. Тесты RF7, RF10.
N2 Пояснения к операциям — в `audit_log`; исходная операция неизменяема. Тесты HIST5, RF11.
N3 Индивидуальная цена может создавать переплату (D3). Исключение — закрытие долга отменённой записи (U10): новая цена не ниже засчитанной. Базовая цена (D1) переплату создавать может. Тесты PR7, PR11, PR12, UI8.
N4 Восстановление записи архивного игрока запрещено; финансовые операции по существующей записи доступны. Тесты PT5, PT13.

N5 (статусы игрока, Павел 2026-11-16: «подходит») «Активный игрок» в U6 и N4 = статус active «Занимается» (0104). Игрок на паузе (paused) и ушедший (inactive) новые записи и восстановление не получают; финансовые операции по существующим записям доступны. Тесты PT5, PT13 проверяют все три статуса.

Открытых вопросов по приёмке нет.
