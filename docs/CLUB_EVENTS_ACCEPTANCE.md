## 0. Утверждённые решения (источник: сообщение Павла 2026-11-16 + ТЗ #677)

### 0.1 Приоритетные решения 2026-11-16 (комментарий #6917798330, выше всего ниже)

P1 Переходы статусов мероприятия только: черновик→активное; активное→завершённое или отменённое; отменённое→активное. Черновик→отменённое запрещён. Завершённое→активное и активное→черновик запрещены.
P2 Платежи разрешены только для активного и завершённого мероприятия. Для черновика и отменённого мероприятия запрещены. По отменённой записи участника запрещены (раньше допускались при долге, это отменено).
P3 Переплата разрешена и показывается отдельно, как в сборах.
P4 Лимит можно снизить ниже числа активных с предупреждением; существующие записи не отменяются; новые добавления блокируются, пока активных не станет меньше лимита.
P5 Обязательные поля: название, дата, базовая стоимость. Время начала необязательно (решение 16.11 13:35): дата обязательна, время может быть не указано.
P6 Изменение индивидуальной стоимости: причина обязательна, минимум 3 символа, сохраняется в истории изменений.
P7 Раздел «Мероприятия» рядом с «События», самостоятельные разделы, функциональность не объединять.
P8 Цвета статусов: «Черновик» синяя подложка; «Завершённое» нейтральный цвет.
P9 Сущность `club_events`, без расширения `tournaments`, матчей, тренировок.
P10 (V1, утверждено 16.11 13:36) Платежи мероприятий хранятся в существующей таблице `service_payments` с новым видом `kind='event'`, `ref_id` = id мероприятия, `player_id` = игрок, `op='payment'`. Отдельной таблицы платежей мероприятий, отдельного финансового источника и таблиц под будущие операции не создаётся. Баланс мероприятия и записи считается только из этого журнала. `service_payments` не расширяется операциями возврата, переноса, сторно и отмены платежа: ограничения `op_kind_check`/`op_sign_check` для этих операций не меняются, для `kind='event'` допустим только `op='payment'`.
P11 Пилот на одном клубе при сохранении серверной изоляции по `club_id` и проверок прав; доступ к данным другого клуба недопустим.
P12 В MVP только приём платежей. Возвраты, переносы, сторно, отмена ошибочных платежей не входят в объём и не проектируются (решение 16.11 13:36); отложено до отдельного согласования. Участники MVP только игроки; семейное участие — запись игрока с нужной ценой. Общий долг игрока вне мероприятий не входит.
P13 Способ оплаты обязателен: только «Наличные» или «Перевод» (значения существующего набора `service_payments.method`); по умолчанию в форме ничего не выбрано; без выбора платёж не отправляется, сервер тоже отказывает.
P14 Ошибочный платёж нельзя исправлять фиктивным возвратом. В MVP исправление выполняется вне приложения владельцем по документированной процедуре (подготовить до реальных платежей, в этот пакет не входит). Защита от ошибки ввода внутри приложения: экран подтверждения (игрок, мероприятие, сумма, способ, дата); после подтверждения запись неизменяема.
P15 Черновик остаётся черновиком: удалить его нельзя, обходов «активировать и отменить» нет.
P16 Изоляция клуба: только на уровне базы (RLS и запрет по умолчанию, тесты); проверка `club_id` одними функциями не принимается.

### 0.2 Ранее утверждённые решения (в части, не противоречащей 0.1)

D1 Базовая цена меняется для всех без индивидуальной цены, включая записанных; баланс считается динамически; каждое изменение в истории цен; платежи не меняются.
D2 Смена базовой или индивидуальной цены требует причину, не короче 3 символов после trim.
D3 Переплата допускается, показывается отдельно от долга, операции не блокирует.
D4 [ОТЛОЖЕНО, P12] Перенос: только тот же игрок; только на другое мероприятие со статусом «Активное»; только если у игрока уже есть активная запись на целевое; между игроками и между типами услуг нельзя.
D5 [ОТЛОЖЕНО, P12] Частичные возвраты и переносы; сумма возвратов и переносов по платежу ≤ его неиспользованного остатка; каждая операция отдельной строкой; исходный платёж не меняется.
D6 Платежи (с учётом P2): черновик — нельзя; активное — можно; завершённое — можно; отменённое — нельзя; отменённая запись — нельзя.
D7 Переходы мероприятия (с учётом P1): черновик→активное, активное→завершённое, активное→отменённое, отменённое→активное. «Завершённое» конечное, в черновик возврата нет, черновик→отменённое нельзя.
D8 Лимит можно снизить ниже числа активных записей: предупреждение, не блок; новые записи сверх лимита нельзя; существующие не отменяются.
D9 Все даты, время, дедлайны и проверки по Asia/Tbilisi.
D10 Участники только игроки клуба.
D11 Восстановление записи сохраняет индивидуальную цену, платежи и историю; перед ним проверяются статус мероприятия, дедлайн, лимит; восстановление записи и реактивация мероприятия независимы.
D12 Пилот FC Kickstart: один клуб. До подключения второго клуба обязательны полная клубная изоляция и привязка админов к клубам (условие масштабирования, не пожелание).
D13 Раздел называется «Мероприятия», отдельно от «События».
T1 Отдельная сущность `club_events` и объекты `club_event_*`; `tournaments` не расширяется.
T2 (V1) Журнал платежей мероприятий = `service_payments` (`kind='event'`, `op='payment'`): только добавление, платёж не редактируется и не удаляется (триггеры 0179 действуют и на новый вид), повтор запроса не создаёт второй платёж (`request_id` обязателен, уникальный индекс `(recorded_by, request_id)` уже есть), автор и время ставит сервер, способ из существующего набора. Запись только через функцию `club_event_pay(...)` и страховочный триггер BEFORE INSERT для `kind='event'`.
T3 Платежи мероприятий входят в кассовые итоги `cash_report` и `cash_day_service` как вид «Мероприятие» без двойного учёта: одна строка журнала даёт одну строку кассы. Возвраты и переносы вне MVP.
Из ТЗ: один игрок — одна запись на мероприятие, включая отменённые (восстановление, не новая запись); отмена записи/мероприятия сама по себе возвратов и переносов не создаёт; физического удаления мероприятия нет; завершение вручную; уведомлений и родительской части нет.

## 1. Определения

- Цена записи = индивидуальная цена, если задана, иначе базовая цена мероприятия (замена, не сумма).
- Засчитано (MVP) = Σ(amount) строк `service_payments` с `kind='event'`, `ref_id` = мероприятие, `player_id` = игрок (все `op='payment'`). Возвратов и переносов в MVP нет, формула расширяется только отдельным решением.
- Долг = max(цена − засчитано, 0). Переплата = max(засчитано − цена, 0). Одновременно ненулевыми они не бывают.
- Связь платёж ↔ мероприятие ↔ игрок: однозначна по тройке (`kind='event'`, `ref_id`, `player_id`); уникальность пары (мероприятие, игрок) обеспечена таблицей участников (`unique(event_id, player_id)`). Ссылки `ref_id` в `service_payments` без внешнего ключа, поэтому существование мероприятия проверяют функция и триггер (PAY12, PAY13).
- Активная запись: статус `active`. В лимит входят только активные.
- Цена 0 допустима (бесплатное мероприятие); на неё платёж не обязателен, долга нет.
- Суммы: numeric(10,2), платёж строго > 0.

## 2. Матрица платежа (D6 и P2, проверяется целиком)

| Мероприятие | Запись | Новый платёж |
|---|---|---|
| draft | — (записей быть не может) | нельзя |
| active | active | можно (в том числе сверх долга, переплата допускается, P3) |
| active | cancelled | нельзя (P2) |
| finished | active | можно |
| finished | cancelled | нельзя (P2) |
| cancelled | любая | нельзя |

### EV. Мероприятие и жизненный цикл
- EV1 админ создаёт с названием, описанием, датой (обязательно) и необязательным временем, местом, базовой ценой ≥ 0 → строка создана, статус draft или active по выбору, club_id заполнен.
- EV2 (P5) обязательны название, дата и базовая стоимость: пустое/NULL название, NULL дата, NULL цена, цена < 0 → отказ; время, место, описание, дедлайн, лимит, группы необязательны; создание без времени проходит, время хранится как NULL (не «00:00»), список и карточка показывают только дату.
- EV3 без групп → общеклубное (признак выводится функцией списка); с 1 и с несколькими группами → связи созданы; дубль группы в списке не создаёт вторую связь; группа другого клуба → отказ.
- EV4 (P1) допустимые переходы: draft→active, active→finished, active→cancelled, cancelled→active. Недопустимые: draft→cancelled, draft→finished, active→draft, active→active, finished→любой, cancelled→finished, cancelled→draft, cancelled→cancelled → отказ 55000, статус не меняется, журнал не пишется.
- EV5 физического удаления нет: DELETE и TRUNCATE таблиц мероприятий, групп, участников → отказ у всех ролей (включая service_role); функции удаления не существует.
- EV6 завершение только вручную: наступление даты ничего не меняет (статус остаётся active после даты).
- EV7 реактивация cancelled→active: записи, платежи, цены, история те же, число строк в журналах не меняется (нет дублей); новые записи снова ограничены дедлайном и лимитом.
- EV8 отмена мероприятия: записи остаются в статусах как были, платежей, возвратов, переносов не появляется.
- EV9 редактирование названия, описания, места, даты, времени (в том числе очистка времени), цены, дедлайна, лимита, групп разрешено в draft, active, cancelled, finished; изменение пишется в журнал изменений (кто, когда, что было, что стало).
- EV10 (U13) смена даты или времени (включая очистку времени) при наличии активных записей: вызов без `confirm` возвращает предупреждение (число затронутых) и ничего не меняет; вызов с `confirm = true` применяет; записи не отменяются. Без активных записей применяется сразу. Тот же контракт у снижения лимита ниже активных (LD4).
- EV11 дата и время хранятся и сравниваются в Asia/Tbilisi; мероприятие без времени относится к дате целиком (сортировка и «дата прошла» по дате); события около полуночи UTC (20:00–23:59 UTC) показывают правильную дату Тбилиси.
- EV12 (P15) у черновика нет перехода в отменённое и нет удаления: из draft возможен только draft→active; функции «отменить/удалить черновик» нет (grep-тест); обход «draft→active→cancelled» разрешён только как обычная последовательность по P1, отдельной кнопки-обхода в UI нет (UI17).
- EV13 сортировка списка по дате: ближайшие сверху, завершённые и отменённые ниже; правило подтверждается владельцем (раздел 9, вопрос 3).

### PR. Цена и история цен (D1, D2)
- PR1 запись без индивидуальной цены берёт базовую; с индивидуальной — её (не сумму).
- PR2 смена базовой цены меняет цену и долг у всех записей без индивидуальной цены, включая уже оплаченные частично; записи с индивидуальной ценой не меняются.
- PR3 смена индивидуальной цены одному игроку не меняет базовую и цены остальных.
- PR4 (P6) причина < 3 символов после trim (пустая, пробелы, 2 символа) → отказ, цена не меняется; для базовой и для индивидуальной; причина сохраняется в истории изменений цены (PR5).
- PR5 каждое изменение (базовая, индивидуальная, сброс индивидуальной на «по базовой») пишет строку истории цен: кто, когда, объект, старое, новое, причина; история не редактируется и не удаляется (update/delete/truncate → отказ).
- PR6 после смены цены платежей, возвратов, переносов не создаётся, строки журнала платежей не меняются (сравнить снимок до и после).
- PR7 снижение БАЗОВОЙ цены ниже засчитанного у записей без индивидуальной цены допустимо (D1+D3): долг 0, возникает переплата (возвращается только обычным возвратом); повышение выше засчитанного → долг > 0; платёжных строк не прибавилось.
- PR8 цена с тремя знаками после запятой, отрицательная, нечисловая → отказ.
- PR9 смена цены в завершённом и отменённом мероприятии разрешена (редактирование исторических данных), с причиной.
- PR10 повтор установки того же значения цены (базовой или индивидуальной) без изменения: новая строка истории и причина не требуются, ничего не пишется; сброс индивидуальной в «по базовой» — это изменение цены, требует причину и пишет строку истории.
- PR11 (N3/U10) индивидуальная цена ниже засчитанной суммы: у АКТИВНОЙ записи допускается и создаёт переплату (D3), долг 0, платёжных строк не прибавляется, переплата возвращается только обычным возвратом; у ОТМЕНЁННОЙ записи новая индивидуальная цена ниже засчитанной → отказ 22023 «price below counted», цена не меняется; равна засчитанной → долг 0, принято; выше → долг. Действует независимо от статуса мероприятия (активное, завершённое, отменённое). Граница: засчитано 0 → любая цена ≥ 0; сравнение с актуальным засчитанным (после возвратов и переносов).
- PR12 (U10, P2) долг отменённой записи: платёж запрещён (PAY10); единственный способ закрыть долг в MVP — изменение индивидуальной цены на сумму ≥ засчитанного с причиной (PR4); списания долга как операции не существует (grep-тест: нет функции/значения op «writeoff»/«списание» в разделе). Восстановление отменённой записи (PT9) после снижения цены: цена и переплата сохраняются как есть.
- PR13 (U1) цена 0: запись создаётся, долг 0, статус «оплачено» (вычисляется), платёж на цену 0 допускается как переплата только по правилам PAY (активная запись); индивидуальная цена 0 допустима.

### PT. Участники (ТЗ 5.3)
- PT1 добавление игрока клуба в active → запись active.
- PT2 повторное добавление того же игрока (активного и отменённого) → дубля нет, отказ 23505 с понятной причиной; параллельное добавление двумя сессиями → ровно одна запись.
- PT3 добавление в draft, finished, cancelled → отказ.
- PT4 игрок не из выбранных групп: функция возвращает предупреждение и добавляет только после подтверждения; без групп мероприятия предупреждения нет; предупреждение не блокирует.
- PT5 (U6) игрок другого клуба, несуществующий, архивный/неактивный (статус не «активный» по `playerStatus`) → отказ при добавлении; уже записанный игрок, ставший архивным: запись, платежи, возвраты, переносы остаются, список показывает запись; восстановление отменённой записи архивного игрока → отказ (повторное включение = новое участие, только активным); платёж по существующей записи архивного игрока разрешён по матрице.
- PT6 родитель, ребёнок-пользователь, тренер, анонимный вызов → отказ (раздел ACL).
- PT7 отмена записи: статус cancelled, строка и платежи на месте, засчитано не меняется, возврата и переноса нет; повторная отмена → отказ или идемпотентный no-op (поведение закрепить в тесте).
- PT8 отмена записи в finished и cancelled мероприятии допустима (исторические данные); добавление и восстановление там запрещены.
- PT9 восстановление (D11): та же запись (тот же id), статус active, индивидуальная цена и платежи сохранены; новая строка не создаётся; повторное восстановление активной → отказ или no-op; восстановление архивного игрока запрещено (PT13).
- PT10 каждая смена статуса записи пишет строку истории участия (кто, когда, из какого в какой).
- PT11 удаление игрока с записью мероприятия, который имеет платежи в журнале → отклоняется (как 0179); удаление игрока без записей не затрагивается.
- PT12 список участников отсортирован по имени, без рейтингов, голов, мест, сравнений; запрос списка не возвращает данных, которых нет в разрешённом наборе.
- PT13 (N4) восстановление отменённой записи игрока со статусом архивный/неактивный → отказ 22023 «player not active», запись остаётся cancelled; платёж, возврат, перенос по существующей записи архивного игрока (активной или отменённой) разрешены по матрице и правилам D5; смена статуса игрока обратно на активный делает восстановление доступным.
- PT14 (макет, экран 4) «Добавить группу»: одной транзакцией добавляет активных игроков группы клуба; уже участвующие (в том числе с отменённой записью) пропускаются и не дублируются; игроки со статусом paused/inactive не добавляются; перед подтверждением функция возвращает список (будет добавлено N, пропущено M); если после добавления активных станет больше лимита, вся операция отклоняется целиком (частичного добавления нет), записей не появляется.
- PT15 «Добавить группу» в draft, finished, cancelled мероприятие, после дедлайна, группа другого клуба → отказ; повтор того же вызова не создаёт дублей.

### LD. Лимит и дедлайн (D8, D9)
- LD1 лимит не задан → без ограничения; дедлайн не задан → без ограничения.
- LD2 лимит N: N активных → добавление (N+1)-го отклонено; отменённые записи место не занимают; после отмены одной активной добавление проходит.
- LD3 восстановление записи при заполненном лимите → отказ; при свободном месте → успех.
- LD4 (P4) снижение лимита ниже числа активных → предупреждение (возвращается число превышения), изменение сохраняется, записи не отменяются; новые добавления и восстановления отказ, пока активных не станет меньше лимита (при активных = лимит — отказ, при активных = лимит−1 — успех).
- LD5 лимит < 1 или нечисло → отказ (как `camps_capacity_check`).
- LD6 дедлайн: до момента — добавление проходит; в момент и после — отказ (граница: проверка `now >= deadline` по Тбилиси); восстановление после дедлайна — отказ; существующие записи, платежи, возвраты, переносы после дедлайна работают.
- LD7 дедлайн проверяется на сервере: прямой вызов функции после дедлайна → отказ независимо от веба.
- LD8 гонка: лимит 1, две параллельные сессии добавляют разных игроков → одна успешна, вторая отказ; гонка добавление/восстановление за последнее место → ровно одна запись активна. Скрипт `concurrency_club_events_seats.sh`.
- LD9 переход дедлайна между открытием формы и сохранением → отказ с кодом/текстом «дедлайн истёк».

### PAY. Платежи (D3, D6, ТЗ 5.5)
- PAY1 платёж по матрице раздела 2: все 6 строк × разрешено/запрещено → ожидаемый результат; для записи в статусе cancelled платёж отказан при любом долге; для active-записи платёж сверх долга принят (переплата).
- PAY2 несколько частичных платежей одной записи суммируются; засчитано, долг, переплата считаются по определениям.
- PAY3 платёж равен долгу → долг 0, «оплачено полностью»; платёж больше долга → переплата показана отдельно, платёж принят; следующие операции не блокируются.
- PAY4 сумма 0, отрицательная, NULL, > 2 знаков → отказ.
- PAY5 (P13) способ обязателен и только «Наличные» или «Перевод»; неизвестный, пустой, NULL → отказ на сервере; значения по умолчанию нет ни в функции, ни в форме; сохраняется как фактический.
- PAY6 (U4) дата платежа: пусто → сегодня по Тбилиси; будущая (по Тбилиси) → отказ; прошлая любой давности → принимается; граница «сегодня 23:59 Тбилиси» не отклоняется из-за UTC.
- PAY7 платёж игрока из другого мероприятия/записи, не существующей записи → отказ; сумма платежа не влияет на другие записи.
- PAY8 флага «оплачено» в таблице нет: статус «оплачено/долг/переплата» вычисляется (тест на согласованность: после любой серии операций вычисленное совпадает с Σ из журнала).
- PAY9 автор (`recorded_by`) и время ставит сервер; клиент подделать не может.
- PAY10 (P2, заменяет U3) платёж по отменённой записи → отказ при любом долге, в том числе в активном и завершённом мероприятии; платёж по активной записи сверх долга разрешён (переплата, P3). Параллельные платежи по одной записи суммируются без потерь (блокировка записи).

### RF. Возвраты [ВНЕ ОБЪЁМА MVP, P12: не проектировать и не реализовывать; таблиц и столбцов под них не создаётся (PAY18)]
Ниже сохранён перечень проверок как заготовка для будущего согласования; он НЕ входит в MVP и не определяет схему.
- RF1 возврат полной суммы платежа → строка refund со ссылкой `refund_of`, исходная строка не изменена (побайтово), засчитано уменьшилось.
- RF2 частичный возврат; два частичных возврата подряд; сумма возвратов = остатку платежа → остаток 0; ещё один возврат → отказ «выше остатка».
- RF3 возврат > остатка платежа → отказ; возврат по платежу другой записи/другого игрока → отказ; возврат по refund/transfer-строке (не по payment) → отказ.
- RF4 возврат разрешён для записей и мероприятий всех статусов, включая отменённое мероприятие и отменённую запись; возврат без предшествующей отмены допускается (U2).
- RF5 возврат допускается, даже если засчитано станет ниже цены (долг возникает); возврат не создаёт отрицательную переплату сверх логики формулы.
- RF6 способ возврата из набора, дата не будущая; авто-возврат при отмене записи/мероприятия/реактивации не создаётся (счётчик строк до и после).
- RF7 (U7/N1) исходный платёж и все строки журнала: UPDATE любого столбца (сумма, дата, способ, игрок, запись, op, ссылки, request_id, комментарий, автор, время) → отказ у authenticated, service_role, anon; DELETE и TRUNCATE → отказ; допустимых «разрешённых столбцов» нет (в отличие от 0179). Корректировки ошибочного платежа функцией «сторно/отмена платежа» нет (grep-тест: ни такой функции, ни op); исправление только обычным возвратом.
- RF8 (U11) переплата возвращается обычным refund (≤ остатка платежа); функции/операции «списать переплату» нет (grep-тест); возврат переплаты уменьшает переплату в точности на сумму.
- RF9 (U4/U5/U8) refund: дата выбирается админом, пусто → сегодня Тбилиси, будущая → отказ; способ выбирается админом из «Наличные»/«Перевод», не обязан совпадать со способом исходного платежа; способ и дата сохраняются в строке возврата.
- RF10 (N1) возврат фиксирует факт возврата денег: обязательны способ из набора и дата (не будущая), параметра «без выплаты/фиктивный/корректировка без движения денег» нет; обязателен комментарий-пояснение не короче 3 символов, который пишется в `audit_log` (RF11); попытка «вернуть» без способа/даты → отказ. Для прочих ошибок ручного исправления в разделе нет (вне MVP), тест: список функций раздела не содержит функций правки/удаления финансовых строк.
- RF11 (N2) пояснение к возврату и любые уточнения к операции пишутся функцией в `audit_log` (actor, действие, сущность = id операции, текст, время); `audit_log` не даёт править исходную строку журнала; у пользователей authenticated прямой записи в `audit_log` нет.

### TR. Переносы [ВНЕ ОБЪЁМА MVP, P12: не проектировать и не реализовывать; таблиц и столбцов под них не создаётся (PAY18)]
Ниже сохранён перечень проверок как заготовка; он НЕ входит в MVP и не определяет схему.
- TR1 успешный перенос: создаются ровно две строки (transfer_out у источника, transfer_in у цели) с общим `transfer_id` в одной транзакции; сумма равна; исходный платёж не изменён; засчитано источника −X, цели +X, итог системы по игроку не меняется (нет двойного учёта).
- TR2 частичный перенос; перенос + возврат из одного платежа в сумме ≤ остатка; превышение → отказ; два параллельных переноса на сумму > остатка → проходит максимум один (скрипт `concurrency_club_events_transfer.sh`).
- TR3 другой игрок (брат/сестра) → отказ; тот же мероприятие → отказ; цель не active (draft, finished, cancelled) → отказ; у игрока нет записи на цель → отказ; запись на цель cancelled → отказ (нужна активная); цель из другого клуба → отказ.
- TR4 цель — не мероприятие (сбор, занятие, взнос матча, событие-турнир, абонемент) → такой операции нет/отказ.
- TR5 после переноса источник мог получить долг, цель — переплату; операции не блокируются (D3).
- TR6 перенос разрешён из мероприятия и записи любого статуса (U2); перенос из «чужого» платежа по другой записи → отказ.
- TR7 пара неделима: сбой на второй строке откатывает обе (инъекция ошибки); у каждой transfer_out есть transfer_in и наоборот (проверка целостности, запрос возвращает 0 сирот).
- TR8 параллельные переносы A→B и B→A: нет взаимной блокировки (порядок блокировок по id), оба завершаются или один получает отказ по правилам.
- TR9 transfer_out/transfer_in нельзя создать напрямую, только функцией (прямая вставка → отказ у всех ролей); повторный перенос с тем же `request_id` → ничего нового, возвращает результат первого.
- TR10 (U8, исправлено противоречие) перенос: дата обеих строк `transfer_out`/`transfer_in` = текущая дата Asia/Tbilisi на момент операции (не дата исходного платежа, не задаётся клиентом); способ обеих строк = способ исходного платежа; клиент не может задать ни дату, ни способ переноса (параметров нет); у обеих строк тот же `transfer_id`, в журнале виден источник (платёж и запись) и цель (запись).

- IDEM4 параллельные платежи по одной записи суммируются без потерь.

### HIST. Неизменяемость
- HIST1 (V1) строки `service_payments` с `kind='event'` защищены существующими триггерами 0179: DELETE и TRUNCATE → отказ у всех ролей; UPDATE полей сумма, игрок, `ref_id`, `kind`, `op`, `request_id`, автор, время, `cancels` → отказ у authenticated, service_role, anon (у ролей приложения нет права UPDATE вообще); новых триггеров «разрешённых правок» нет; приложение не содержит функции правки/отмены/удаления платежа (PAY18). Дата и способ уже исправляются владельцем БД существующим механизмом 0179 с записью в `audit_log` (`payment_correct`); тест фиксирует, что это единственный путь и что запись в журнале аудита создаётся; нужна ли для мероприятий более строгая блокировка (без правок даты и способа) — вопрос владельцу (раздел 9, вопрос 4). Отключённые триггеры показывает preflight (красный).
- HIST5 (U7/N2) уточнения к финансовой операции хранятся только в `audit_log`: функция добавляет запись с id операции, автором, временем, текстом ≥ 3 символов; исходная строка журнала не меняется (снимок до и после побайтово равен); повторное уточнение добавляет новую запись, старые не правятся; вызывать функцию может только админ (ACL1).
- HIST2 таблицы записей, истории статусов, истории цен, журнала изменений мероприятия, переносов: update/delete/truncate запрещены для исторических столбцов.
- HIST3 каскады: удаление игрока, группы или мероприятия с платежами → отклоняется целиком; ни один внешний ключ не имеет `on delete cascade` к финансовым строкам.
- HIST4 откат миграции (скрипт rollback) удаляет объекты только до появления данных; после появления платежей откат отказывает с понятным текстом либо сохраняет таблицы (поведение указать в README откатов).

## 4. Права доступа и клубная изоляция (обязательная проверка)

Роли для теста: A1 админ клуба; A2 админ второго клуба (фикстура); LA локальный админ (location_admins); C тренер; C2 тренер другой группы; P родитель с ребёнком в мероприятии; K ребёнок-пользователь; G гость/без роли; N аноним (anon-ключ, без JWT); S service_role.

### ACL. Права
- ACL1 функции создания, редактирования, смены статуса, добавления/отмены/восстановления записи, смены цены, платежа (`club_event_pay`): A1 — разрешено; LA, C, C2, P, K, G, N — отказ 42501; решение 13.11 (тренерам события создавать нельзя) соблюдено.
- ACL2 чтение таблиц и функций списков/карточек/участников/платежей/истории: A1 — можно; LA, C, P, K, G, N — пусто или отказ, без данных (в том числе имён игроков и сумм); P не видит даже мероприятия своего ребёнка (родительской части нет в MVP).
- ACL3 прямая запись в таблицы раздела и в `service_payments` (INSERT/UPDATE/DELETE) из роли authenticated, включая A1, → отказ; запись только функциями (SECURITY DEFINER с проверкой `is_admin()` внутри).
- ACL4 `anon`: EXECUTE на все функции раздела отозван, SELECT на таблицы отозван; проверка через `has_function_privilege`/`has_table_privilege` для anon, authenticated, service_role, public на базе с default privileges Supabase и на чистой базе; вспомогательные функции недоступны authenticated.
- ACL5 service_role: SELECT на таблицы разрешён для импорта/бэкапа, прямая запись в журналы запрещена (как 0165).
- ACL6 админ без записи в users или с `is_admin=false` → отказ; вызов без JWT → «not authenticated».
- ACL7 тренер не получает прав через имеющиеся функции событий-турниров (`event_assert_staff`): функции «Мероприятий» отдельные, `is_any_coach()` в них не используется (grep-тест на текст функций).
- ACL8 ни одна функция не возвращает данные о доле, голах, рейтингах, местах (продуктовое правило «без сравнений детей»).

### ISO. Клубная изоляция (P16: RLS, запрет по умолчанию, тесты; одних проверок в функциях недостаточно)
Определение клуба вызывающего: `club_event_current_club()` = `users.club_id` вошедшего; если пусто и в `clubs` ровно одна строка, то она; иначе NULL (NULL = отказ во всём разделе). Клуб клиентом не задаётся.
- ISO1 `club_id` есть у мероприятия, записей, журналов и истории; выводится сервером; клиент не может его задать или изменить (параметра нет, UPDATE закрыт).
- ISO2 целостность между клубами: игрок клуба 2 в мероприятие клуба 1, группа клуба 2 у мероприятия клуба 1, платёж по записи другого клуба → отказ (функция, триггер PAY13 и ограничения).
- ISO3 один клуб, `club_id` у админа NULL: раздел работает у админа (клуб определяется как единственный); у не-админа и anon нет.
- ISO4 два клуба, `club_id` у админа A1 = клуб 1, у A2 = клуб 2: A1 видит и меняет только мероприятия, записи, платежи (в том числе строки `service_payments` kind='event') и кассовые строки клуба 1; A2 только клуба 2; проверка и через прямой SELECT таблиц (RLS), и через функции, и через обе кассовые функции.
- ISO5 два клуба, `club_id` у админа NULL: весь раздел закрыт для этого админа (создание, чтение, платёж, касса), без ошибок утечки в тексте; прочие разделы приложения не затронуты (запрет только внутри раздела мероприятий).
- ISO6 подделка клуба: `users.club_id` не меняется пользователем (нет политики UPDATE на `users`, тест от роли authenticated отказывает), в параметрах функций клуба нет, `club_id` из JWT/метаданных пользователя не используется.
- ISO7 ограничительная (restrictive) политика на `service_payments` для `kind='event'`: другие виды не затронуты (регрессия по существующим тестам RLS), строка `kind='event'` видна только админу клуба мероприятия; локальный админ видит только `kind='equipment'` по прежним правилам и не видит `kind='event'`.
- ISO8 тест-страж `club_event_*`: каждая функция раздела и политика таблиц содержат проверку `club_event_current_club()`; глобальный `is_admin()` без клуба в этих телах и политиках → красный.
- ISO9 preflight: строка-страж «при `clubs` > 1 есть администраторы без `users.club_id`» → предупреждение (не блокирует, раздел закрыт у таких админов, ISO5); строка о наличии restrictive-политики и функции `club_event_current_club`.
- ISO10 доступ тренера, локального админа, родителя, ребёнка, гостя, anon к таблицам и функциям раздела и к строкам `kind='event'`: отказ или пусто, на базе с привилегиями Supabase по умолчанию и на чистой базе.
- ISO11 `service_role` (доверенная роль импорта и бэкапа) читает всё (SELECT), прямая запись в журнал запрещена (как 0165).

### NOSIDE. Побочные эффекты и смежные модули
- NOSIDE1 ни одна операция раздела не создаёт строк в очереди уведомлений, в `camp_*`, `points_ledger`, `booking_cancellations`, `tournament_*`, `match_*`, `payments`; в `service_payments` создаются только строки `kind='event'` через `club_event_pay`; счётчики этих таблиц (и `service_payments` по прежним видам) до и после полного сценария равны.
- NOSIDE2 мероприятия не попадают в `event_list`, `my_tournaments`, «Добавить матч», родительский календарь, статистику посещаемости и рейтинг (запросы этих функций до и после создания мероприятия возвращают то же).
- NOSIDE3 общие долги игрока и родителя (`DEBT_RULES`, `debtSeason`) не меняются от мероприятий в MVP (отдельное решение, U9).
- NOSIDE4 нигде не включаются реальные уведомления и не трогается `consent.mode` и `camps.notify`.

N5 (статусы игрока, Павел 2026-11-16: «подходит») «Активный игрок» в U6 и N4 = статус active «Занимается» (0104). Игрок на паузе (paused) и ушедший (inactive) новые записи и восстановление не получают; финансовые операции по существующим записям доступны. Тесты PT5, PT13 проверяют все три статуса.

## 8. Расхождения между условиями приёмки и мобильными макетами v3

Макеты: https://claude.ai/artifact/Kni1xBMVeH11WWHX4DoPx6. Совпадают: статусы и цвета (P8), переходы (черновик → «Сделать активным», активное → «Завершить»/«Отменить», отменённое → «Активировать снова»), дата обязательна и время необязательно, причина цены ≥ 3 символов, способ оплаты без значения по умолчанию, экран подтверждения платежа с фразой «Запись нельзя изменить или удалить», нет кнопок правки и отмены платежа, платёж запрещён по отменённой записи и в черновике, возвраты и переносы не показаны, переплата как отдельная строка у участника.

Расхождения (кто правит: M = макет, A = приёмка; решение за владельцем):

- M1 (переплата, вкладка «Финансы» и карточка участника): в блоке сумм «Начислено / Оплачено / Остаток» переплата не показана отдельно, у участника с переплатой «Остаток» неясен. По P3/UI14 нужны «Долг» и «Переплата» раздельными суммами, без отрицательного остатка и без взаимозачёта между игроками. Правит макет (A уже требует).
- M2 (окно отмены мероприятия): текст «Возврат автоматически не создаётся: решение по каждой оплате принимаете вы» подразумевает возвраты в приложении; в MVP их нет. Нужен текст вроде «Записи и платежи сохранятся. Возвраты в приложении недоступны» (UI12). Правит макет.
- M3 (вкладка «Финансы», примечание): ссылка на «отдельный журнал по образцу 0188» и «ожидает подтверждения» устарела: принят V1 (`service_payments`, `kind='event'`). Правит макет.
- M4 (отменённая запись): в макете нет «Изменить цену». По U10/PR12 закрыть долг отменённой записи можно только индивидуальной ценой с причиной, не ниже засчитанного; кнопка и нижняя граница нужны (UI16). Правит макет.
- M5 (изменение цены): нет предупреждения «возникнет переплата X» для активной записи и нижней границы для отменённой (PR11, UI8); поле «Причина» не помечено обязательным. Правит макет.
- M6 (список мероприятий): показаны только «Участников: N»; по U14/UI6 нужны лимит и свободные места. Правит макет, либо владелец сокращает UI6.
- M7 (завершённое мероприятие): в макете нет экрана; по EV9 «Редактировать» остаётся, кнопок статуса нет; платёж по активной записи в завершённом мероприятии разрешён (матрица). Нужен макет завершённого с «Принять оплату».
- M8 (история платежей): в строке время (14:20); в журнале есть `paid_on` (дата, выбирается админом, может быть прошлой) и время записи. Нужно решить, показывать ли обе даты, если они различаются (разница не противоречит правилам, а только отображению).
- A1 (приёмка v5): не было тестов на «Добавить группу» (экран 4 макета); добавлены PT14, PT15, UI15. Правит приёмка (сделано).
- A2 (приёмка v5): сортировка списка не была определена; добавлена EV13 с вопросом владельцу.
- A3 (приёмка v5): время считалось обязательным («дата-время»); исправлено (P5, EV2, UI13).
