# Техническая архитектура (Issue #18, черновик решений)

Статус: решения согласованы 2026-10-22, реализация начинается с миграций схемы. Бизнес-правила — `docs/RATING_SPEC.md`, переход — `docs/PLATFORM_PLAN.md`.

## Решения

1. **Бэкенд: Supabase (Postgres)** — авторизация, RLS, Edge Functions. Миграции через Supabase CLI, файлы в `db/migrations/`.
2. **Серверная логика бота и вход через Telegram: Edge Functions**, без отдельного Node-сервера.
3. **Клиент: `supabase-js` напрямую + SQL-миграции**, без ORM. RLS проверяется тестами в БД.
4. **Фронтенд: статическое SPA**, один код для браузера и Telegram Mini App.

## Вход через Telegram

Mini App передаёт `initData`. Edge Function проверяет подпись HMAC (ключ — HMAC-SHA256 от строки `WebAppData` с токеном бота), находит или создаёт `users` по `telegram_id` и выдаёт сессию Supabase. Роли берутся из связей: `coach_groups`, `player_guardians`, флаг администратора.

## Персональные данные

- Дата рождения и ФИО — доступ только через RLS; шифрование колонки — отдельная задача после первой миграции.
- Согласие родителя хранится с версией и датой; отзыв — `revoked_at`.
- `audit_log` пишется для изменений персональных данных и баллов.

## Баллы

Баллы — только журнал `point_events` (добавление без изменения). Сумма и уровни считаются запросом. Каждая запись ссылается на `rules` и хранит текст объяснения.

## Тесты

- Миграции и RLS: pgTAP в CI.
- Правила баллов: unit-тесты на функции начисления.

## Миграция данных

Сервисный аккаунт Google читает таблицы (только чтение), скрипт грузит данные по внешнему ID (`ID игрока` и аналоги) идемпотентно. Двойная запись и сверка — по `docs/PLATFORM_PLAN.md`.

## Структура репозитория (новая часть)

- `db/migrations/` — схема и политики
- `db/tests/` — pgTAP
- `supabase/functions/` — вход через Telegram, бот, групповой рейтинг
- `web/` — SPA
- `scripts/import/` — миграция из таблиц
