# Сериализация оплат взносов матчей и событий (миграция 0232, Issue #722)

Условия приёмки. Тесты `db/tests/rls_fee_pay_serialization_test.sql` и `db/tests/concurrency_fee_pay.sh` пишутся от этих условий, код после тестов.
Проблема: `event_pay` и `match_pay` (последние тела в 0072) читают взнос без блокировки и считают доплату по текущему остатку. Два параллельных вызова с `amt = NULL` оба видят остаток 100 и оба вставляют по 100, в журнале 200 при взносе 100.

1. **Блокировка до расчёта.** `event_pay` и `match_pay` перед расчётом остатка блокируют строку взноса игрока (`tournament_fees` / `match_fees`) через `select ... for update`. Остаток (`tp_paid` / `mp_paid`), материализация импортированной оплаты и вставка платежа выполняются уже под блокировкой, поэтому второй вызов по тому же игроку ждёт первый и читает остаток после его фиксации.
2. **Нет переплаты на гонке.** Два и больше параллельных вызова с `amt = NULL` по одному игроку дают ровно одну оплату на остаток; сумма платежей = сумме взноса; остальные вызовы возвращают 0 (остатка нет) и не вставляют строк. Для матча и для события.
3. **Частичная и полная оплата.** Частичная оплата с суммой `amt` не меняет правила: платёж на `amt`, флаг `paid` ставится, только когда сумма оплат ≥ суммы взноса. Доплата `amt = NULL` закрывает остаток; при остатке 0 возвращается 0. Явная сумма (`amt` задана) по-прежнему допускает переплату сверх взноса (решение владельца 13.11: переплата допустима, нужен явный ввод суммы); одинаковые явные платежи двух вызовов остаются двумя самостоятельными платежами (идемпотентность по ключу не входит в этот PR).
4. **Пакеты без deadlock.** Идентификаторы игроков блокируются в стабильном порядке (по `player_id`). Параллельные пакетные вызовы с пересекающимися наборами в разном порядке завершаются без `deadlock detected`, у каждого игрока ровно одна оплата остатка.
5. **Импорт.** Игрок с импортированным `paid = true` и без строк оплат: материализация «Оплата из импорта» выполняется один раз и под блокировкой; параллельные вызовы не создают две материализации.
6. **Права и бизнес-правила не меняются:** `event_assert_admin()` / `match_assert_fees(m)` вызываются до блокировки (тренер, не-администратор и чужой тип матча получают `42501` без блокировки строк); `player not in event` / `player not in match fees` (`P0002`), `bad selection` / `bad amount` (`22023`), дедупликация массива (0072), лимит 60 игроков, возвращаемое число — число игроков с проведённой оплатой. RLS таблиц и привилегии функций (`authenticated` — да, `anon` / `public` — нет, проверка на базе с привилегиями по умолчанию Supabase) без изменений. `search_path = public, pg_temp`.
7. **Не блокируем лишнего:** вызовы по разным игрокам одного матча и по разным матчам друг друга не ждут (блокировка строки, не таблицы); `match_fees_list`, `event_fees` и чтение не блокируются.
8. **Вне объёма (не расширять):** ключ идемпотентности для `event_pay`/`match_pay` (повтор с явной суммой после потери ответа); блокировка в `event_discount`, `match_discount`, `event_cancel_payment`, `match_cancel_payment`, `event_set_fee`, `match_set_fee`; проверка клуба в `match_assert_fees` (#843). Остаточные риски описаны в PR.

Откат: `db/ops/rollback-0232-fee-pay-serialization.sql` (тела 0072). Применяет только Павел после `db/ops/preflight.sql`; production backfill не нужен: функции только добавляют блокировку.
